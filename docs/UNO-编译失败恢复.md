# UNO 编译失败恢复

核对日期：2026-09-19。现行恢复契约为 `compile-response-recovery-v1`，局部失败隔离契约为 `compile-isolation-v1`。新建 v3 编译启用隔离；已有 v3 在用户明确继续后启用，历史 v2 保持原恢复行为。恢复与隔离不拥有知识写入权，也不替代原检查器、HarnessGateway、请求预算或用户停止状态。

## 主线与未组织池

正常单元保持一次生成、一次审核；通过卡先保存。缺失覆盖说明等确定性缺陷零请求处理；响应结构有歧义时最多一次仅含原响应、错误与局部 Schema 的格式恢复。空传输响应最多额外重试一次。单卡或关系每个未变问题仍最多两次自动修复。

局部失败超过上述额度后，保留原响应、候选、审核意见、来源版本、调用记录与已保存收据，将问题放入未组织池，主线继续独立的后续单元。候选 ID 无效或重复时隔离对应原对象，其余合法候选可以继续；无法辨认卡片边界时保留响应待恢复。未恢复的截断前完整候选仍保留在原检查点。

同一未组织池界面区分两类内容：**待组织**是已通过审核的正式卡；**待修复**是任务中的候选、响应、遗漏或待补写关系。待修复内容保存在原任务 `unit_work.isolation`，不写入正式卡片目录、不参与普通知识检索、不参与正式卡的领域治理。列表是任务状态的只读投影。新状态 `quarantined` 不计为单元完成，也不能让原书提前移出 Inbox。

仅明确的局部响应／候选错误可隔离。认证、额度、写入版本或来源冲突、用户停止等仍暂停主线；连续三个单元没有可用候选时熔断，避免供应商故障造成整本空转。格式恢复全任务最多三次，不因进入下一单元清零。

## 单项修复与结算

未组织池可查看候选正文、具体问题与来源，补充修复要求并启动独立修复任务。卡片正文修复仅发送该卡与问题；关系修复可额外交付明确关联的端点，且只能改 `relations`。无法辨认的响应可填写校正 JSON，再执行原审核与 Gateway 校验；原响应确实为空时，按钮明确说明将重新请求该单元候选。

每次显式单项处理有独立 12 次请求上限，绑定原任务、单元、隔离项、来源版本与候选快照。请求 ID 防止重复创建，同项已有运行、暂停或待确认任务时只能打开该任务。原任务运行中拒绝另开修复。用户显式新开单卡修复可获得该卡的新一轮修复额度，原任务的失败次数与账本不清零。

修复成功必须先经 HarnessGateway 原子保存，再由实际收据核对并回填原任务；收据关联同时验证父子任务范围、文件与历史版本。失败保留最新候选与问题，可继续精细处理。响应恢复后仍有单卡问题时转为对应的单卡待办，不把整个响应反复重做。通过卡指向原隔离候选的待补写关系，须按修复后的两端再次核验；关系失败单独留池，已保存正文保持可用。

修复后无领域的正式卡进入既有领域未组织池。只有该单元所有隔离项、遗漏与候选结算后才回填为 `processed`；整本来源满足原有完成条件后，通过 Gateway 核验原件再归档。用户已结束的原任务不会因修复被重新启动，后续成果由独立修复任务记录。

接口：`GET /api/uno/unassigned` 合并两类待办；`GET /api/uno/repairs/:id` 查看待修复内容；`POST /api/uno/repairs/:id` 要求知识库 ID、快照 revision、幂等 request ID，并可携带局部修复说明或校正 JSON。提交不直接写知识。

## 制卡覆盖说明缺失

生成或遗漏补全响应含有非空候选数组，数量及唯一安全 ID 合法、各卡标题与正文非空，但 `note` 缺失、为 null 或空白时，宿主标记“模型未提供覆盖说明；保留已返回候选，覆盖情况未作声明。”卡片内容保持原样，原始响应、恢复指纹和零模型调用记录保留，再进入正常审核与 Gateway 校验。该标记不证明覆盖完整，也不替代来源核验。

空候选仍须有具体不成卡理由；错误类型的 note、缺失数组、超量、重复 ID 或不完整候选不通过此路径。旧 v2 任务不启用此归一化。启用隔离的 v3 可对生成响应执行一次局部结构恢复，保留知识内容并重新校验，不能借此重新生成单元。

已有 v3 停点若保留了可恢复的生成响应，接口只读提供“审核已保留候选并继续”；用户继续后复用原响应，不重发原文。延期、结束、版本冲突和重复空转停点保持原限制。无法恢复的生成格式错误归为 `INVALID_GENERATION_RESPONSE`，界面区分缺数组、超量、缺说明及 ID 错误。

## 停点恢复计划

以下语义停点的延期／放弃行为用于尚未启用隔离的历史任务。启用 `compile-isolation-v1` 后，局部失败按前述规则留池并推进，不要求用户丢弃问题候选。

任务接口使用 `uno-resume-plan-v1` 把停点明确分为 `resume`、`decision`、`review`、`blocked` 和 `complete`。普通“继续”只对可重试的传输、额度、截断、提取失败或仍有明确检查点的任务开放；领域提案进入专用确认；版本冲突、已结算范围和没有安全恢复路径的失败不显示通用继续。

`UNIT_CARD_REPAIR_EXHAUSTED` 与 `UNIT_COVERAGE_BLOCKED` 属于语义停点。启用隔离的 v3 任务在前者发生时优先提供“保留到未组织池并继续”：不删除候选，把当前单元按 `quarantined` 结算并继续主线；用户仍可明确选择放弃候选或延期。尚未启用隔离的历史任务保持原来的放弃／延期选择。两类处理都保留原文、审核意见、已保存卡片和收据；放弃只移除本单元尚未发布且已经达到修订上限的候选，不触碰已保存卡片。延期把当前单元写入延期结果，后续明确恢复时仍可重开，不能计入全书完成。

语义失败单元延期到全书末尾时不会重新变成通用恢复。其修订次数和问题仍然有效；启用隔离的任务可将候选保留到未组织池后结束主线，也可明确放弃候选或结束任务并保留延期记录。不能靠再次点击继续重置修订上限。

恢复前保存语义检查点指纹，执行结束时只比较单元阶段、候选、审核问题、修复次数、收据和错误类别，不把版本号、时间和调用账本等记账变化当作进展。同一动作回到同一检查点与同一错误时，任务记录 `no_progress`，下一次不再提供相同普通继续路径。API 在补充预算、清空错误和启动任务之前检查恢复计划，因此被拒绝的点击不会消耗或提高预算，也不会改写任务版本。

建构任务使用同一恢复计划：真实的暂停检查点和仍有待发布批次可继续；人工审核进入专用确认；退役／版本冲突、未知非重试失败、无未完成批次以及重复空转均阻止普通继续。会话工作列表从同一计划投影 `can_continue`，不再依据“paused”状态猜测。

## 处理顺序

1. **先核对已保存状态**：恢复任务时先执行收据对账，已提交卡片不重写；同一请求已有有效恢复结果时直接复用。
2. **确定性修复**：只处理无需语义判断的缺陷。例如常规无原文检查中，`checked_ids` 与 `issues` 均有效而 `unit_issues` 缢失时，程序补为必需的空数组，再交回原校验器。此步骤不调用模型。
3. **局部响应恢复**：只有模型已经返回内容、但 JSON 语法或外层结构存在歧义时，才允许一次恢复请求。请求只包含失败响应、错误、预期 ID、允许的关系端点和局部 Schema；不包含原书、候选卡正文、参考卡、历史或工具。恢复模型关闭可选思考，只能重排已有内容，不能增加、删除或改写知识问题。
4. **原契约复验**：恢复结果必须重新通过 `validateReview`、审核范围、ID 和关系端点校验。恢复层不能降低质量门槛，也不能直接保存卡片。
5. **熔断**：同一失败响应按阶段、请求键和原始返回生成指纹。每个指纹最多一次模型恢复，每个任务最多三次；失败后进入隔离或历史停点，继续同一任务也不能再次支付同一恢复请求。

## 失败分类

下表描述停点保护；启用隔离后的局部结构、上下文或知识审核失败转入未组织池，全局错误仍暂停。

| 类别 | 典型情况 | 自动处理 |
|---|---|---|
| 响应结构 | 必需空字段缺失、JSON 外层错误 | 确定性修复；仍有歧义时最多一次局部恢复 |
| 输出上限 | 单元制卡被截断 | 沿用完整候选续写机制，不交给响应恢复模型 |
| 写入后中断 | Gateway 已提交而任务状态未保存 | 按幂等收据对账，不重新生成 |
| 预算与上下文 | 本轮可用额度不足、局部上下文超限 | 暂停并明确条件；只有用户明确继续才补足新一轮额度，不截断证据 |
| 状态冲突 | 来源、卡片版本变化或退役 | 暂停，不用模型覆盖版本冲突 |
| 知识审查 | 卡片或关系连续两次仍不通过 | 继续前先确定性对账审核范围、合法关系、宿主来源和过期问题；只为对账后实际变化的问题重新开放局部修复，未变的语义失败仍停止 |
| 用户停止 | 暂停、结束或执行超时 | 保留进度；结束后不允许迟到响应继续写入 |

## 状态与审计

任务公开 `last_recovery` 与 `last_failure` 的结构化摘要。提示词检查器把模型恢复单独标为“编译 · 响应恢复”，可以核对它是否只携带局部失败响应。原始模型返回保留在原调用记录中，恢复结果作为该响应的附属检查点保存，不覆盖原证据。

界面只说明恢复正在进行、已成功或已熔断。成功恢复不等于卡片已经通过后续知识审核或已经写入；任务仍按原编译阶段继续。

## 完成边界

程序回归覆盖必需空字段零调用恢复、一次局部恢复、同指纹熔断、输出截断、局部修复、关系修复和收据对账。脚本模型测试不能证明真实供应商总能返回可恢复内容。认证错误、供应商持续不可用、来源版本变化、语义缺陷和超出局部 Schema 的响应仍会暂停并等待明确处理。

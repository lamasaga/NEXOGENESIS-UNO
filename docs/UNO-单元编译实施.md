
## 原件与编译材料

现行局部失败处理为 `compile-isolation-v1`：通过卡立即保存；恢复及修复额度用尽的问题进入未组织池，主线继续独立单元。待修复候选、原响应和问题留在任务检查点，不进入正式卡库与检索；`quarantined` 不计为完成。未组织池支持每次最多 12 请求的独立单项修复，修复经原审核、Gateway 和真实收据回填原任务，待补关系重检端点后补写。全部待办结算前不归档原书。认证、额度、版本冲突、用户停止和连续三个无可用候选单元仍暂停。完整规则与历史契约兼容见[编译失败恢复](UNO-编译失败恢复.md)。

原始文件保存在 `03-Archive/books/<原件哈希>/original.<扩展名>`；清洗拆分后的 Markdown 单元、目录和提取图片保存在 `05-Buffer/books/<原件哈希>/<提取哈希>/`。来源单元按版本持续保留，被卡片引用后不能当作临时缓存清空。已有 Archive 单元仍支持校验、阅读与任务恢复，不自动迁移；明确授权的存储迁移通过 `HarnessGateway.migrateBookMaterialStorage` 校验整个提取版本后原子搬运。旧路径缺失时只读取 Buffer 中相同原件哈希、提取哈希和单元编号的文件，不改写来源内容或卡片引用。参考卡同源判断使用这些版本和单元编号。Buffer 的存储用途不自动扩大普通对话检索范围。

## 2026-09-18：统一分类契约

新建任务升级为 `unit-cards-v3` / `uno-unit-compile-v3`。每张卡只有一个主类型 `type` 与零到三个既有领域 `domains`；没有合适领域时使用空数组，新卡不得写 `tags/topics`。卡片自身 `domains` 是领域成员归属的唯一事实源。生成、常规审核、局部修复和复核共用同一分类说明、正文骨架及正反例；Gateway 使用任务冻结的同一领域目录校验。历史 v2 任务只按原契约恢复，不改签或混写。

自 2026-09-18 起，空领域卡不会只停留在 warning：它们进入可重建未组织池。编译在 10 个有效单元、20 张新未组织卡或有足够材料的书末边界批量治理一次。已有领域可原子挂靠；新领域形成有完整边界和成员清单的提案，默认逐项确认，也可在开始任务时授权本次编译自动批准。批准后由 Gateway 同时写入领域记录和首批成员。该请求不携带原书，完整卡正文最多 5 张，不能进入逐卡返工循环。详见 [领域治理方案](UNO-领域治理方案.md)。

未组织池的正式单卡可直接执行 `single-card-domain-assignment-v1`：请求只含当前卡和最多 8 个既有领域定义，不携带来源正文，也不重写卡片；确认归属后由 Gateway 原子挂靠。需要同时重写正文时使用 `single-card-source-rewrite-v2`，正文发布后再进入相同领域步骤。两条模型路径都不能自动凭单张卡新建领域；没有可靠既有领域时保持 partial 并继续留池。用户可另行从当前卡显式发起人工建域，完整填写领域定义并确认后，由 Gateway 原子创建领域、挂靠当前首个成员并关闭该未组织项；该操作不调用模型，不改变自动建域授权。领域请求中断不会撤销已发布正文，继续任务只恢复未完成的领域核对。

## 2026-09-18：卡片修复与关系修复分流

现行审核策略升级为 `review-publish-repair-v2`。审核问题必须声明 `kind=card|relation`；关系问题还必须列出本轮完整核对过的 `related_card_ids`。

- `card`：只提交问题卡与具体问题；不得新增关系目标。
- `relation`：只提交待修改卡、问题明确引用的当前端点卡与具体关系问题；允许在这些端点内新增、删除或改向关系，但程序强制正文、标题、类型、领域、摘要和来源保持不变。
- 关系修复先按当前两端版本判断旧问题是否仍成立。另一张卡已经改变、旧反向关系已消失时，返回原卡即可，不能执行过期意见。
- 两类问题分别计数，每类最多两次；复核也按同一类别和相同端点执行。旧任务里没有类别的关系问题，仅在问题文字明确包含关系语义及现有卡 ID 时迁移为关系修复，否则仍按单卡问题处理。

## 2026-09-17：审查后先落卡，问题卡独立修复

以下为 `review-publish-repair-v1` 的历史记录，已由上面的 v2 分流规则替代。标记本身不作为行为验证。

1. 建卡：一次提供完整单元、有限参考卡、与 Gateway 相同的主类型正文规范及经过该规范验证的完整示例。模型只输出 JSON，不附修复说明。
2. 审查：程序一次收集逐卡规格问题，模型检查内容和关系。具体问题须写明改法及必要的短证据，避免修复阶段再读原文。可选扩展不作为阻塞理由。
3. 落卡：通过的卡立即经 Gateway 保存。指向尚未通过新卡的关系暂存在任务中，目标通过后补上；不保存幽灵链接。每笔提交保存幂等收据。
4. 修复：只提交问题卡及具体 issues，source_chars=0，无其他卡、整章原文、旧卡参考或历史。仅核对该卡与原问题，每卡最多两次模型修复；原响应重读不算新请求。
5. 恢复：已收到的响应先接收，已提交的收据先恢复，之后才判断是否需要模型请求。历史请求账本不清零；用户明确继续时，可用额度补足到本轮设定值，未发生新请求时重复点击不叠加。失败不撤销通过卡，不冒称全章完成，原书保留。
6. 响应 Hook：检查和复核响应先通过原 Schema；缺少必需空字段等零歧义缺陷由程序归一化。仍有歧义时只允许一次局部模型恢复，不携带原书、卡片正文或历史，且恢复结果必须重过原校验。同一响应失败后按指纹熔断。

验证包含保存发生在修复之前、失败保留成果、延期关系补写、旧响应接回、写后中断收据恢复，以及实际请求中没有原文或其他卡。程序回归与历史响应回放不是新模型质量验收；不得据此宣称新书真实编译已经成功。

## 3. 编译现行契约（2026-09-17 单元制卡）

- 新入口统一为 `compile_profile=unit-cards-v3`、`workflow=uno-unit-compile-v3`。已保存 v2 任务按原契约恢复；v1 和更早任务只读，不改签、迁移或自动重放旧材料。
- Python 负责格式提取、清洗和 Markdown 切分。图书按真实章节，短文章保留整篇，长文章按内部章节与段落；自动判断可由用户明确选择图书/文章覆盖。
- 每个新任务按精确模型冻结 `workflow_limits=provider-aware-v1`。百万级上下文模型的原文与其余上下文分别最多 90,000 Unicode 字符，256K 模型分别为 72,000，128K 级模型与未知能力模型保持 60,000，更小的已登记模型使用保守上限。两类输入独立计数；旧任务没有该快照时仍按 60,000/60,000 恢复。
- 宿主一次提交完整原文生成本单元全部卡片，无模型补读工具、无原生多轮工具循环、无历史正文叠加、无子代理笔记。所有外发仍经过既有模型适配器、请求预算和快照记录。
- 生成后由同一 Gateway 预检规格、单一主类型、既有领域归属、来源、关系端点与版本；常规审核只携带候选卡与必要关系目标，不重新发送整章原文，不判定领域语义归属。例行审核显式使用七种合法关系枚举；程序剔除把合法关系判为非法或越权改领域的意见。需要核验明确遗漏时才按该遗漏携带必要短证据。检查材料超限时按卡片分组，不截卡、不累积历史。
- 只有问题卡收到修复请求，其他卡正文不重写。卡片问题只带本卡；关系问题只额外带明确的关系端点并只能修改 `relations`。每张卡每类最多两次自动修复，仍失败保留候选和具体问题；继续前若确定性治理使问题集合实际变化，只重新开放该卡受影响的问题类别。未变问题不清空计数，不重做已成功生成的整个单元，也不冒充完成。
- 标准质量模式下，正常单元一次生成、一次检查。高质量模式 `refine-each-card-v1` 在生成与同名卡处理后、正式审核前，对每张候选各增加一次独立精修：请求重新携带本单元完整原文、本卡和其已有的完整关系端点，可改善表达并确认主类型、领域与已有关系；ID、来源及关系目标范围由宿主锁定，结果仍须通过 Gateway 和独立审核。每张卡的输入、输出哈希与完成状态持久化，后续检查失败或任务恢复不会重复精修。存在具体问题时再增加局部修复及该卡复查请求。检查不是全库遍历，也不是多代理独立二审队列。语义检查可能判断错误，模型检查通过不代表知识质量得到证明。
- 参考卡只在本库卡片中确定性匹配，最多 3 张完整卡，另加最多 5 张仅含 ID、标题、主类型、摘要与既有关系的导航摘要，总计不超过 22,000 字符；不访问 Buffer 索引，不声称完成全库语义去重。导航摘要不能被修改，也不能作为新关系的内容依据。
- 已经引用当前原文单元的旧卡优先进入参考集。旧任务的冻结参考集仍可能遗漏同源旧卡；若模型再次返回同一 ID，宿主将其登记为本单元已覆盖并复用当前旧卡，不提交覆盖，也不阻塞同批其他新卡。重复编译不是分类迁移入口；旧卡需要改写时应在完整读回后走建构或明确修订。
- 用户设置的思考开关与深度只用于普通对话。新建 v3 编译按环节固化策略：制卡、遗漏补全、卡片修复和关系修复使用模型支持的较低有效档；候选审核及两类复核在可关闭模型上关闭思考。建构使用模型支持的高强度。固定思考且没有强度档位的模型不发送控制参数，保留供应商默认，不把 DeepSeek 的开关假定为所有模型都支持。
- 输出预算按精确模型冻结并受其能力上限约束：能力足够时单元制卡最多 98,304 tokens，遗漏补全、精修及两类修复最多 49,152，候选审核及两类复核最多 16,384；输出能力较小的模型自动取更低上限。预算是最大允许输出，并非固定消耗。若单元制卡因输出上限中断，程序只恢复 `cards` 数组中已经完整闭合且能独立解析的卡片对象，不发布这些候选；启用隔离时留池继续后续单元，其余任务暂停。明确续写时重新提供本单元原文与已保留卡片的 ID、标题、类型、摘要和关系清单，只请求剩余卡片，禁止重写已保留卡。
- 所有保存经过 HarnessGateway，单元卡片及同批关系原子提交；保留来源、版本冲突、幂等、历史版本和回滚。Markdown 仍是唯一语义事实源。原书在整本完成前留在 Inbox，成功后核验不可变归档才移出；原件归档在领域治理检查点之前执行，领域提案待确认不阻塞已完成原件归档。维护归档必须显式绑定当前任务、原件及提取版本，并记录对提取警告的核对依据；不能绕过未处理单元、递送记录或原件哈希检查，也不能把历史提取警告和任务状态改写为成功。
- Python 只清除有结构证据的噪声（控制字符、重复空行、PDF 页眉页脚、EPUB 链接目录）；不能因为论证重复就删除正文。原件、图像保全，OCR/图表无法可靠提取时明确缺口。
- 当前方法和正反例由 docs/design/book-compile-method.md、book-compile-examples.md 同批提供给模型。按知识对象完整性与复用价值决定卡片，不按字数或章数凑产量。

## 2026-09-17：真实 Web 任务的三处故障与一处审核范围错误

### 实际代码怎样走

### 1. 卡片格式从未真正接到执行链

此前 unit-card-request.js 只要求 body 为完整 Markdown，book-compile-method.md 写“结构随内容而定”。book-store.js 只验证非空正文、标签、来源与关系，没有调用金融底座的正文结构校验。因而按任意标题写出的读书笔记可以通过。抽查金融底座《12 国实际资产价格周期规律》等真实卡片可见稳定的分型骨架；当前已保存 5 张及第一章 12 张候选均未通过对应段落检查。这是格式不符的证据，不等于断言它们的全部内容错误。

历史修复：knowledge-quality.js 导出同源正文规范与预检函数；生成、审核、修复提示词使用该规范，并附完整既有正例；book-store.js 在原子写入前检查明确的主 type 和实际段落内容。当时 v2 仍使用 tags；v3 已由单一 `type` 与 `domains` 取代。来源段允许“来源与证据边界”，不因换行或标点变化拒绝引文，不强迫补造反例。结构正确仍不等于语义正确。

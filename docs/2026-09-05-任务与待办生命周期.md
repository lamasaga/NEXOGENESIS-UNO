# 任务、对话与执行状态

  本次修复源于实际故障：原生 `ask_user_question` 已在后台等待，但 Web 没有对应面板，实例切换却被会话的 running 标记拦截。普通对话、固定管线与浏览器连接还分别维护部分状态，容易出现完成提示互相矛盾或遗留任务接入下一轮。

| 对象 | 含义 | 本次实现 |
|---|---|---|
| 对话 | 消息与用户决定的记录 | 查看不会执行；所有新管线任务使用独立会话，旧记录保留 |
| 任务 | 明确的目标、冻结范围、进度与产物 | 继续复用原 Run 和预算，不创建新目标、不清空进度 |
| 执行回合 | 实际的模型和工具活动 | 回合结束与任务验收分开；后台观察者负责收尾和可信任务接续 |

## 使用方式

1. 顶栏“任务与待办”显示当前实例的全部可见会话，待答问题排在前面，并有数量提醒。
2. 点击“打开并处理”进入原对话。右侧“查看待办”可定位选择或确认卡；原生问题支持单选、多选和自由回答，失败保留表单。
3. 点击编译、主题编译、消化或建构，先进入对应任务列表。“新建”使用独立会话；“继续此任务”恢复原任务。旧任务不会因新建而被自动归档隐藏。
4. “暂停并保留”中断当前执行，保留任务进度与待答问题；“停止此任务”还撤销尚未提交的选择与写入提案。已提交的知识不回滚。管线执行时仍可使用“当前操作后暂停”，等待最小工作单元边界。
5. 实例切换只在没有实际执行、启动或接续操作时放行。保存的等待事项可留在原实例，切回后处理；正在执行时显示具体阻挡会话。

## 状态与恢复

  Web 通过 `/api/work` 获取统一视图，分别保留执行中标记与任务结果。原生待答队列由 DSH `apiProxy.events.mux` 重放；问题同时保存在原会话元数据。刷新浏览器不丢失待办；服务重启或暂停造成原问题调用失效时，用户回答会作为恢复消息投递原会话，而不是伪造原工具已成功返回。

  项目自己的选择卡和写入确认从现有持久化记录恢复。提交错误不先移除面板；选择卡不再因聊天仍连接而永久禁用。后台事件观察者独立于浏览器 SSE 连接处理回合结束、异常状态与可信管线接续；相同结束事件幂等处理。

  模型正常结束但任务没有通过完成门时，手动任务暂停并保留进度；可信任务沿用已有接续机制，在上限或投递失败后暂停。完成门、写入校验和预算不会因恢复而跳过或重置。没有新版 Run 的旧对话作为历史记录呈现，不猜测其已经验收。

## 验证与边界

  已有隔离回归覆盖待答重放、回答校验、失败保留、重启恢复、独立任务、幂等收尾、无浏览器连接时收尾、可信接续与边界暂停、实例切换与启动命令互斥。前端验证覆盖选择表单和等待优先于旧完成状态；真实模型的复杂长任务质量仍需后续使用观察。

  本机 Chrome 已验证真实待答问题在后台重载、浏览器刷新和实例来回切换后仍可显示，右侧与底部状态一致。模拟提交故障验证选项保留及重试，测试没有代答真实问题。桌面与窄屏均完成界面检查。

  启动器以 `work_lifecycle_version: 2` 检查后台版本。首批修复已在本机加载；最后补丁的进程重启遭自动审批拒绝，需用户重新运行启动脚本并接受旧服务重启提示。代码与构建已完成，不能把最后补丁尚未加载描述为完全生效。

  当前工具仍使用进程级活动实例目录，因此本次通过执行检查和指令互斥保护切换，未实现不同实例同时后台执行。暂停不是事务回滚，也不是所有外部工具都能瞬间终止；知识提交仍由原 Harness 保证。旧版已经归档隐藏的对话不会自动恢复到新列表。

  撤回可恢复旧 Web 与 Host 实现，保留原会话、Run、知识文件和待答问题元数据；本次没有迁移或改写知识卡片。

## 一、结论

当前主要问题是：工具协议故障迫使模型排错；预处理没有充分剥离元数据和公共尾部；字段修正被实现为全文覆盖；关系契约压制了一部分有价值的跨材料导航；批次遗留事项没有可靠地回收；动态系统提示词破坏缓存前缀。这些因素相互放大，不能简单归结为模型不够聪明或独立审核没有价值。

保留模型对选材、知识对象、聚合、归属、边界和导航价值的判断。程序接管可确定的定位、批处理、版本检查、依赖处理、进度统计和结算。先修可靠性与缓存，再衡量审核该如何压缩。

## 三、已经证实的问题

### A．工具协议故障正在消耗判断轮次

88 次工具错误中，40 次属于 `INVALID_TOOL_OUTPUT / value is not lossless JSON`：compile_task 15 次、compile_checkpoint 8 次、compile_read_material 17 次。

当前 snapshotV3 可产生值为 undefined 的 selection_reminder；归档阅读返回对象也可能包含缺失的元数据属性。直接渲染 JSON 字符串与工具框架验证原始对象不是同一件事。已实际运行只读快照检查，确认存在 undefined 属性；具体故障覆盖应在隔离宿主中验证。

尤其 checkpoint 会先保存再返回快照：保存成功但回执报错，会诱导模型重复保存或诊断无意义问题。归档阅读故障还使审核人反复更换路径，并尝试把草稿来源改成可读的 Buffer 引用。

其余错误包括清理区间不匹配 11 次、审核来源/版本/范围不满足等。部分属于必要保护，不能把全部 88 次都算成可删除的校验。

优化：工具输出统一成为合法 JSON 数据；可选属性省略或显式 null；每个写入回执明确是否已提交及稳定收据 ID。同一确定性程序错误不让模型盲目重试。修复范围包括原生工具验证层，不能只测函数返回值。

### B．预处理把不需要单独判断的东西变成了工作对象

16 份文章形成 32 个单元，其中每篇都有一个约三四百字符的 title、author、account、date、url、digest 头部单元。这些单元继续经历分类、阅读、结算与去向审核。

分批按单元数量和总字符数推进，还把李可书文章的元数据放在第二批、正文放在第三批。第二批将元数据标为 deferred，第三批处理正文后该遗留项仍在。另有采购文章的头部和正文被分到不同批次。

大量正文仍含“关于极新”“推荐阅读”等公共尾部。仅按标记以后长度估算会混入有价值内容，不能据此宣称某个精确比例可以安全删除；但现有样本足以证实公共推广和链接列表没有被充分清除。

优化：先解析文章元数据，作为来源属性随正文提供，不再生成独立消化对象。短文章以整篇为调度单位；长文分页只是阅读方式，不能无意拆散文章。跨文章重复模板由程序识别候选，模型处理有歧义的段落和保留要求。正文图示、出处链接与营销推荐链接分别处理，图片留档选项不意味着保留全部网页噪声。

### C．清理工具让模型承担字符定位劳动

compile_prepare 要求模型同时提交 Unicode 起止位置与完整删除原句，导致 11 次精确区间失败。选择阶段已经提交的 material_kind、attention、theme 又需要在正式阶段逐单元确认。

优化：让模型按稳定段落/区块 ID 选择删除范围、说明理由；程序计算字符偏移并验证版本。保留完整原件和删除记录。筛选中已经有效填写的分类和注意力继承下来，仅在有新证据时修改。明确模板清理自动执行，语义不确定项再交给模型，不增加一次固定的分类调用。

### D．局部修改意图导致整张草稿清空

日志证实 6 次只提供 sources 的 write 调用；stageKnowledge 的普通写入分支把未提供的 title、summary、body、tags 等设为空。这些草稿基础检查失败并被保存为 rejected，后续需要重新生成正文。此问题发生在草稿层；不是 6 张正式历史卡永久丢失。

91 次 write 不能视为 91 次高价值创作，也不能简单减去 52 就把其余全部算浪费，里面同时有合法修订、首次错误和修复性重写。

优化：明确区分完整替换与字段修改。完整替换缺少必填字段时，在覆盖现有草稿前返回字段错误；字段修改保留未提交内容。保留新候选与上个有效版本，避免修正一个字段使原正文消失。关系修改也应使用明确的增量接口。

### E．关系不足同时来自语义规则与工具负担

本轮并非完全没有建关系：20 次 link、1 次 unlink，最终保存 19 条关系。华强北、视频模型、采购案例已形成局部连接。但演讲观点、人物实体与技术卡的大量关系没有形成。

直接案例：首轮把“斯加鲁菲的定制化/低算力路线”与“霍夫曼的垂直 AI / 专有数据壁垒”以 analogy 相连，并说明两人的论据和适用维度不同。审核人依据 relations.md 中“编译只保存来源已经表达的类比”将其删除。审核人是在执行当前规则，不能简单指责其不注意关系。该关系是否适合称为类比，或更宜整理为对照，需要保留语义判断；但不应仅因两份来源没有互相比拟就禁止保存可解释的阅读导航。

另一例：霍夫曼实体卡写着“详见本库各主题卡”，却没有具体卡片链接和结构化关系。用户要求尽量保存实体，是为了后续关联使用，孤立的人物简介尚未实现这个用途。

当前关系统一标记 origin: document，也不适合直接承载模型整理的导航联系。仅改变提示语而不区分依据，会把导航判断伪装成作者论断。

优化建议：保留七种关系类型，增加关系依据区分——来源明确表达 / 根据已读卡片整理的导航。后一种须给出两端内容、具体比较或补充维度、适用边界；不允许凭空补因果或宣称证明。思考上下文中也保留这个区分。实体提及/观点归属可用可回查的实体引用索引承载，不必把所有关系硬塞进“补充”，也不需新增复杂的论证图谱。

制卡和审核时提供当前卡片组加相关旧卡的紧凑摘要，让模型一起考虑连接；保存卡片与待核对关系可以在一次语义提交中完成，由程序处理端点依赖。端点未通过时保留关系待办，不能因一条边牵连已经合格的整组正文。关系审核要求检查候选和给出实际理由，不要求每卡最低边数，不以连通率验收。

### F．独立审核做了必要工作，也承担了过多维修

审核 124 次请求，输入合计 7,723,802 tokens，约占全轮输入 44%。它确实核对了数字、作者身份与观点归属、预测和公告口径，并补回部分内容；不能据此取消审核。

但它同时处理了归档阅读失败、来源格式修复、整卡重建、版本变化后反复读回等。审核日志里存在很长的重复检查说明。仅改来源或关系，也会使整个草稿版本的读回/检查失效。

优化：为审核人直接组织当前有效草稿与按来源去重的证据，不提供作者长篇操作历史。完整审核干净来源与实质草稿；修改后的复核按影响范围区分。数字、归属、边界或来源变化需要回查对应证据；关系变化核对端点和理由；纯排版不自动触发全文重新理解。基础字段、端点、版本和引用存在性由程序检查。审核保留简短结论与具体问题，不要求每卡重复写一篇审稿报告。

阅读回执只证明文本曾返回，不证明理解。若新审核会话未获得对应证据，不能凭旧回执免读。对过长或来源不可靠材料保留分页补读和延期自主权。

### G．领域层需要跨批次回收整理建议

卡片引用 3 个领域 ID。本任务作者曾尝试创建领域，因仅允许审核人操作而失败；审核日志写明留给后续整理，但本任务没有成功执行领域写入。

更正：初稿以 02-Profile 为空推断当前领域文件不存在，检查路径有误。源码实际写入 01-Cards/_meta/domains；随后核对确认新任务 be347b32 已在那里建立 ai-industry.md。不能沿用“当前领域索引为空”的结论。其余两个领域 ID 是否已有实质索引、既有卡如何纳入领域，应按实际目录和检索实现核对。

优化：作者可以提出领域建议；程序把缺失领域汇总为当前批次或任务收尾的明确待办。语义摘要由模型按领域合并更新一次，程序建立成员反查。不逐卡调用领域工具，不拿自动生成的空壳冒充领域整体说明。领域关系仍只连接领域。

### H．任务收尾缺少针对遗留事项的路由

前两批各有 1 项 pending：华强北正文 cleaning_review_required 尚为 true；李可书文章元数据为 deferred。后续已完成正文，不会自动回收先前的元数据延期。

finishSelection 统计了历史 pending，因此部分完成并不是纯粹显示错误。但 remaining_sources 和 remaining_units 为 0，仅代表当前筛选与后续批次没有剩余，不代表历史待办消失。partial 的继续入口又把任务送回 select，容易出现“没有待筛材料→再次结束筛选→仍部分完成”。截图第 7/6 批则来自结束后的 batch_index + 1 被直接用于展示。

优化：结束时由程序核对实际对象，而非累计旧 pending 数字；区分范围完成、质量遗留与执行停止。继续操作应直达具体未完成对象，全部范围已结束时不再启动空筛选。面板展示“已完成 6 批；2 项需处理”及对象原因。模型阶段小结与程序统计分开；调用量、预算、余量、状态由程序渲染，长篇 Markdown 小结不直接塞入状态栏。

### I．缓存问题使所有额外轮次进一步变贵

本轮完整任务命中率 10.84%，此前中途快照约 10.6%。一个连续作者会话中，33 次请求有 33 个不同的系统提示词，工具定义稳定。最前面的变化是快照中的 remaining_calls。系统提示词位于所有历史消息之前，使后续重复的长上下文难以复用缓存前缀。

优化：固定规则、示例和工具定义维持稳定；任务初始要求固定注入；状态变化追加到后续运行时消息。只把状态移动到系统提示词末尾仍不够。回执按需返回，不反复携带整份任务快照。缓存命中与减少输入总量分别优化，不通过重复塞文本提高命中比例。

官方规则：DeepSeek 缓存自动启用，依赖完整匹配已缓存前缀，尽力而为，不保证固定命中率。[官方说明](https://api-docs.deepseek.com/zh-cn/guides/kv_cache/)

## 四、哪些地方需要模型判断

| 工作 | 模型应承担什么 | 程序应承担什么 |
|---|---|---|
| 材料筛选 | 结合用途判断价值、不确定时补读、决定投入顺序 | 提供全范围概览、版本与进度、记录理由 |
| 分类和主题 | 首次语义分类、有新证据时调整 | 继承已确认值，执行移动/更名 |
| 清理 | 判断有歧义的广告、事实、引文是否保留 | 元数据解析、已确认模板、区块定位、删除执行与回滚 |
| 阅读 | 理解干净正文、发现论证与知识对象 | 分页、去重、同篇归组、证据定位 |
| 成卡 | 对象粒度、正文、边界、标签和来源用途 | 字段检查、局部写入、版本保全、回执 |
| 关系 | 比较维度、导航价值、区别来源论断与整理判断 | 候选召回、端点与重复检查、反向索引 |
| 聚合档案 | 确有跨材料问题时整理证据和分歧 | 来源清单和稳定定位；简单单篇不强制另写档案 |
| 审核 | 独立核对忠实度、遗漏、归属、边界及关系 | 证据包、机械校验、变更范围、已解决问题结算 |
| 结束与恢复 | 解释实质未完成项；必要时提出下一步 | 计算状态、剩余对象、预算与路由，不空转询问模型 |

这是一份职责划分，不是要求每行独立调用一次 LLM。一次模型回复可同时提交若干已确定决定；工具结果带来新信息或出现实质不确定性时，再继续判断。模型仍决定下一步处理什么。

## 五、实施顺序与验收

### 第一组：修复已证实的程序缺陷

包括合法 JSON 回执、归档阅读、写入与字段修改分离、停止空筛选、历史待办直达、正确批次与用量展示。收益是消除维修性调用，代价是工具契约与状态恢复测试；不改变模型、知识类型或实质审核要求。

验收：在原生隔离宿主中重放上述失败形态，协议错误为 0；仅修改来源不得清空正文；写入已成功但响应异常可以凭收据恢复；完成 6 批不显示第 7/6 批；两个遗留项能被准确展示和定向处理。

### 第二组：同时修复缓存与预处理

固定提示前缀，动态状态后置；文章头部转为元数据；同篇短材料不跨批；重复尾部清理用程序执行，模型按块决策。删改保留原件、版本和差异记录，图片留档规则不变。

验收：相同任务目标和规范下，预算变化不改变固定前缀；16 篇样本不再产生 16 个独立头部消化任务；无需模型计算字符偏移；抽查重要引文、数字、图像引用与实质推广案例未被误删。真实服务的命中率和费用必须实测，不以本地前缀比较替代。

### 第三组：关系与审核方式一并调整

先对关系依据做明确语义区分，再组织候选、实体引用、领域待办和增量关系提交。保留独立审核，但让审核人阅读干净、按来源去重的证据，对修订按影响范围复核。来源内容与检索导航都保存在可追溯 Markdown 中，索引可重建。

验收：针对霍夫曼与斯加鲁菲、Sora 与混元、招采汇总与项目案例进行检索检查。比较是否召回互补信息和不同观点，理由是否准确，是否把模型导航冒充作者论断。不设最低边数；无有用联系可以不建。领域有实质说明或明确待办，不能只有不存在的 ID。

### 第四组：同材料对照，不凭调用量宣布成功

以这 20 份材料作为固定样本，在隔离知识库对照；已有卡片作为基线保留，不清空用户知识。先用小样本确认故障修复，再执行整组对照。模型、原始材料版本、用户偏好保持一致，记录真实请求数、输入/命中/未命中/输出、延迟、失败原因及恢复成本。

同时评估关键知识遗漏、数字与作者归属错误、卡片独立可读性、来源追溯和关系带来的检索增量。选定的问答样本至少覆盖观点比较、实体回查、案例召回和边界检索。成本改善不能以漏读、误删或削弱必要审核换取。暂不承诺某个降幅或 80%/90% 命中率。

# 历史关系遗留治理报告

## 一、治理目标

  本轮工作的目标不是为旧关系机械补齐 `note`，而是把历史图边重新判定为可保留、应改向、应改型、应移除或需延期，并确保最终进入 OPS 多跳推理的每条关系都有明确方向、具体机制和可检查边界。

  治理同时处理了旧冲突卡越权承担论证关系、互为镜像的冗余边、自指边与完全重复边。模型只负责提出语义判断，读取、预检和写入均由本地工具与 Harness 控制。

## 三、实际执行序列

1. 全量扫描旧边，按直接证据、共享来源、语义复核、优先移除和 conflict 角色迁移分组。
2. 将 conflict 收缩为争议档案，只允许用 `involves` 指向真实参与方。
3. 移除冲突档案与参与方之间重复、反向或越权的论证边。
4. 人工治理直接证据、全部 `involves`、含糊 note，以及随机贴现因子和危机形态学两个高连接关系簇。
5. 以受控批次调用 DeepSeek Reasoner 复核长尾关系；输出只写入 JSONL 决策记录，不直接改卡。
6. 丢弃格式不合格输出，延期低置信判断；其余决定编译为原子操作，经 Harness 全量预检后按每批不超过三张卡提交。
7. 人工精读最后六组端点，完成最终保留、改型与移除。
8. 检查并清理未被 `legacy_candidate` 捕获的自指边和重复边，同时将两类错误加入 Harness 硬约束。

  全过程共完成 159 个小批 Harness 事务。任何模型输出都没有绕过 Harness 直接写入卡片文件。

## 四、治理规则

- 同领域、标题相似或共享关键词不构成关系。
- `supports` 必须回答“源为目标提供了什么论据”。
- `based-on` 必须回答“源对象的成立为何依赖目标”。
- `extends` 必须保留目标核心并增加范围、条件或机制。
- `part-of` 表示源是目标结构中的组成环节。
- `applies-to` 表示框架、方法或原则在目标对象上的适用。
- `influences` 只用于源条件改变目标概率、方向或强度的机制。
- `conflicts-with` 只连接真实立场，conflict 卡只用 `involves` 归档参与方。
- 证据不足时优先移除或延期，不以流畅叙述替代关系证据。
- 卡片不得指向自身；同一来源、类型与目标只能保留一条关系。

## 五、工具与防复发机制

- `tools/audit-legacy-relations.mjs`：全库旧关系审计与证据分组。
- `tools/migrate-legacy-relations.mjs`：冲突契约与镜像关系迁移。
- `tools/review-legacy-relations-with-model.mjs`：只生成语义复核记录，不写知识体。
- `tools/compile-relation-review-decisions.mjs`：过滤低置信和不合格结果，编译原子决定。
- `tools/apply-relation-decisions.mjs`：统一预检与 Harness 小批提交。
- `relation-semantics.js`：现在硬性拒绝 conflict 越权出边、自指关系和同签名重复关系。

## 六、验收结果

  最终全库扫描结果为：1832 条关系全部 `ready`，`legacy = 0`，`invalid = 0`，`ghost_targets = 0`，`conflict_non_involves = 0`，`self_edges = 0`，`duplicate_edges = 0`。

  回归测试覆盖了关系语义、GraphOps 一至三跳、就绪关系扩散、Harness 原子写入与修订冲突、建构治理和写后验证。相关测试全部通过，其中 GraphOps 测试为 61 项通过、0 项失败。

## 七、结果边界

  本轮解决的是“历史关系是否达到当前推理契约”的遗留问题。`ready` 表示关系结构、来源和说明满足当前 OPS 使用门槛，不等于所有知识主张已经经过外部事实核验，也不等于关系强度已经有统计度量。后续知识质量评测仍应分别检验卡片内容真实性、证据强度和任务中的实际推理增益。

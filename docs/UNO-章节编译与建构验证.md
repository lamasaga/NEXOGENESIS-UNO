已确认的运行问题：

1. **选材完成后仍空转两次请求。** 第四次选材请求的 `compile_select(begin)` 已保存交接要求并返回 `end_turn:true`，随后仍发生一次无状态改变的 `compile_select(finish)` 和一次纯文字结束。UNO 没有接通原生工具的 `concludeTurn()`，运行时把结束信号当普通 JSON；`taskProgress` 在 `selection_request` 已存在时仍提示继续查看任务，形成相互矛盾的指令。
2. **简单阶段携带过多常驻内容。** 每次选材请求都有约 15,107 字符系统段及 10,994 字符工具 Schema，包含此阶段不会使用的成卡类型、正文示例和写入工具。这一层与“首包减少读操作”是不同的优化点，下一轮应按阶段缩小提示和工具集合，仍保留必要判断规则。
3. **请求预算实际上按 step 统计。** 原生同一步的错误重试、自动命名和压缩可产生额外供应商请求。因此 `budget_calls:20` 本身不能承诺最多 20 次外呼。本轮临时代理解决实验止损；它不代表正式产品已具备统一的供应商请求预算。
4. **检索和草稿写入也有本地耗时。** 阅读制卡阶段工具累计约 46.7 秒；首个查询约 13.6 秒。需要在后续同等冷热缓存条件下分开测量，不能全部归因于模型速度。
5. **关系依据字段错位后被静默升级。** 本轮一次 `compile_edit(action=link)` 把 `basis:"navigation"` 放在顶层，实际保存程序只读 `link.basis`，于是默认保存为 `basis:"source", origin:"document"`。请求成功和 `telemetry.ok:true` 没有暴露这种语义差错。新关系必须显式给出正确层级的依据，不能把未识别的导航意图默认为原文关系。

进一步核对：本轮 13 次作者阶段工具调用没有写入拒绝或重复 operation_id；7 个收据来自一次材料整理、五次制卡、一次添加关系。两次检索返回共 24,209 字符，超过一次完整章节读取返回的 9,821 字符。现有数据不支持把这轮问题归因于反复全文读取或反复写入失败。

## 据首轮证据实施的修复

已接通原生 `ToolRunContext.concludeTurn()`：只有成功结果携带结束标志，并核对当前任务已持久化交接、同一会话仍有效时，才结束原生回合。暂停、取消、错误、未通过完成门槛与批量中的未执行操作不算完成。`taskProgress` 同时识别选材交接标志，不再要求模型继续查目录。新增 6 项真实原生 ToolRuntime 用例验证交接边界；正式服务与本轮原始运行日志尚未使用此修复，真实节省量待下一轮验证。

已修正新关系的依据校验：`action=link` 必须显式提供 `link.basis: source | navigation`；顶层错位、缺失、非法值或同时提供两处依据一律拒绝，不写草稿、不追加成功收据。工具说明同步标清参数层级，删除关系仍可省略依据。校验位于事务的新写入分支，已有历史收据仍可按相同操作 ID 和原参数重放，保留后续审核；不会自动改写既有关系。13 项新用例覆盖本轮实际错误、两种合法归属、拒绝后无写入和历史重放。

两处修复合并后，`npm test` 全套 415 项通过，0 失败、0 跳过。其中关系归属及相关基础、建构用例 37 项通过。测试书草稿和原始运行记录保持不变。

阶段专用提示和工具过滤仍是下一项实验，没有混入本次结束接口修复。首包及元数据阅读复用仍通过 `evidence-pack-v1` 显式开启，不把未测路径自动设为默认。

独立本地核对（不替代模型审核）发现：5 张草稿正文合计约 5,493 字符，八项章节验收主题均有实质覆盖，保留了相对工资、广告空间口径、局部军工短缺与一般短缺的区别，也覆盖教育政策与教师工资。**卡片数少不是这轮低效的主要证据。** 当前更具体的质量问题是：

- 补贴卡称“作者承认其政策结论是规范性的”，把整理者对观点性质的判断归给作者。

- 军事卡将广告现象与解释称为“相互印证”，证据强度高于原文；具体论点目前只绑定整章，精确回查仍有改进空间。

## 本次架构取舍

程序负责原文切分、版本比较、范围校验、资料装入、收据、预算与原子提交；模型负责价值判断、机制解释、对象区分、证据忠实度与具体修订。减少模型做文件搬运、重复读稿和报进度的次数，保留需要语义判断的部分。

作者与审核者仍使用独立上下文。审核者直接看到当前稿件和原文，而不是长篇作者笔记；审核不以新增卡数、连边数或“全部满分”为目标。没有改善依据时允许保留原样，但要有实际阅读和具体保留理由。冲突观点可以并存，不用关系连线消除分歧。

本次没有同时更换 Agent 引擎、增加子代理、移除独立审核或缩写全部核心提示。先用同章对照判断首包和正文复用是否有效，再决定是否缩减常驻指南或改变作者输出接口。新机制仅由任务的 `execution_profile: "evidence-pack-v1"` 开启；普通入口与历史任务不自动迁移。撤回时不再为新任务传此字段即可；已有实验任务应先正常结束。

## 真实对照的执行与判断

1. **基线与改进分开运行。** 同一个章节、同一金融底座快照、同一模型和用户要求，各自使用新的运行目录。预处理修复先在两组共同固定，避免把切分差异误算为首包收益。记录代码哈希、来源哈希、模型配置与任务原始请求。
2. **一次只测一个完整章节。** 首轮按用户要求最多 20 次供应商请求；报告用量达到 25 万 tokens 或 15 分钟时请求暂停。监控不是精确账单硬限额，在途请求、未报告 usage、压缩和标题请求另行核对。暂停请求不等于底层已经退出。首轮已确认任务为 paused、代理无在途请求。
3. **编译逐项核对语义。** 保留作者身份、历史时点、因果机制、关键案例、证据与反例、成立条件。第三章的验收要点不等于要求生成固定数量卡片。新建、丰富或保留来源都必须解释真实增量与去向。
4. **建构只处理具体成果。** 从发布收据取得本章新增或改动卡片 ID，通过 `card_ids` 启动；必要的旧卡作为只读对照。比较正文、边界、来源和可检索性是否变好，拒绝为了凑联系而改写观点。
5. **检查重复与恢复。** 同版本重试不得重复写入；正文/来源变动应使旧阅读和审核失效；暂停后恢复不得自动扩大范围或恢复旧队列。
6. **用下一章检验迁移。** 第三章结果只能支持一个样本结论。用未参与调试的章节复测，再决定是否让普通 Web 入口默认采用新路径。

每轮记录：任务模型请求及缺失用量、非缓存输入、缓存读取、缓存写入、输出、压缩/命名辅助请求、总耗时、重复与失败工具调用、实际发布的新卡/修订、暂存草稿、未覆盖要点和建构前后差异。成本按同一供应商实际口径对比；字符数不能直接当 tokens。

验收优先级是：不越权、不丢来源、不重复提交；知识忠实度和可用性不下降；再比较成本与延迟。未达到质量要求时不能用“请求减少”宣布成功。若新路径无稳定收益，保留已经证实的切分与范围修复，撤下实验开关即可。

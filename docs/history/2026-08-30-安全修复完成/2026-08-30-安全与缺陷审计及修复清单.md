## 四、详细发现与修复要求

### SEC-01：本机 API 缺少可靠的同源请求校验

**证据位置**

- `packages/nexogenesis-web-host/lib/rpc.js`：`assertTrustedRequest` 只校验 `Host`，没有校验 `Origin`、`Referer` 或本地会话令牌。
- `packages/nexogenesis-web-host/lib/rpc.js`：`readJsonBody` 接受任意 `Content-Type`，包括浏览器可直接发送的 `text/plain`。
- `packages/nexogenesis-web-host/lib/index.js`：相关 API 路由只复用了上述 Host 检查。

**复现事实**

  使用 `Origin: https://evil.example` 和 `Content-Type: text/plain` 向 `/api/candidates/prepare` 发送无副作用的测试请求，服务返回了 `200`。单元级验证也表明：只要 `Host` 是回环地址，恶意来源仍会被接受，纯文本请求体也会被当作 JSON 解析。

**实际影响**

  浏览器同源策略通常会阻止恶意网页读取响应，但不会阻止它发送满足“简单请求”条件的 POST。因而，用户打开恶意网页时，该网页可能向正在运行的本机 Nexo 服务发起部分写操作。无需秘密 ID 的接口风险最高，例如创建项目、创建会话或上传 Inbox；依赖 UUID 的接口利用难度更高。这里不应夸大为“任意远程接管”，但它已经越过了当前本机服务应有的请求边界。

**最小修复**

1. 对所有会改变状态的请求严格校验 `Origin`；允许值只包括当前服务自身的精确来源。
2. 在 `Origin` 缺失的兼容场景中，结合 `Sec-Fetch-Site` 与 `Referer` 做保守判断，不能把“缺失”直接视为可信。
3. JSON API 只接受 `application/json`；上传接口只接受预期的 multipart 类型。
4. 服务启动时生成短期本地令牌，并要求前端在自定义请求头中携带。令牌只需用于本机 Web 会话，不必扩张为完整账号系统。
5. 为恶意 Origin、缺失令牌、`text/plain` JSON、合法同源请求分别增加回归测试。

**验收标准**

- 恶意 `Origin` 的所有写请求返回 `403`，且没有产生文件、会话或运行状态变化。
- `text/plain` 伪装的 JSON 请求返回 `415`。
- 正常 Web 页面在重新加载、流式对话、上传和任务运行中不受影响。
- 回环地址的不同端口不被自动视为同源。

### SEC-02：Harness 的 YAML/frontmatter 标量允许换行注入

**证据位置**

- `packages/nexogenesis-tools/lib/cards.js`：`quoteYaml` 没有拒绝或转义 `\r`、`\n` 等控制字符。
- 同文件中的 `validateCardRecord` 只校验卡片 ID 和部分基础字段，没有完整约束 `sources`、关系备注、metadata 键和值中的控制字符。
- 同文件中的 `serializeCard` 直接拼接 frontmatter。
- `packages/nexogenesis-tools/lib/index.js`：`propose_write` 的 metadata 允许额外属性；可信自动提交路径会直接提交通过现有预检的记录。

**复现事实**

  在临时知识库中，通过真实 Harness 提交来源字段 `05-Buffer/evidence/a.md\nlifecycle: archived`。预检与提交均成功，但重新加载卡片时，该卡片因被注入的 `lifecycle: archived` 而从默认结果中消失。这证明普通字段值能够改变 frontmatter 的结构含义。

**实际影响**

  该问题目前不是代码执行漏洞，但它会破坏 Harness 的核心承诺：通过结构化事务写入的数据，重新读取后不一定保持原结构与原含义。攻击或异常模型输出可以隐藏卡片、改变生命周期，或污染其他元数据，进而影响检索、建构和后续写入判断。

**最小修复**

1. 使用成熟 YAML 序列化器生成 frontmatter，避免自行拼接不完整的标量语法。
2. 对所有 frontmatter 字符串值和 metadata 键拒绝换行、NUL 及其他不允许的控制字符。
3. 文件落盘前，将序列化结果重新解析，并与规范化后的待写对象做深比较；不一致则拒绝提交。
4. 将“重新解析等价”放在临时文件重命名之前，保留现有原子写入流程。
5. 在可信自动模式和人工确认模式中使用同一套验证，不允许可信模式绕开语义完整性检查。

**验收标准**

- 所有包含 CR、LF、NUL 的 frontmatter 标量均在预检阶段被明确拒绝。
- 合法的中文、引号、冒号、反斜杠和 Unicode 内容能够无损往返。
- 对卡片执行“对象 → Markdown → 对象”后，结构化字段深度相等。
- 已有合法卡片能够继续加载与写入，不发生格式迁移事故。

### BUG-01：上传内容不完全保真，并可静默覆盖同名文件

**证据位置**

- `packages/nexogenesis-web-host/lib/inbox.js`：自写 multipart 解析保留了分隔边界前的 `CRLF`。
- 同文件上传写入使用 `writeFileSync`，目标存在时会直接覆盖。

**复现事实**

  在临时 Inbox 中先创建内容为 `original` 的 `same.md`，再上传同名文件。原文件被替换为 `overwritten\r\n`。这同时证明了静默覆盖和额外尾部字节两个问题。

**实际影响**

  同名上传或文件名清洗后的碰撞会造成原材料丢失；尾部 CRLF 会让磁盘文件与用户原始文件不完全一致，并影响文件哈希、归档指纹和二进制格式可靠性。对 PDF、EPUB 等二进制材料，不能依赖“多两个字节通常没事”。

**最小修复**

1. 优先采用维护中的 multipart 解析库；如果保留现有实现，必须严格按字节定位边界，不能通过文本式裁剪猜测内容范围。
2. 默认使用排他创建；同名时返回冲突，并由前端让用户选择重命名或跳过。
3. 如果采用自动重命名，名称必须稳定、可理解，并在响应中返回最终文件名。
4. 增加文本、PDF、EPUB、包含 NUL 字节文件的逐字节一致性测试。
5. 对文件名清洗后碰撞、大小写碰撞和重复上传增加测试。

**验收标准**

- 上传前后字节哈希完全相同。
- 已存在文件不会被无提示覆盖。
- 冲突响应不会留下半写文件。
- 前端能够明确显示“已上传、已重命名、已跳过或冲突”。

### SEC-03：EPUB 解压与 PDF 外部工具缺少资源边界

**证据位置**

- `packages/nexogenesis-tools/lib/compile/epub.js`：读取 ZIP 条目的未压缩大小，但没有设置单条目大小、总大小、压缩倍率或条目数上限；`inflateRawSync` 没有 `maxOutputLength`。
- `packages/nexogenesis-tools/lib/compile/pdf.js`：调用 `pdftotext` 时没有超时。
- `packages/nexogenesis-tools/lib/compile/figures.js`：调用 `pdftoppm` 时没有超时。

**风险说明**

  当前上传大小限制不能替代解压后大小限制。体积不大的恶意或损坏 EPUB 可能在解压时占用极大内存；异常 PDF 也可能让外部程序长期不返回。由于 Web、任务编排和转换目前位于同一 Node 进程链路，这会拖住任务甚至终止服务。

**最小修复**

1. 设置上传大小、ZIP 条目数、单条目未压缩大小、总未压缩大小和最大压缩倍率。
2. 为解压调用设置明确的输出上限，并在达到上限时返回可理解错误。
3. 为 `pdftotext`、`pdftoppm` 设置超时、输出大小限制和可取消机制。
4. 优先将高风险转换放到可终止的子进程；近期无需为此新建分布式任务平台。
5. 将资源限制作为配置常量集中管理，并在前端说明失败原因。

**验收标准**

- 超过任一限制的文件会快速失败，服务进程继续响应。
- 超时后子进程被可靠终止，不遗留孤儿进程。
- 正常规模的书籍、报告和图像转换不受影响。
- 测试使用可控小阈值模拟超限，不在测试机上制造真实内存耗尽。

### BUG-02：回答待决交互时先修改状态，后校验会话归属

**证据位置**

- `packages/nexogenesis-web-host/lib/chat.js`：先调用 `prepareCognitiveInteractionAnswer`，随后才比较交互所属会话。
- `packages/nexogenesis-web-host/lib/cognition.js`：准备回答会修改 interaction、workspace 和 run 状态。

**复现事实**

  使用不匹配的会话回答一个已有待决交互，接口最终正确返回“待答问题不属于当前会话”，但原交互已经变为 `answered`，对应 run 变为 `running`，且没有真正排入继续执行。这是典型的“报错了但状态已经变了”。

**最小修复**

1. 将查询和归属校验做成无副作用步骤。
2. 所有权限、状态、版本检查通过后，再一次性修改交互与运行状态并排入执行。
3. 如果入队失败，回滚状态或记录可恢复的待续事件，不能留下伪运行状态。
4. 增加错误会话、重复回答、已过期交互、入队失败的回归测试。

**验收标准**

- 任一校验失败时，interaction、workspace、run 和队列状态均保持不变。
- 成功回答只产生一次续跑，不会重复消费。
- 服务重启后能够识别并恢复或明确终止处于中间状态的交互。

### SEC-04：Nexo 项目对 DSH 会话的归属检查不完整

**证据位置**

- `packages/nexogenesis-web-host/lib/projects.js`：会话列表会过滤为项目 metadata 中登记的 Nexo 会话。
- 但会话详情、重命名、对话、取消和部分流式接口只接收 DSH session UUID，没有统一确认该会话属于当前 Nexo 项目。

**实际影响**

  如果知道另一个 DSH 会话的 UUID，当前接口可能读取、继续、重命名或取消该会话。回环监听、单用户环境和 UUID 难猜降低了外部利用概率，但这仍违反了项目隔离边界，也会让未来多项目并行时出现难以解释的串话或误操作。

**最小修复**

1. 提供一个共享的 `assertNexogenesisSession(projectId, sessionId)` 检查函数。
2. 会话详情、更新、聊天、流式事件、取消和各类 pipeline 接口全部复用该检查。
3. 检查必须基于项目登记信息或明确的会话所有权字段，不能只验证 UUID 格式。
4. 暂不扩张为多租户账号权限系统；先守住当前项目与会话的归属关系。

**验收标准**

- 当前项目只能访问自己登记的会话。
- 合法 UUID 但未登记的 DSH 会话统一返回 `404` 或 `403`，且无状态变化。
- 所有涉及 `sessionId` 的路由均有归属测试，而不只覆盖列表接口。

### SEC-05：CognitiveRun 的 `run_id` 存在路径穿越

**证据位置**

- `packages/nexogenesis-web-host/lib/run-store.js`：使用未验证的 `run_id` 拼接记录路径。
- HTTP 路由会先解码路径参数，编码后的斜杠可能重新成为目录分隔符。

**复现事实**

  单元级调用 `runtime.get('../escaped')` 可以读取 `runs/` 目录之外、名称符合预期后缀的 JSON 文件。固定目录、固定扩展名和本机访问限制了读取范围，但路径边界已经被绕过。

**最小修复**

1. 在路由层和 run-store 层都验证 `run_id`，只接受系统实际生成的 UUID 格式。
2. 明确拒绝点段、斜杠、反斜杠和解码后分隔符。
3. 路径拼接后校验解析结果仍位于 `runs/` 目录内，形成纵深保护。

**验收标准**

- `../`、`..%2F`、反斜杠、双重编码和非 UUID 值全部被拒绝。
- 合法运行记录的读取、更新和事件订阅保持正常。

### DEP-01：开发依赖存在公告，服务端依赖审计不可复现

**证据位置**

- `web/package.json` 中的 Vite 与 Vitest 版本落入当前公告影响范围。
- 完整 `npm audit` 报告 5 个受影响包；生产依赖审计为 0。
- 仓库根部和 Web Host 依赖没有完整、统一、可复现的根锁文件审计路径。

**风险说明**

  Vitest 的严重级公告主要与其 UI/开发服务暴露方式有关；当前项目使用 `vitest run`，没有发现 Vitest UI，因此不能把该公告描述为生产环境已可利用漏洞。Vite 高危同样主要影响开发服务器。不过，开发工具仍会处理本地源码与浏览器请求，应升级并保持只监听回环地址。

**最小修复**

1. 在现有测试全部通过的前提下升级 Vite、Vitest 及受影响传递依赖。
2. 明确开发服务器默认只监听回环地址。
3. 为服务端依赖建立与实际部署一致的锁文件和审计入口；如果现有部署不使用根工作区，不必为了形式统一强行重构包结构。
4. 将生产依赖与开发依赖审计结果分开记录，避免用一个总数误导判断。

**验收标准**

- 升级后前端测试、构建和浏览器基本流程全部通过。
- 生产依赖继续保持 0 项已知漏洞。
- 开发依赖剩余公告有明确的适用性说明或升级计划。
- 新环境能够从锁文件安装出一致版本。

### BUG-03：聊天 SSE 的单帧解析错误会终止整条流

**证据位置**

- `web/src/api/client.ts` 的聊天流解析对每个 `data:` 帧直接执行 `JSON.parse`，没有单帧级异常处理。
- 同文件另一条事件订阅路径已经具备局部捕获，两个实现行为不一致。

**实际影响**

  网络截断、服务端异常帧或代理插入的非 JSON 消息会让整个聊天流抛错退出。它通常不是安全漏洞，但会造成“模型没有反馈就结束”的用户体验，并掩盖真正的服务端错误。

**最小修复**

1. 统一两条 SSE 解析逻辑，按帧捕获 JSON 错误。
2. 对不完整尾帧执行 decoder flush，并区分“可忽略心跳”“服务端错误事件”和“损坏数据”。
3. 向上层返回可理解的流错误，同时保留此前已收到的内容。

**验收标准**

- 单个损坏帧不会清空已显示内容。
- 截断尾帧、空帧、心跳和明确错误事件均有测试。
- 正常流的首字延迟与渲染行为不明显退化。

### RISK-01：不可信材料中的提示内容可能影响编译与消化决策

**现状判断**

  项目级 compile/digest 技能尚未明确地把来源正文标记为“不可信数据，而不是可执行指令”。如果书籍、网页导出或报告中包含“忽略此前要求”“调用某工具写入某内容”等文字，模型可能把材料中的句子混同为系统要求。在 trusted/auto 模式下，结构合法但语义受污染的结果仍可能被 Harness 提交。

  这属于知识污染和 Agent 提示注入风险，不等同于当前已经存在主机代码执行。上游 DSH 或模型服务可能还有通用防护，但本次审计没有在 Nexo 项目自身契约中看到足够明确、可测试的边界，因此应作为设计风险处理。

**最小改进**

1. 用明确的数据包络标记材料正文、用户任务、系统契约和工具返回，禁止把材料正文当作指令。
2. 在 compile/digest 的系统要求中写明：只能提取和分析嵌入指令，不能服从嵌入指令。
3. 对来源不明的材料默认保留人工确认或隔离预览；不要声称可以自动识别所有恶意提示。
4. 所有写入继续保留来源、证据定位和写入事务记录。
5. 建立几份包含典型提示注入文本的对抗样本，验证系统不会据此改变任务目标或绕过写入规则。

## 七、建议新增的安全回归测试

### 请求边界

- 恶意 Origin 的 POST、PUT、DELETE 请求均被拒绝。
- `text/plain`、错误 multipart 类型和缺失本地令牌的写请求被拒绝。
- 合法同源请求、SSE 和文件上传保持正常。

### Harness 与卡片完整性

- sources、relations、metadata 键和值中的 CR/LF/NUL 被拒绝。
- 引号、冒号、中文、Unicode 和反斜杠能够安全往返。
- 序列化后重新解析的对象与预期结构一致。
- trusted/auto 模式不能绕过上述验证。

### 上传与编译

- 文本、PDF、EPUB 和二进制样本上传前后哈希一致。
- 同名文件、清洗后同名和大小写碰撞不会覆盖已有材料。
- ZIP 条目数、解压总量、单条目大小、倍率和工具超时均有边界测试。

### 会话与运行状态

- 错误会话回答交互后，所有状态保持不变。
- 未登记会话不能被读取、续聊、重命名或取消。
- 非 UUID、编码斜杠和点段不能访问运行记录。
- 重复回答、重复取消和入队失败保持幂等或可恢复。

### 前端流式处理

- 损坏帧、截断尾帧、空帧和错误事件不会清空已有内容。
- 用户能看到明确错误，而不是无反馈结束。

## 八、本轮明确不做的扩张

  为保持修复范围可控，本轮不因为本机同源问题引入完整账号、组织和多租户权限系统；精确同源校验加短期本地令牌已经足以解决当前风险。会话隔离只补齐项目归属谓词，不预先搭建未来可能用到的 RBAC 平台。

  本轮也不为了一个 ZIP 或 multipart 问题重写整个编译系统。优先使用成熟解析库、资源上限和回归测试替换脆弱局部；只有当现有同步执行无法可靠终止时，才把具体转换步骤迁移到可终止子进程。

  对提示注入不作“完全防住”的承诺。当前目标是明确区分指令与材料、降低自动写入权限、保留来源和建立对抗测试，而不是制造一个无法验证的语义安全模块。

\# 图检索与高级图分析：技术讲解（面向实施选型）



　　先把一句话说清：\*\*你们现在的「图」已经存在，只是还缺「能程序化走路、能算结构指标」的那层索引服务\*\*。下面按「今天有什么 → 要加什么 → 代码怎么跑」来讲。

\## 二、今天代码里「图」已经是什么



\### 2.1 节点：每张卡片是一个 dict 里的 `Card`



`Store.load()` 扫 `01-Cards/\*.md`，把 frontmatter 解析成 `Card` 对象，放进 `cards: dict\[id, Card]`：



```19:38:nexogenesis/store.py

&#x20;       self.by\_domain = {}

&#x20;       ...

&#x20;       for path in sorted(self.cards\_dir.glob("\*.md")):

&#x20;           ...

&#x20;           card = Card.from\_dict(meta\["id"], meta, body, str(path))

&#x20;           for d in card.domains:

&#x20;               self.by\_domain.setdefault(d, \[]).append(card.id)

&#x20;       return self
```

　　这就是图的\*\*节点表\*\*：key 是 `id`，value 是整张卡（含 `relations`、`domains`、正文）。



\### 2.2 边：三种来源，目前只「嵌在节点里」



| 边类型 | 存在位置 | 今天怎么用 |

|--------|----------|------------|

| 语义边 | `card.relations\[]` | validate 检查 target 是否存在 |

| 领域边 | `card.domains` | 建成 `by\_domain` 反向索引 |

| 正文边 | 正文 `\[\[id]]` | `WIKILINK\_RE` 在 validate 里扫幽灵链接 |



```61:78:nexogenesis/store.py

&#x20;           for rel in card.relations:

&#x20;               if rel.target not in self.cards:

&#x20;                   errors.append(f"{card.id}: 关系指向不存在的卡片 {rel.target}")

&#x20;           ...

&#x20;           for m in WIKILINK\_RE.finditer(card.body or ""):

&#x20;               target = m.group(1).strip()

&#x20;               if target and target not in self.cards:

&#x20;                   errors.append(f"{card.id}: 正文幽灵链接 \[\[{target}]]")

```



　　\*\*缺口\*\*：边没有单独的「邻接表」，所以不能高效地问：「从 A 出发走 2 跳能到哪些卡？」——每次都要重新扫全库。

　　适合人读、Agent 渐进阅读；\*\*不适合\*\*程序化多跳遍历。



\*\*（2）给 construct 用的结构扫描\*\* — `structure\_signals`：



```15:44:nexogenesis/ingest/structure\_signals.py

&#x20;   ...
```

　　这是\*\*高级图分析的雏形\*\*：在全图上跑确定性规则，输出文字信号。但它不做子图抽取，也不服务 `/answer` 检索。



\*\*（3）digest 的「伪检索」\*\* — `select\_deep\_cards`：用 Buffer 里的词去卡片 title/id/domains 里打分，\*\*不是沿边走\*\*，只是关键词撞库。

\## 三、图检索（G1）：代码里要发生什么



　　G1 的核心思想：\*\*不用向量，用「种子 + 沿边走 + 预算裁剪」\*\*。可以把它想成在知识地图上，从几个入口出发，只展开相关街区，而不是把整个城市塞进 LLM。



\### 3.1 第一步：`graph rebuild` — 建邻接表



　　输入：`Store`（已从 markdown 加载）。  

　　输出：`.nexogenesis/graph/` 下的边表 + 邻接结构。



伪代码（概念上）：



```python

def build\_edges(store: Store) -> list\[Edge]:

&#x20;   edges = \[]

&#x20;   for card in store.cards.values():

&#x20;       # 1) frontmatter 关系

&#x20;       for rel in card.relations:

&#x20;           edges.append(Edge(card.id, rel.target, kind="relation", type=rel.type))

&#x20;       # 2) 领域归属

&#x20;       for d in card.domains:

&#x20;           edges.append(Edge(card.id, d, kind="domain"))

&#x20;       # 3) 正文 wikilink

&#x20;       for target in parse\_wikilinks(card.body):

&#x20;           edges.append(Edge(card.id, target, kind="wikilink"))

&#x20;   return edges



def build\_adjacency(edges) -> dict\[str, list\[Edge]]:

&#x20;   adj = defaultdict(list)

&#x20;   for e in edges:

&#x20;       adj\[e.from\_id].append(e)

&#x20;       # 可选：无向边则 adj\[e.to\_id].append(e.reversed())

&#x20;   return adj

```



　　\*\*为什么要落盘？\*\* 卡片到几百张时，每次 digest 都全库扫一遍关系仍可接受，但邻接表缓存后：



\- `retrieve` 多跳是 O(边数)，不必重复解析 markdown  

\- `analyze` 算度分布、连通分量有统一数据结构  

\- 与 `index` 一样：\*\*删了 `.nexogenesis/graph/` 再 `rebuild` 即可\*\*



　　\*\*挂钩点\*\*：在 `write --batch` 成功、`generate\_indexes()` 之后加一行 `graph\_rebuild()`，和现有事务一致。



\### 3.2 第二步：种子选择 — 「从哪开始走」



　　用户问题：`怎样区分有效反思与自我感动？`



```python

def pick\_seeds(query: str, store, profile\_questions) -> list\[str]:

&#x20;   seeds = \[]

&#x20;   tokens = tokenize(query)  # 简单分词即可



&#x20;   # 策略 A：domain 卡 title / 核心问题 与 query 重叠

&#x20;   for cid, c in store.cards.items():

&#x20;       if c.type == DOMAIN and overlap(tokens, c.title, c.body\[:500]):

&#x20;           seeds.append(cid)



&#x20;   # 策略 B：问题清单里相似问题的关联领域

&#x20;   # 策略 C：显式 --seed 教学

&#x20;   # 策略 D（digest 专用）：Buffer 的 proposed\_domains、加粗词



&#x20;   return dedupe(seeds)\[:5]

```



　　\*\*空库\*\*：`seeds == \[]` → 返回 `status: empty-graph`，digest 仍走 bootstrap「先写 domain」。  

　　\*\*小库（<30 卡）\*\*：可退化「种子 = 全部节点」，不必多跳。



　　这和今天 `select\_deep\_cards` 的打分逻辑\*\*同源\*\*，差别是：种子确定后还要\*\*沿边走\*\*，而不是只看 token 撞 title。



\### 3.3 第三步：图扩展 — BFS 多跳



　　这是最「图」的一步。用队列做广度优先搜索：



```python

def expand(seeds, adj, \*, max\_hops=2, max\_nodes=24):

&#x20;   visited = {}

&#x20;   queue = \[(sid, 0, None) for sid in seeds]  # (node\_id, hop, via\_edge)



&#x20;   while queue and len(visited) < max\_nodes:

&#x20;       nid, hop, via = queue.pop(0)

&#x20;       if nid in visited:

&#x20;           continue

&#x20;       visited\[nid] = {"hop": hop, "via": via}



&#x20;       if hop >= max\_hops:

&#x20;           continue



&#x20;       for edge in adj.get(nid, \[]):

&#x20;           # 按场景过滤边类型

&#x20;           if edge.type in ("conflicts-with", "involves"):

&#x20;               ...  # judge / distinguish 场景多走这类边

&#x20;           if edge.target not in store.cards:

&#x20;               continue  # 不应出现，validate 已挡

&#x20;           if store.cards\[edge.target].lifecycle == "archived":

&#x20;               continue

&#x20;           queue.append((edge.target, hop + 1, edge))



&#x20;   return visited

```



　　\*\*hop 策略\*\*（设计计划里的 `construct-aware`）本质是 \*\*if 过滤不同 relation 类型\*\*：



\- 第 1 跳：所有 `relation` + `wikilink` + `domain`  

\- 第 2 跳：只沿 `supports` / `extends` / `applies-to` / `based-on`  

\- 遇到 `conflict` 卡：额外把 `involves` 的各方拉进来  



　　这样 LLM 看到的是「主张 → 依据 → 领域 → 对立面」的\*\*局部论证网\*\*，而不是随机邻居。



\### 3.4 第四步：排序与预算 — 装进 Context 窗口



　　扩展可能得到 40 个节点，但 `max\_chars=12000`。对每个候选节点打分：



```python

def rank\_nodes(node\_ids, query, store):

&#x20;   scores = {}

&#x20;   for nid in node\_ids:

&#x20;       c = store.cards\[nid]

&#x20;       s = 0

&#x20;       s += token\_overlap(query, c.title, c.id) \* 3

&#x20;       s += type\_weight(c.type)      # conflict/model 在分析场景加分

&#x20;       s += maturity\_weight(c.maturity)

&#x20;       s -= hop\_penalty(visited\[nid]\["hop"])

&#x20;       scores\[nid] = s

&#x20;   return sorted(node\_ids, key=lambda x: -scores\[x])

```



　　然后按分数从高到低累加正文字符，直到触顶：



```python

def pack\_context(ranked\_ids, store, budget\_chars):

&#x20;   parts = \[]

&#x20;   used = 0

&#x20;   for nid in ranked\_ids:

&#x20;       excerpt = excerpt\_body(store.cards\[nid].body, max\_per\_card=800)

&#x20;       if used + len(excerpt) > budget\_chars:

&#x20;           break

&#x20;       parts.append({"id": nid, "excerpt": excerpt, "hop": ...})

&#x20;       used += len(excerpt)

&#x20;   return parts

```



　　输出就是设计计划里的 \*\*Context Package\*\*（YAML/JSON + 可选写入 `04-OutBox/`）。



\### 3.5 与现有命令怎么接



| 今天 | 图检索之后 |

|------|------------|

| `select\_deep\_cards(store, buffers)` | `retrieve(mode="digest", seeds=from\_buffers(buffers))` |

| `card\_catalog` 全量塞进 prompt | catalog 仍全量（目录轻），\*\*正文\*\*只来自 retrieve 子图 |

| Agent 自己猜读哪些卡 | `graph retrieve --query "用户问题"` 先跑一遍 |



　　\*\*实施选型建议\*\*：不要另写一套 digest 逻辑，而是让 `context\_pack.select\_deep\_cards` \*\*内部改为调用 `graph.retrieve`\*\*，对外 API 不变——风险最小。

\## 四、高级图分析：代码里要算什么



　　分析 = 在整张图上跑\*\*确定性算法\*\*，产出 JSON + 一份人读的 `latest-summary.md`，供 `construct --diagnose` 读。  

　　你们已有 `structure\_signals`，相当于 \*\*L1 分析的手写版\*\*；正式 `analyze` 是把指标结构化、可缓存、可对比。



\### 4.1 L0–L1：健康与结构（实现简单，优先做）



| 指标 | 算法直觉 | 代码怎么做 |

|------|----------|------------|

| 节点/边计数 | 数数 | `len(store.cards)`, `len(edges)` |

| 孤立点 | 度为 0 | `len(adj\[id])==0 and len(in\_adj\[id])==0` |

| Orphan 实例 | 无出边且无 wikilink | 与 `structure\_signals` 第 40–44 行同逻辑，输出 `{id, type}` 列表 |

| 空 domain | `by\_domain` 只有领域自身 | 已有 signals，改为 JSON |

| Conflict 缺口 | `A conflicts-with B` 但无 conflict 卡 covers | 双重循环 + 查 `involves` 集合 |



　　\*\*与 structure\_signals 的关系\*\*：不要两套规则长期并存。理想做法是：



```text

analyze.py  →  metrics.json（机器读）

&#x20;          →  latest-summary.md（人读）

structure\_signals.py  →  读 metrics 或共享 analyze 内部函数，只负责「转成 construct 镜头语言」

```



\### 4.2 L2：拓扑（稍复杂，有价值）



\*\*桥接点（articulation point）\*\*  

　　直觉：删掉某张卡，图会不会裂成两块？  

　　经典算法：对每个节点临时 BFS/DFS，看连通分量是否增加——图很小（<500 节点）时暴力即可，不必上 Tarjan。



```python

def find\_bridges\_naive(adj, nodes):

&#x20;   bridges = \[]

&#x20;   base\_components = count\_components(adj, nodes)

&#x20;   for n in nodes:

&#x20;       adj2 = remove\_node(adj, n)

&#x20;       if count\_components(adj2, nodes - {n}) > base\_components:

&#x20;           bridges.append(n)

&#x20;   return bridges

```



\*\*领域间割\*\*  

　　把节点按 `domains` 上色，看连接不同领域的边有多少——边少 = 领域孤岛化。



\### 4.3 L3：与 Buffer / 涌现衔接



　　这部分你们\*\*已经有一半\*\*：`structure\_signals` 里 tension Buffer 未升格、`link-hypothesis` 待衔接等。  

　　`analyze` 只是把 Buffer 索引和 Card 图\*\*放在同一份报告\*\*里，让 construct 一眼看到「质料层张力 ↔ 卡片层冲突」的缺口。



\### 4.4 L4 / P2：演进与可视化



\- \*\*演进\*\*：对比两次 `metrics.json` 的 diff（新节点、新边、某 domain 成员数变化）——依赖 git 历史或 Journal，可很晚再做。  

\- \*\*GraphML\*\*：把 `nodes` + `edges` 导出 XML，给 Gephi 画——\*\*纯导出\*\*，不参与运行时检索。

\## 六、实施方法怎么选（决策清单）



\*\*问题 1：要不要单独图数据库（Neo4j）？\*\*  

　　\*\*建议：不要。\*\* 事实在 markdown，`Store` + 邻接表足够；节点规模到万级再考虑专用库。底座原则是「删索引零损失」。



\*\*问题 2：G1 和 G2 能不能跳过 G1 直接上向量？\*\*  

　　\*\*不建议。\*\* 向量解决「语义相近」；图遍历解决「结构相关」（A supports B，title 里没出现 A）。你们的关系是 digest/construct \*\*精心写进 frontmatter 的\*\*，不用图就浪费了。



\*\*问题 3：retrieve 放哪一层？\*\*  

　　推荐：`nexogenesis/graph/retrieve.py` 纯函数，无 LLM；`context\_pack` 和未来的 `talk`/`answer` 都调它。Harness 负责图，LLM 负责语义——与 AGENTS「Harness 过程、LLM 语义」一致。



\*\*问题 4：空库怎么测？\*\*  

　　契约测试：`rebuild()` → `stats()` 节点 0；`retrieve("任意问题")` → 空 package；`analyze()` → 空报告。  

　　\*\*不需要等有内容才写代码。\*\*



\*\*问题 5：与 v0.11 的 `--auto` 怎么配合？\*\*  

　　`digest --auto` 生成 prompt 前，Harness 先 `graph retrieve` 填深读卡列表；Agent 仍写 batch，自检逻辑不变。图检索\*\*不替代\*\* LLM，只缩小它该看的范围。

\## 七、一次完整调用的故事（串联）



　　假设库里有 50 张卡，用户说：「开始消化」。



1\. `digest --auto` → `context\_pack` 选 Buffer 波次  

2\. \*\*`graph retrieve(mode=digest, seeds=from\_buffers)`\*\*  

&#x20;  - rebuild 邻接表（若 write 后已做过则读缓存）  

&#x20;  - 种子：`教学` domain + Buffer 里加粗的「反馈差距」  

&#x20;  - 扩展 2 跳 → 12 张相关卡  

&#x20;  - 预算 12000 字 → 6 张深读正文 + 边列表  

3\. 组装 `prompt.md`（目录仍全量，正文来自子图）  

4\. Agent → LLM → `batch.yaml`  

5\. `digest --auto` 自检 → apply → `write` → \*\*`index` + `graph rebuild`\*\*  

6\. 下次 `construct --auto` → \*\*`graph analyze`\*\* 发现新 orphan → `distinguish` 镜头



　　全程没有向量、没有 Neo4j；图来自你们已经维护的 `relations` 和 `domains`。

\## 八、建议你采用的实施顺序



1\. \*\*G0\*\*：`graph rebuild` + `stats` + 写入后自动 rebuild（1 个 PR，空库可测）  

2\. \*\*G1 检索\*\*：`retrieve` 替换 `select\_deep\_cards` 的后端（digest 立刻受益）  

3\. \*\*G1 分析\*\*：`analyze` 吸收 `structure\_signals`（construct 诊断更稳）  

4\. \*\*攒 20+ 卡 + 手工黄金集\*\* 再决定要不要 G2  

5\. \*\*有审图需求\*\* 再做 GraphML

\*\*总结\*\*：图检索 = \*\*从 markdown 建邻接表 + BFS 取子图 + 预算打包\*\*；高级图分析 = \*\*在同一邻接表上跑确定性指标\*\*（你们已在 `structure\_signals` 里做过一版）。两者都是可重建索引，空库友好，且与 v0.11 摄入流水线自然衔接。



若你准备动手，最稳的第一刀是 \*\*G0 的 `graph rebuild`\*\*：不改任何 LLM prompt，只加索引层和测试；需要的话我可以按这个讲解直接拆成实现任务清单（文件级 + 测试用例）。

## 二、为何归档

  这些原稿分别形成于 ORG 迁移、DSH Agentic baseline、认知动效、知识沉淀闭环和关系质量改造等不同阶段。它们包含大量仍有价值的讨论，但也同时存在以下问题：

- 同一项目定位在多份文档中反复解释，概念层次和措辞不完全一致。
- 部分文档仍以 ORG/Python 路径、双执行平面或旧 CLI 作为当前实现。
- 已经落地的设计仍标记为“尚未实施”，阶段审计数字容易被误当作实时状态。
- 评测、受控迭代和历史回放分别成稿，但评价原则与实施顺序重复。
- 旧计划和新 SPEC 同时承担“唯一实施依据”，容易产生冲突。

  因此，本目录只用于追溯问题如何被发现、方案如何演变和某个数字来自哪次快照。开发者不得直接修改这里的旧文件来表达新状态。

## 三、使用历史材料的规则

1. 先读当前活文档，再按具体问题打开历史原稿。
2. 历史文件中的路径、命令、状态、数量和“已完成”均需重新核对。
3. 需要恢复某个被省略的研究细节时，把经过验证的结论补入对应活文档，而不是把旧文件移回根目录。
4. 不在历史目录继续形成平行规格。

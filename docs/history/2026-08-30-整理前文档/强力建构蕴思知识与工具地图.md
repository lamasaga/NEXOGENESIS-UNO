## 0. 这份文档回答什么问题

  这不是一份“把所有热门 AI 项目都装进来”的清单，而是对 Nexogenesis 愿景的一次技术整合。它回答四个问题：建构蕴思到底需要哪些能力；哪些学科和数学能把这些能力说清楚；哪些开源项目可以借用；这些知识最后应落在哪些代码边界中。

  主要依据有三组材料：`D:/UESR/Desktop/Evolvable Cognitive Architecture/` 中的《路线图》《数学》《学习》《SPUER知识图谱》《LOOP》《编译OPS》等讨论；本仓 `docs/可演化认知架构愿景与演进路线.md`；本仓 `docs/架构真图与后续路径.md` 以及当前 `nexogenesis/` 实现。外部项目和链接按 2026-08-23 的公开资料核对。

  “所有”在这里采用能力覆盖意义，而不是无限罗列项目。对每个方向都给出它解决的真实问题、适合进入的 GraphOps、建议阶段和不应做的事情。

## 1. 结论先行：建构必须是什么

  建构不是 `选择一个任务 → 调用一次模型 → 通过 Harness → 结束`。那种形式只能叫结构化管线，无法完成用户所说的蕴思。真正的建构应是一个有预算、有边界、可暂停、可恢复、能观察知识体并主动选择下一步的自治认知循环：

```text
观察知识图谱局部状态
    ↓
提出多个“下一步值得做什么”的假设
    ↓
用图结构、证据、因果、论证和历史轨迹比较候选
    ↓
选择一个 GraphOp 或继续侦察，而不是被固定步骤推动
    ↓
先 shadow/probe，再经过 Harness 闸门提交原子事务
    ↓
重新观察写入后的图，检查是否真的改善、是否制造新债务
    ↓
更新 agenda、置信度、策略经验和下一轮优先级
```

  这个循环的目标不是让一次运行“完成很多动作”，而是让每一轮都能说明：看到了什么、为什么选择这个动作、动作改变了什么、哪些候选被否决、下一步为什么转向别处。没有这些轨迹，就没有可进化的思维体。

  愿景中的外置认知架构可以写成：

```text
ECA = Memory + Representation + Operators + Policy
      + Workspace + Evaluation + Learning
```

  在本项目中，这七个部分不是七个平行产品，而是同一条建构链上的七种职责：

| 部分 | 在 Nexogenesis 中的落点 | 建构蕴思的作用 |
|---|---|---|
| Memory | `01-Cards/`、`05-Buffer/`、来源、Episode | 保留知识、材料、历史和可追溯性 |
| Representation | 知识图、论证图、因果图、推理图 | 让“结构问题”可观察、可计算 |
| Operators | GraphOps 与 Harness | 把观察转成安全、可回滚的结构动作 |
| Policy | agenda、选择器、停止条件、思维模式 | 决定现在先做合并、拆分、冲突还是补证据 |
| Workspace | 本轮上下文、候选、假设、未决债务 | 让多轮推理不依赖隐含上下文 |
| Evaluation | 结构指标、证据指标、反事实检查、回归集 | 判断“变好了”还是只是改写了文本 |
| Learning | Episode、策略版本、案例反馈 | 让下一次建构更会选择动作，而不是训练模型权重 |

## 2. 与当前愿景的对齐

  《可演化认知架构愿景与演进路线》给出的北极星是：把知识、认知状态、思考操作、思考策略和经验学习外置为显式、可组合、可评价、可修订、可继承的计算对象，让不同模型都能在这套结构中工作。它明确反对把系统做成单纯的更大知识库，也反对一开始就训练一个不可解释的端到端模型。

  讨论文件夹中的《SPUER知识图谱》进一步指出，知识不能只保存“实体—关系—实体”，还要保留 claim、evidence、mechanism、assumption、context、counterclaim、source。因而建构不是把节点排得更漂亮，而是不断改善知识的可解释性、可推理性和可反驳性。

  《LOOP》暴露了当前最关键的技术缺口：Web 侧语义执行器缺少持续的工具调用—观察—再决策通道。仅把更长的提示词塞给模型，仍然是一次性流水线。自治建构的第一基础设施不是某个图数据库，而是可恢复的工具循环、结构化工作区和安全写入边界。

  因此，本项目的正确顺序是：先让循环真正会看、会问、会换方向；再让它会安全改图；再用案例和指标学习“什么时候做什么”。搜索、贝叶斯和多目标选择应先于强化学习；评估应先于策略优化；图结构与向量检索应互补，而不是互相替代。

## 3. 学科知识地图

### 3.1 知识表示、图谱与本体

  知识表示回答“什么东西可以成为节点、关系、断言和证据”。本项目需要的不是一个一开始就封闭的超级本体，而是一组稳定的小原语：卡片、断言、来源、证据、机制、假设、上下文、反主张、冲突、关系、领域、Episode。

  应掌握的概念包括 RDF/属性图、实体解析、关系类型、类型约束、开放世界与封闭世界假设、本体演化、语义版本、数据血缘和可追溯性。它们直接决定 `rewrite_node`、`add_relation`、`create_conflict`、`extract_entity` 是否能被验证，而不是只依赖模型自觉。

  进入代码的形式应是 `NodeContract`、`RelationContract`、`EvidenceRef`、`Provenance`、`GraphVersion` 和 `ImpactSet`，而不是把所有规则散落在提示词中。

### 3.2 图论与网络科学

  图论是最先要落地的数学。它能把“这个领域太臃肿”“这个节点像枢纽”“这两片知识可能断裂”转成可检验的信号：度数、加权度数、介数、接近中心性、连通分量、k-core、社群、桥边、孤立点、重复边和路径长度。

  图指标不直接决定动作，只负责生成 agenda 候选。例如高介数节点可能是重要枢纽，也可能只是错误地吸收了多个主题；社区边界可能提示拆分，也可能提示跨领域关系。最终判断仍要回到卡片正文、证据和关系语义。

  适合的 GraphOps：`inspect_hub`、`find_orphans`、`detect_bridge`、`compare_neighborhoods`、`propose_split`、`propose_merge`、`find_duplicate_relation`。

### 3.3 论证理论与计算论证

  Toulmin 模型和计算论证把卡片从“陈述集合”提升为“可争辩的主张结构”：claim 由 data/evidence 支撑，经 warrant/mechanism 连接，受到 qualifier、rebuttal 和 counterclaim 限制。它适合处理社科知识中“同一个词下有不同立场”“冲突并不等于错误”的情况。

  建构应区分三种结果：真正的逻辑冲突、上下文不同导致的表面冲突、证据强弱不同导致的未决争议。`create_conflict` 不应把任何语义相似都写成冲突卡；它需要记录冲突两端、冲突类型、适用上下文、证据和待验证问题。

### 3.4 因果推断与结构因果模型

  因果图是把“相关”与“作用机制”分开的工具。核心区别是 `P(Y|X)` 与 `P(Y|do(X))` 不等价；前者是观察到 X 时 Y 的分布，后者是主动干预 X 后 Y 的分布。它适合检查领域卡片是否把相关关系写成因果关系，也适合发现混淆变量、反向因果和缺失机制。

  本项目不要求第一期自动从文本发现完整因果模型，而应先做轻量的因果审查：检测断言中“导致/影响/决定”等因果词；要求变量、方向、时间条件和机制证据；对候选关系标记 `causal_status`；需要时调用 DoWhy、causal-learn 或 pgmpy 做可选验证。

### 3.5 贝叶斯推断、概率图模型与不确定性

  建构面对的不是二值真伪，而是“当前证据下应该相信什么、还缺什么证据”。贝叶斯更新提供最小的可解释形式：

```text
P(H | E) = P(E | H) P(H) / P(E)
```

  实现上可以不把所有卡片变成精确概率，而先保存 `prior`、`evidence_strength`、`confidence`、`calibration_status` 和更新来源。概率图模型则适合表达多个变量的条件依赖，帮助发现“两个冲突其实由第三个上下文变量分开”的情况。

### 3.6 信念修订、真值维护与冲突处理

  AGM belief revision、Truth Maintenance System 和 paraconsistent reasoning 提醒我们：知识库遇到冲突时不应粗暴删除一端，也不应静默覆盖旧知识。正确流程是保留来源，生成冲突或待决对象，计算受影响的下游结论，并允许以后基于新证据修订。

  这与本项目的宪法完全一致：Markdown 是语义事实源；卡片不能删除，只能标记生命周期；任何实质写入必须经过 `write --batch`；冲突应可追溯、可撤回、可重新评估。

### 3.7 认知架构与工作区理论

  ACT-R、SOAR、Global Workspace 等理论提供的是“认知系统怎样分配注意力、保持工作记忆、选择动作”的参照，不是要直接照搬。对 Nexogenesis 最有用的三个抽象是：有限工作区、显式的长期/情景/程序记忆、可观察的认知轨迹。

  建构每轮都应有一个小工作区：当前范围、已观察事实、候选动作、反证、未决问题、预算和停止原因。工作区不是把整本书塞进提示词，而是对当前议程的可重建快照。

### 3.8 规划、搜索与决策过程

  MDP、bandit、HTN、A*、beam search、Monte Carlo Tree Search 共同回答“下一步怎么选”。对当前阶段最实用的是有限预算的启发式搜索和 bandit 式动作选择：先评估每个候选 GraphOp 的预期收益、风险、信息增益和成本，再决定是否执行。

  MDP 的映射是：状态 `S` 为图局部状态与工作区，动作 `A` 为 GraphOp，转移 `P` 为写入后图变化，奖励 `R` 为结构/证据/可操作性改善，策略 `π` 为建构选择器。第一期只需记录这些量，不必马上用 RL 学策略。

### 3.9 信息论、主动学习与实验设计

  熵和信息增益帮助建构决定“下一轮应该读哪张卡、查哪条关系、做哪一个 probe”。典型形式是：

```text
IG(Q) = H(G) - E[H(G | answer(Q))]
```

  如果一个查询能显著减少合并/拆分/冲突判断的不确定性，它就比继续重写一张已经清楚的卡片更值得优先。实验设计和主动学习则用于设计最小验证集：只读一小组节点，也能区分两个候选结构是否真的更好。

### 3.10 多目标优化、进化计算与策略学习

  建构不能只有一个“质量分”。至少应同时关注语义保真、证据覆盖、结构连通、冲突可见性、检索可用性、写入风险、成本和新债务。可将候选动作表示为向量：

```text
score(a) = (evidence, coherence, causal_support, retrieval_gain,
            novelty, reversibility, -risk, -cost, -new_debt)
```

  早期用 Pareto 前沿和人工确认即可；有了稳定案例集后，再用 Bayesian optimization、进化搜索或 DSPy/GEPA 优化选择器和提示程序。没有基准集就做 RL，会把偶然的模型偏好误认为策略进步。

### 3.11 复杂系统、持续学习与元学习

  知识体是一个会改变自身边界的复杂适应系统：领域会分裂、关系会重组、中心节点会迁移、规则会影响未来观察。持续学习和元学习的启发是分开三种时间尺度：本轮 Episode 的局部修订；思维模式的策略经验；跨领域的模式和本体演化。三者不能混成一次运行的隐式记忆。

## 4. 数学工具到 GraphOps 的映射

| 数学/算法工具 | 输入 | 输出 | 适合的 GraphOp | 当前建议 |
|---|---|---|---|---|
| 度数、介数、k-core | 局部图 | 枢纽/桥/边缘信号 | `inspect_hub`、`detect_bridge` | 立即做本地诊断 |
| 社区发现 | 节点与边权 | 候选领域 | `propose_regroup`、`propose_split` | 作为候选，不自动写 |
| 相似度、实体链接 | 卡片标题/正文/实体 | 重复或同实体候选 | `compare_nodes`、`extract_entity` | 先 shadow |
| 贝叶斯更新 | 假设、证据、先验 | 后验与不确定性 | `update_confidence`、`ask_for_evidence` | 先保存可解释字段 |
| 熵/信息增益 | 未决问题、候选查询 | 下一步价值 | `choose_probe`、`prioritize_agenda` | 立即用于排序 |
| DAG/SCM 检查 | 变量、方向、机制 | 因果假设/混淆警告 | `assess_relation`、`find_confounder` | 可选分析适配器 |
| 论证图 | claim/evidence/rebuttal | 支撑、反驳、冲突类型 | `assess_conflict`、`create_conflict` | 立即补充 schema |
| A*/beam/MCTS | 当前状态、动作候选 | 动作序列 | `plan_episode` | 有预算后使用 |
| MDP/bandit | Episode 轨迹 | 动作选择策略 | `select_next_op` | 先记录，不急于 RL |
| Pareto 前沿 | 多维候选评分 | 非支配候选集 | `rank_candidates` | 立即用于多目标选择 |
| 统计检验/校准 | 变更前后样本 | 置信区间/回归 | `evaluate_episode` | 建立 benchmark 后用 |
| 约束求解 | 影响集、关系约束 | 可行写入方案 | `check_plan_feasibility` | 高风险写入前使用 |

### 5.2 有价值但必须等基准集出现

| 项目 | 官方资料 | 适合解决的问题 | 风险与边界 |
|---|---|---|---|
| DSPy / GEPA | [GEPA in depth](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/diving-deeper/gepa-in-depth.md) | 把 GraphOps 选择器、提示程序和评估指标作为可优化程序；GEPA 可根据验证反馈维护候选并搜索 Pareto 前沿 | 没有稳定 benchmark 时会优化噪声；不得替代 Harness |
| Optuna | [GitHub](https://github.com/optuna/optuna) | 搜索预算、阈值、权重和策略超参数 | 优化的是策略参数，不是知识事实；需要可复现 Episode |
| DEAP | [GitHub](https://github.com/DEAP/deap) | 遗传算法、多目标 NSGA-II/III、遗传编程和 checkpoint | 搜索空间容易失控；只在动作 DSL 稳定后使用 |
| Gymnasium / RLlib | [Gymnasium](https://gymnasium.farama.org/)、[RLlib](https://docs.ray.io/en/latest/rllib/) | 将建构选择建模为环境、策略和回报 | 过早 RL 会学习错误奖励；先做 bandit/搜索和离线评估 |
| Neo4j GraphRAG | [Python 文档](https://neo4j.com/docs/neo4j-graphrag-python/current/) | 图构建、图检索和 RAG 生产化 | 适合规模化检索实验；当前不应夺走 Markdown 主权 |

### 5.3 只作方法参考或暂不采用

| 项目/方向 | 原因 |
|---|---|
| Microsoft GraphRAG | 方法论有价值，但官方仓库当前已转为维护模式且索引成本可能很高；借鉴社区摘要、局部图和检索思路，不作为核心依赖。见 [GitHub](https://github.com/microsoft/graphrag)。 |
| Kùzu | 嵌入式属性图的设计有启发，但项目仓库已进入归档/停止维护状态；不作为新的底座。见 [GitHub](https://github.com/kuzudb/kuzu)。 |
| 直接迁移到 Neo4j/向量数据库 | 会把“存储迁移”误当成“认知能力升级”，并削弱 Markdown 唯一事实源与可打包分发能力。 |
| 一开始训练专用模型或多 Agent 社会 | 没有可观察轨迹和评估集时，复杂度只会掩盖建构为什么失败。 |

## 6. 一个完整示例：从臃肿领域到可解释结构

  假设“金融危机”领域有 80 张卡片。中心节点“市场信心”连接 31 张卡，连接了行为、政策、机构、宏观变量四种主题；两张卡分别说“资本管制降低危机传播”和“资本管制加剧流动性冲击”，表面上互相冲突。

### 6.1 观察阶段

```json
{
  "scope": {"domain": "金融危机", "max_nodes": 120},
  "signals": [
    {"kind": "hub", "node_id": "card:market-confidence", "weighted_degree": 31},
    {"kind": "mixed-neighborhood", "clusters": 4},
    {"kind": "possible-conflict", "claims": ["c-102", "c-247"]}
  ],
  "unknowns": [
    "两条资本管制断言是否处在不同时间/制度上下文？",
    "市场信心是机制、结果，还是过于宽泛的中介概念？"
  ]
}
```

  图算法只提出“混合邻域”和“冲突候选”，不直接宣布拆分或合并。论证分析接着读取证据、机制和上下文；因果分析检查两条断言的方向和潜在混淆变量；信息增益排序决定先读取哪两张卡最能减少不确定性。

### 6.2 候选动作阶段

```json
[
  {
    "op": "split_node",
    "target": "card:market-confidence",
    "preconditions": ["4 clusters remain distinct after evidence review"],
    "risk": "high",
    "mode": "shadow"
  },
  {
    "op": "create_conflict",
    "target": ["c-102", "c-247"],
    "reason": "same variable, opposite effect, contexts not yet reconciled",
    "risk": "mid"
  },
  {
    "op": "add_relation",
    "target": ["c-102", "context:capital-mobility"],
    "reason": "missing context candidate",
    "risk": "low"
  }
]
```

  选择器不以“动作数量最多”为目标，而比较一个多目标向量：证据覆盖、结构改善、因果清晰度、检索收益、风险、成本、新债务和可回滚性。若 `split_node` 的证据不足，系统可以先执行低风险的 `add_relation` 或继续 probe，而不是因为流程规定必须拆分就硬写。

### 6.3 验证与结果阶段

  对 `create_conflict`，Harness 检查两端是否是允许的断言/模型/方法类型、关系方向是否符合 ontology、来源是否存在、作用域是否在 Mission 内、是否重复创建同一冲突。对 `split_node`，第一期只生成 shadow proposal 和影响集，不自动提交高风险结构变更。

  写入后重新计算：中心节点度数是否下降但语义路径是否仍可达；冲突是否新增了明确上下文；检索同一主题是否更容易找到相反证据；是否出现孤儿节点或幽灵链接。若任一指标恶化，就把 Episode 标记为“可回滚/需要复查”，而不是宣称建构成功。

## 7. 建议的代码结构

  当前 `nexogenesis/application/workflows/construct.py` 已具备议程种子、观察、候选拒绝回流、局部写后复核与 Workspace 持久化，但仍由工作流内部的单 action 循环驱动；`nexogenesis/construct/v1.py` 负责动作编译和风险限制，`construct_service.py` 负责诊断和局部上下文。它不是已完成的自主建构 Agent。实施结构已收束为“共享 Agent Tool Loop + construct 模式 + Mutation Gate”，当前实现进度、接口与后续顺序以 [架构真图与后续路径](架构真图与后续路径.md) 为准；本节只保留能力分层，不是独立实施规格。

### 7.1 核心状态对象示例

```python
@dataclass
class ConstructState:
    mission_id: str
    scope: Scope
    read_revisions: dict[str, str]
    agenda: list[AgendaItem]
    observations: list[Observation]
    hypotheses: list[Hypothesis]
    proposals: list[OperationProposal]
    committed: list[TransactionRef]
    rejected: list[Rejection]
    unresolved: list[Question]
    budget: Budget
    stop_reason: str | None = None

    def snapshot(self) -> dict[str, object]:
        """只保存可重建的状态，不保存不可审计的隐式模型记忆。"""
        return asdict(self)
```

### 7.2 自治循环接口示例

```python
class SharedAgentLoop:
    async def next(self, workspace, tools):
        decision = await self.model.decide(workspace, tools.schemas())
        if decision.kind == "tool_calls":
            return await tools.execute_read_only_batch(decision.calls)
        if decision.kind == "mutation_proposal":
            return await self.mutation_gate.evaluate_and_apply(decision.proposal)
        return decision
```

  这个接口的关键是模型可以自由选择观察、更新议程、提出改变、请求用户或停止，而不是每轮被迫走完一组预定阶段。状态在安全边界保存；模型只能通过注册工具获得事实；写入只能经过 Mutation Gate/Harness；拒绝作为下一轮 observation 返回。

## 8. 分阶段实施路径

  本节表达长期能力依赖，实际开发顺序以 [架构真图与后续路径](架构真图与后续路径.md) 的 P0—P2 为准。尤其不要先把全部 Observation、Hypothesis、Proposal 等对象固化成庞大 schema，也不要在共享 Agent Tool Loop 之前开发独立 Observer/Analyzer 管线。

### B0：把当前一次性建构变成可重建的自治骨架

- 只固化 Workspace、AgendaItem、ToolObservation、AgentDecision、MutationProposal、HarnessResult 和 EpisodeEvent 这组 R1 最小对象。
- 给安全边界生成 `episode_id`、checkpoint、受影响对象 revision 和 `idempotency_key`；不用一个全库版本阻塞非重叠任务。
- 把 `success_criteria` 与 `stop_criteria` 从 Mission 字段变成真正可执行的评估器。
- 保留当前 `write --batch` 唯一写入入口；不引入图数据库。

### B1：只读自治 loop

- 实现图诊断、成员读取、关系遍历、证据缺口和冲突候选等 observation Ops。
- 建立 agenda：高介数节点、孤儿、重复关系、冲突候选、领域边界、低置信断言都可以进入候选。
- 每轮允许“继续观察”作为合法决策，允许转向不同子问题，不要求动作必须产生写入。

### B2：低/中风险 GraphOps 与 shadow

- 低风险优先：补上下文关系、补来源、记录冲突、记录结构债务、改写不改变语义的字段。
- 高风险合并、拆分、提取实体、提升枢纽先生成影响集和 shadow 结果。
- 验证“写入后再观察”而不是只验证 JSON 格式。

### B3：结构验证与可解释决策

- 引入 NetworkX 本地诊断；必要时以 RDFLib/pySHACL/LinkML 的 shape 思想补充自有契约。
- 增加论证和因果字段，允许 DoWhy/causal-learn/pgmpy 只读分析。
- UI 展示当前范围、读过的证据、候选动作、拒绝原因、影响卡片、停止原因和回滚入口。

### B4：Episode 评估与策略学习

- 建立 50–100 个可重复案例：臃肿领域、重复节点、上下文冲突、枢纽误聚、缺失实体、错误关系。
- 评估语义保真、证据覆盖、结构连通、冲突可见性、检索收益、用户复核成本和新债务。
- 先用规则/beam/bandit/Pareto 选择器；再试 DSPy/GEPA、Optuna 或 DEAP。

### B5：规模化和长时运行

- 只有当本地 Episode/checkpoint 不足以支撑并发和多年运行时，才评估 Temporal。
- 只有当 Markdown + 本地索引无法支撑检索规模时，才评估 Neo4j GraphRAG 或其他外部图存储；外部索引必须可删除、可重建，不能成为语义事实源。

## 9. 验收标准：怎样证明建构真的“蕴思”了

  不能用“模型输出更长”或“执行了更多轮”作为主要指标。至少要观察以下结果：

| 维度 | 可检验问题 |
|---|---|
| 自主性 | 没有用户逐轮指挥时，是否能提出并执行下一项合理观察/动作？ |
| 方向切换 | 发现证据不足或风险过高时，是否会 probe、换子图或停止，而不是硬写？ |
| 语义保真 | 改写/合并/拆分后，原始主张、来源和适用条件是否可追溯？ |
| 结构改善 | 枢纽、孤儿、重复关系、领域边界和可达性是否改善？ |
| 冲突能力 | 是否区分真实冲突、上下文冲突和证据不足，并保留两端来源？ |
| 因果纪律 | 是否减少把相关写成因果的关系，并暴露机制和混淆变量缺口？ |
| 可恢复性 | 中途暂停、失败或重启后，是否能从最后一个一致状态继续？ |
| 可解释性 | 每次动作能否回答“基于什么观察、为何选它、影响什么、为何通过/拒绝”？ |
| 策略进化 | 同类案例重复运行时，动作选择和失败率是否有可测改善？ |

## 10. 明确不做的事

  不把建构重新包装成固定的 `for round in range(...)` 管线；轮数只是预算，不是思维顺序。 不把“LLM 可以自由发挥”当作自治；没有工具、状态、反馈和检查点的自由发挥仍然是一轮提示词调用。 不让外部项目绕过 Harness 写 Markdown。 不在没有 benchmark 的情况下引入 RL、遗传优化或多 Agent。 不把图数据库、向量数据库或 GraphRAG 的索引当成知识事实源。 不因一次冲突就删除旧卡片，不因一次相似度就合并节点。

  最终要实现的不是“一个更复杂的工作流”，而是一个受约束但可探索的建构认知系统：模型负责提出意义和假设，图算法负责发现结构信号，数学工具负责量化不确定性与选择代价，Harness 负责边界和可逆性，Episode 负责把过程变成未来可学习的经验。

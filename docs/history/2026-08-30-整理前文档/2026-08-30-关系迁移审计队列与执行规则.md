## 二、为什么不能机械补齐

  “给 975 条旧边批量生成一句说明”会制造新的伪证据。关系 `note` 不是装饰字段，而是 Thinking Model 判断方向、机制、条件和可否继续扩展的依据。缺少正文证据时，正确动作可能是补说明、改关系类型、迁移到另一张立场卡，或者删除旧边；这些选择不能由字符串模板决定。

  同样，324 张没有 ready 关系的卡并不等于 324 个缺陷。有些卡确实是孤立证据，有些只需要领域归属，有些需要等待新的材料，只有一部分应该建立论证或情境联系。

## 三、执行优先级

### P0：维持结构安全线

- 每次运行 `inspect_structure_issues(kinds=["duplicate_id", "sample_card"])`，优先清除检索身份歧义。
- 新增或修改关系必须通过 Harness 的签名、目标与 note 校验。
- 幽灵目标、关系指向 domain、非法签名必须维持为零。

### P1：修复会直接影响推理的核心边

- 从高连接 `model`、核心 `claim` 和报告常用结论开始。
- 对目标卡使用 `inspect_argument`，检查支持、依据、冲突、边界与来源。
- 若要验证两点已有链路，使用 `graph_path`；不得用关键词相似代替关系证据。
- 每次最多修复三条紧密相关关系，写后重复相同观察。

### P2：整理 conflict 结构

- 对 100 条 conflict 非 `involves` 出边逐簇检查。
- conflict 卡只保留争议档案职责；直接支持、依据、影响或扩展关系迁回具体立场卡。
- 若现有两造不能对应正文中的真实分歧，不机械迁移，先补齐或重构参与方。

### P3：解释旧关系

- 缺 note 但关系方向与正文一致：用 `propose_relation_patch(action="upsert")` 补充具体说明。
- 类型与实际语义不符：同一局部任务先移除旧边，再新增正确类型；两步都经过 Harness。
- 证据不足：保留为待核验或移除，不生成泛化说明。

### P4：接入孤立对象

- 使用 `inspect_unconnected_cards(scope="without_ready_relations")` 取得有限候选。
- 精读卡片后先判断它需要领域归属、论证关系、情境关系，还是保持独立。
- 新联系必须能说明两个端点、方向、机制与边界；只共享关键词或领域不构成连边依据。

## 四、标准局部修复循环

```text
选择一种问题
→ 取得不超过 12 个候选
→ 精读 1–2 张端点卡
→ inspect_argument / compare_cards / graph_path 验证
→ 在 Workspace 写明局部假设与候选动作
→ propose_relation_patch 提交一条关系变化
→ 重复原 Observation 做写后复核
→ 继续下一个局部簇或在轮次上限处结束
```

  完全信任模式可以自动提交已经通过上述证据链与 Harness 的关系补丁；手动确认模式仍展示确认卡。两种模式使用同一套关系语义与校验，不再各自维护一套逻辑。

## 五、第一批建议批次

1. 先处理重复 id 与样例隔离，消除对象身份歧义。
2. 选择 5–10 张报告输出中最常被引用的核心模型或主张，修复其直接论证边。
3. 选择一个 conflict 密集的小领域，验证“争议档案只用 involves”的迁移方式。
4. 选择一组历史事件卡，验证 context 平面的 `influences` / `precedes` 及时间锚点。
5. 再扩大到没有 ready 关系的卡，避免在契约尚未验证时全库铺开。

## 六、批次验收

- 修复后的关系均有具体 `note`，并达到 `argument_ready` 或 `context_ready`。
- 二跳、三跳路径不经过待核验旧边。
- 关系写入不改变正文、来源、领域和生命周期。
- 写后图谱观察能够显示准确端点、方向、关系原色和跳数。
- 每批都记录保留、修改、移除和延后原因，不能只报告关系数量变化。

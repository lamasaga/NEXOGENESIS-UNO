## 0. 本文的职责与阅读纪律

  本文合并并取代本轮的《强力建构蕴思 PRD》《强力建构蕴思 SPEC》《编译与消化智能化实施指南》与《编译与消化认知工作流设计》。它同时回答四件事：系统当前真实能做什么；三项工作流最终要成为什么；哪些接口已经实现或仅被预留；下一步应按什么顺序补齐。

  本文不是宪法，也不替代卡片、写入、摄入和检索契约。发生冲突时，`AGENTS.md` 与 `.agent/reference/` 优先；本文只负责把它们落实到 Web 运行时、工作流和开发路径。任何实现状态都必须以代码和测试为准，不能把目标接口写成既有能力。

  本轮被吸收的设计稿已从工作目录移除，以避免并行规格继续漂移；需要追溯讨论和措辞时使用 Git 历史。长期愿景与工具地图继续保留，因为它们是研究输入，不是当前实现承诺。

### 0.1 双版本与三仓关系

  Nexogenesis 当前存在两条彼此关联、但运行时并不相同的实现路线。**ORG 版本**是项目原生开发形成的 Python + Web 实现，本仓是 ORG 的纯开发仓；它另有一个与之单向联动的领域实践仓，用于承载真实知识体与日常使用。**DSH 版本**位于 `D:/UESR/Desktop/NEXOGENESIS-DSH/`，是发现 ORG 缺少真正接管运行的 Agent Loop、编译/消化/建构等功能过度管线化之后，基于 DeepSeek Harness 进行迁移和重新实现的独立版本。

| 对象 | 真实角色 | 不应误解为 |
|---|---|---|
| ORG 开发仓 | 原生 Nexogenesis 的代码、契约与 Web 运行时开发仓 | DSH 的上游运行内核 |
| ORG 实践仓 | 从 ORG 单向拉取代码、承载领域知识和真实任务 | DSH 版本 |
| NEXOGENESIS-DSH | 基于 DeepSeek Harness 的另一套实现路线，用 Agent 工具循环改造过度管线化问题 | ORG 的策略包、领域配置层或普通部署仓 |

  两个版本共享 Nexogenesis 的产品目标、Markdown 语义主权、卡片本体和一部分历史契约，但拥有不同的运行栈、写入权威与实现状态。讨论和实施时必须明确标注结论针对 **ORG、ORG 实践仓、DSH，还是需要双端对照**；未经核对，不得假定一端的代码、修复或能力已经被另一端继承。

  DSH 是否最终替代 ORG 的运行时、两者是否合并，以及 Agent Loop 的最终代码主权，仍属于待比较验证的架构决策。作出该决策前，应以相同真实任务对比两端的自主循环质量、确定性写入安全、可恢复性、可观测性和维护成本，而不能仅按目录名称或现有模块骨架判断。

## 1. 系统现在真正是什么

  Nexogenesis 是一个以 Markdown 为唯一语义事实源的知识操作系统。`01-Cards/` 和 `05-Buffer/` 是知识体；Web 思维体通过对话、编译、消化和建构操作该知识体。模型负责语义判断，Harness 负责权限、事务、恢复、索引、校验和审计。

```text
材料 ── Compile ──> Buffer ── Digest ──> Card ── Construct ──> 更可用的知识结构
                         │                      │
                         └─────────────── talk / assess / emerge / refine / report

确定性底座：Markdown · fingerprint · ledger · revision · write --batch
运行记录：.nexogenesis/ 下的 Run · Checkpoint · Episode · Job · 审计轨迹
```

### 1.1 不可退让的底座

- Markdown 是唯一语义事实源；索引、图、向量和运行缓存都必须可删除重建。
- 所有实质知识写入都经过 `python -m nexogenesis write --batch`；不得从工作流直接改卡片。
- Harness 不判断观点、概念或冲突是否有意义；它只约束范围、证据、关系、本体、revision、幂等和原子提交。
- LLM 不直接获得任意文件写权限；它只能在当前模式的工具白名单和授权边界内提出决定。
- 编译、消化、建构不是同一个万能 Agent；它们只共享运行协议，不共享权限、任务目标或写入边界。

### 1.2 双执行平面

| 平面 | 主职 | 边界 |
|---|---|---|
| Code Agent | CLI 的 compile / digest 编排与开发辅助 | 不代替 Web 建构或思维体策略 |
| Web 思维体 | talk 与固定工作流，后续扩展 assess / emerge / refine / report | 通过 Harness 读取和写入知识体 |
| Harness | 事务、验证、账本、恢复、归档、索引 | 不替模型决定认知方向 |

## 3. 目标真图：共享协议，不是万能流程

  三项工作流最终共享“模型决定 → 工具观察 → 工作空间更新 → 安全边界”的运行协议，但每种模式有自己的 Workspace、工具白名单、账本、完成条件和写权限。

```text
项目级协调器
  ├─ 任务队列、预算、取消、暂停、恢复、并发与状态聚合
  └─ Shared Agent Tool Loop
       ├─ CompileSession：理解来源并形成 Buffer
       ├─ DigestSession：识别贡献并同化到 Card
       └─ ConstructSession：审视结构并提出/提交图谱改变

每个 Session
  Workspace → AgentDecision → ToolObservation → Workspace
                                      │
                                      └─ MutationProposal → Mutation Gate → write --batch
                                                                    │
                                                                    └─ 写后观察 → Workspace

旁路：Episode · Checkpoint · SteeringInbox · DecisionRequest · StatusProjector
```

  共享 Loop 不规定“先观察、再分析、再写入”的阶段顺序。Agent 可以连续读取、比较、更新议程、形成候选、记录债务、申请用户决定或结束当前焦点。Harness 只在提交、授权、预算、并发与可恢复性上拥有最终权威。

### 3.1 共享稳定接口（未来实现必须复用）

```python
@dataclass
class AgentDecision:
    kind: Literal[
        "tool_calls", "update_workspace", "propose_change",
        "request_user", "finish_focus", "finish_run",
    ]
    summary: str
    payload: dict

@dataclass
class ToolObservation:
    tool_name: str
    ok: bool
    summary: str
    evidence_refs: list[str]
    payload_ref: str | None
    error_kind: str | None
    retryable: bool
    workspace_revision: int

@dataclass
class WorkspaceCheckpoint:
    mode: Literal["compile", "digest", "construct"]
    workspace_revision: int
    episode_id: str
    read_set: dict[str, str]
    pending_work: list[str]
    committed_transaction_ids: list[str]

@dataclass
class DecisionRequest:
    reason: Literal["high_risk", "value_judgment", "goal_drift", "authorization"]
    summary: str
    impact_summary: str
    evidence_refs: list[str]
    choices: list[dict[str, str]]
    allow_free_text: bool = True
    allow_defer: bool = True
```

  这些是运行对象，不是知识事实，不写入 Card。它们必须可序列化、可版本化、可由 `.nexogenesis/` 删除后重建知识索引，并以 Episode 保留审计依据。

### 3.2 驱动器端口

```python
class AgentLoopDriver(Protocol):
    async def run(self, *, session: AgentSession, budget: LoopBudget) -> WorkspaceCheckpoint: ...

class AgentSession(Protocol):
    mode: str
    workspace: dict
    tool_registry: ToolRegistry

    async def decide(self) -> AgentDecision: ...
    async def reduce(self, decision: AgentDecision) -> tuple[ToolObservation, bool]: ...
    async def absorb_steering(self) -> None: ...
    async def checkpoint(self) -> WorkspaceCheckpoint: ...
```

  当前 `nexogenesis/runtime/agent_loop.py` 仅提供轻量函数和 `LoopBudget`。后续必须让 Construct 先迁入该端口，再让 Compile 与 Digest 以不同 Session 接入；禁止各工作流再复制一份模型循环。

## 4. 三种模式的职责、现状与未来接口

### 4.1 Compile：自适应阅读与质料形成

  Compile 的边界是读懂一份来源，形成可独立使用、带稳定来源锚点的 Buffer。它不决定 Card 归属、不创建知识关系、不重组图谱。来源完成由 coverage ledger 证明，而不是由模型说“读完了”证明。

| 当前实现 | 后续接口 |
|---|---|
| 来源/阅读窗遍历、用户选材、断点恢复、逐窗原子提交 | `CompileSession` 与 `ReadingWorkspace` |
| Semantic Inventory、提炼、忠实度复核、定向返修、Coverage 检查 | `inspect_source_map`、`read_focus`、`read_previous_context`、`read_next_context`、`expand_context`、`inspect_artifact` |
| 图表独立处理、重复图表复用、deferred 后继续正文 | `update_semantic_inventory`、`draft_buffer_candidates`、`review_fidelity`、`audit_coverage`、`defer_for_review` |
| 当前仍是固定语义流水线 | `preflight_buffers`、`commit_buffers`、`settle_source` 经 Buffer Gateway 提交 |

  ReadingWorkspace 必须至少含 `structural_map`、`source_agenda`、`semantic_inventory`、`coverage_ledger`、`buffer_candidates`、`unknowns`、`artifact_refs` 与 `deferred_items`。Agent 可以因证据不足回读或前瞻；Harness 必须保证 SourceAgenda 不会遗忘正文主线。

### 4.2 Digest：知识同化与语义补丁

  Digest 的边界是判断 Buffer 对现有知识体的贡献，并以 enrich、必要的新建、skip 或 deferred 结算它。它可以建立来源直接支持的局部关系，但不承担跨领域重组、冲突消解、枢纽拆分或高阶概念涌现；这些属于 Construct。

| 当前实现 | 后续接口 |
|---|---|
| 两阶段路由、SemanticPatch 编译、事务写入、暂停恢复 | `DigestSession` 与 `AssimilationWorkspace` |
| 单批失败后待复核、排除当前材料并改选其他 Buffer | `inventory_contributions`、`retrieve_candidate_cards`、`read_candidate_card`、`compare_candidate_cards`、`search_alternative_cards` |
| 关系 disposition、write gate、无限 Web 波次 | `update_assimilation_hypothesis`、`draft_semantic_patch`、`review_patch_fidelity`、`split_commit_groups` |
| 当前原子单位仍是波次，不是贡献级自由循环 | `preflight_semantic_patch`、`compile_transactions`、`commit_group`、`settle_buffers` |

  AssimilationWorkspace 必须至少含 `buffer_scope`、`contribution_ledger`、`candidate_cards`、`observed_cards`、`assimilation_hypotheses`、`semantic_patches`、`relation_intents`、`commit_groups` 与 `deferred_items`。`SemanticPatch` 是模型唯一的写入中间层；模型不得重新承担完整 write batch 编码。

### 4.3 Construct：主动审视、结构改善与蕴思入口

  Construct 是知识图谱搭建的最后一环，也是思维体主动使用知识结构的开端。点击后它应自主选择有理由的局部，观察、比较、形成问题、提出安全改变、写后回看，并使知识体更适合后续推理。

| 当前实现 | 后续接口 |
|---|---|
| 自动 Mission、Episode、checkpoint、Workspace、Agenda seed | `ConstructSession` 与共享 `AgentLoopDriver` |
| `read_node`、`walk_relations`、`compare_nodes`、`inspect_conflicts` | `AgentDecision.tool_calls` 支持一次多项只读调用 |
| `rewrite_node`、`add_relation`、`remove_relation`、`create_conflict`、`record_debt` | `MutationProposal → ImpactSet → RiskAssessment → HarnessResult` |
| Harness 拒绝回流、局部 revision、写后确定性复核 | `ReadScope`、`WriteScope`、`AuthorizationGrant` 与 `intent_revision` 贯通 |
| 当前仍是工作流内部“单 JSON action、多轮循环” | Steering、决策、恢复与同一 Episode 的用户共驾 |

  R1 可自动提交低中风险局部改善；merge、split、实体提取、领域重组与枢纽调整只形成 shadow 候选。新概念、模型、方法、领域与研究问题在 R1 只保留带证据的候选，不自动写空心卡。

```python
@dataclass
class ImpactSet:
    card_ids: list[str]
    domain_ids: list[str]
    relation_count: int
    creates_new_type: bool
    affected_hubs: list[str]

def assess_risk(proposal: MutationProposal, impact: ImpactSet, store: Store) -> RiskAssessment:
    """综合操作类型、影响范围、成熟度、中心性、可逆性与长期承诺。
    返回可解释的 low / medium / high；不使用未经校准的质量分。
    """
```

## 5. 人机协作、状态与并发

  默认入口是“开始编译 / 开始消化 / 开始建构”，而不是先要求用户理解窗口、波次、Mission 或 GraphOp。建构默认自动侦察；高级设置可选择范围、排除项、预算和只读/shadow/安全写入，但不是启动前置表单。

  运行主界面只回答四个问题：现在关注哪里、发现了什么、准备做什么、是否需要用户决定。波次、窗号、任务 id、长路径、JSON、模型返回量和 Harness 原始错误只进入折叠的技术证据层。

```text
当前关注：正在比较这组材料中“流动性不足”和“资不抵债”的边界。
发现：两者共享一段机制，但适用条件不同。
准备：回读上一节定义并核对资产负债表示例。
需要你决定：否。
```

### 5.1 Steering 与决策恢复

```text
普通对话 / 固定线程输入
  → SteeringInbox.append(run_id, episode_id, text)
  → 下一个安全边界 absorb_steering()
  → Workspace.intent_revision += 1
  → 若改变写入范围、执行模式或目标：旧 AuthorizationGrant 失效
  → 同一 Episode 继续，不回滚已提交原子事务
```

  当前后端已有 Construct steering 文件和决策 API，但 Web 固定线程输入被锁定，且高风险暂停后的决策展示/恢复链不完整。此处是 P0 接口，不能以“重新启动一次建构”替代。

### 5.2 并发与 revision

| 情形 | 目标处理 |
|---|---|
| Compile 新增 Buffer | Digest 冻结本轮 `buffer_scope`；新 Buffer 留给后续焦点 |
| Digest / Construct 同时读同一 Card | 提交前比较 read-set revision；重叠对象重新观察 |
| 两个任务写不相交对象 | 不相互阻塞 |
| 两个任务写相交对象 | 后到提案转为 conflict Observation，不覆盖先到结果 |
| 用户暂停 | 在 Observation、Workspace 更新、候选形成、原子写入、写后复核等安全边界生效 |

  当前 Web 只有一个 `pipelineBusy`，仍禁止多任务同时启动；普通对话可在另一个非固定线程继续，但不能向正在运行的 Construct 注入 Steering。这是当前能力，不得误写为并发已完成。

## 6. 后续实施路径与交付物

### P0-A：让共享 Loop 成为真实运行主体

- Construct 迁入 `AgentLoopDriver`，不再自行实现 action while-loop。
- 实现模式工具注册表、统一 `AgentDecision` 解析和 `ToolObservation` 归约。
- 一次 Decision 可包含多个只读工具调用；Mutation Gate 每次只接收一个明确 `MutationProposal`。
- 把 Harness 拒绝、revision 冲突、工具失败和无新信息统一回传为 Observation。

**验收：** 脚本 Agent 能连续 read → compare → observe failure → alternate read → propose；ConstructWorkflow 不再直接管理模型循环。

### P0-B：贯通 Steering、决策与恢复

- 固定线程 Composer 改为“普通聊天禁写、Steering 可发送”的双通道输入。
- 前端接入 `steerConstructRun`、`decideConstructRun`、`resumeConstructRun`；决策卡在 `running` 与 `paused` 都持续读取状态。
- DecisionRequest 支持自由输入、暂缓、停止和“继续观察”，回复进入同一 Episode。

**验收：** 运行中输入“只看两个模型差异，不要写入”，下一个安全边界生效；高风险候选暂停后仍可做决定并从同一 checkpoint 恢复。

### P0-C：项目级多任务协调

```python
class RunCoordinator(Protocol):

    async def pause(self, run_id: str, *, after_boundary: bool) -> None: ...
    async def cancel(self, run_id: str) -> None: ...
    async def status(self) -> list[RunStatusView]: ...
```

- 任务按 `run_id` 独立显示、取消、暂停和恢复。
- 写网关只在短事务临界区串行；读取、模型调用和普通对话不应被全局阻塞。
- 为同源 Compile、同 Buffer Digest、同 Card Construct 加入明确冲突策略。

**验收：** Compile、Digest、Construct 三任务可并存；普通对话可继续；只有重叠写入发生局部重读或冲突。

### P1-A：CompileSession 自适应阅读

- 以 shadow 模式接入 ReadingWorkspace 与 SourceAgenda；旧稳定路径继续负责实际 Buffer 写入。
- 验证 Agent 能因证据不足主动前瞻/回读，又不会遗忘正文主线。
- 达标后开放 `draft_buffer_candidates → preflight_buffers → commit_buffers`。

### P1-B：DigestSession 同化与 CommitGroup

- 以 shadow 模式形成 ContributionAgenda、候选比较和替代搜索轨迹。
- 维持 SemanticPatch 为唯一语义中间层；引入 CommitGroup，使失败关系或陈旧目标不拖垮无关 enrich。
- 用贡献去向、重复新建率、陈旧覆盖率和人工复核时间评估，不使用单一“智能分”。

### P2：基于证据开放更高阶蕴思

  只有 R1 在真实案例中稳定带来净收益后，才考虑高风险结构模拟、概念/模型/方法候选、论证图、因果审查、策略比较或外部数学工具。不得为了“像 Agent”先接强化学习、多 Agent、图数据库或未经验证的自动本体演化。

## 7. 验收与评价

### 7.1 全模式不变量

- 零绕过 `write --batch` 的实质知识写入。
- 零幽灵链接、零范围外写入、零重复提交。
- 暂停、重试、恢复不重复已提交事务。
- 失败必须留下可行动的 Observation、deferred 或停止理由；不得静默吞掉材料或贡献。
- 用户界面不把模型内部推理当作事实或进度。

### 7.2 R1 行为案例

| 案例 | 必须观察到的行为 |
|---|---|
| 非法关系端点 | Harness 返回原因；Agent 改选、继续观察或记录债务，不立即结束 Mission |
| 信息不足 | Agent 回读、比较、defer 或形成待验证问题，不硬写结果 |
| 成熟卡高风险改变 | 只保留 shadow 候选并请求用户确认 |
| 用户运行中改目标 | 下一个安全边界吸收 Steering；旧授权不越过新意图 |
| 并发重叠修改 | 仅受影响对象重读；无关任务继续 |
| 无写入运行 | 至少留下新观察、候选、债务或有解释力的停止理由 |

### 7.3 上线门槛

- 协议测试：driver、schema、checkpoint、Episode 与版本迁移。
- 事务测试：范围、关系、本体、revision、幂等、断点恢复。
- 行为测试：改选、无进展、Steering、决策恢复、并发重叠。
- 真实材料回归：一本长书、一份报告、一篇含表图论文，以及人工标注的结构案例。
- 体验测试：用户无需阅读技术轨迹即可说出当前关注、发现、下一步和是否需要决定。

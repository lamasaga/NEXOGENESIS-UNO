# 面向 OPS 的知识图谱关系设计

> 状态：设计基线，尚未批量改写任何 Card。
>
> 目标：让 Thinking Model 能够用卡片关系完成可解释的检索、论证、反证、适用性核验与结构建构；不把视觉上连得很多误当成可推理。
>
> 依据：本设计参考《知识卡片标注与统一推理 OPS 清单》，并以 2026-08-29 对现有知识库的实际审计为起点。

## 1. 结论

  当前图谱的引用完整性已经达到可用水平：正式检索图没有幽灵关系目标，也不再把领域成员关系伪装成论证边。真正阻碍 OPS 推理的不是关系类型不够，而是大量边没有说明其成立理由，且历史上被广泛使用的 `influences` 同时承担了因果、理论关联、应用与“看起来相关”四种含义。

  因此本次不新增一批近义关系，也不把所有共现都连成边。图谱应改为四个明确的平面：**领域归属、论证、情境因果、来源追溯**。Thinking Model 只把通过关系就绪检查的论证边当作回答依据；情境边服务于历史与情景分析；未说明的旧边只能作为待核验线索，不能在多跳推理中充当证据。

## 2. 现有图谱的实际起点

| 审计项 | 当前值 | 对 OPS 的含义 |
|---|---:|---|
| 正式 Card | 986 | 体量已经需要受控检索，不能整体塞入上下文 |
| 关系 | 2,028 | 图谱不是空的，但不能只以边数评价质量 |
| 有出边的 Card | 723 | 相当一部分卡仍未进入论证网络 |
| 完全无关系的非领域 Card | 186 | 应逐簇判断：补真实边、保留为独立证据，或归档，而非统一补边 |
| 无 `note` 的关系 | 975（48.1%） | 无法向模型或用户解释“为什么能走这条边” |
| `influences` | 506（25.0%） | 当前占比最高，却默认不进入论证检索 |
| `part-of` | 2 | 机制的组成与阶段结构几乎无法被路径检索 |
| `precedes` | 0 | 历史时序没有被正式编码 |
| 非 `involves` 的 conflict 出边 | 100 条，分布在 43 张 conflict 卡 | conflict 容器与双方立场、证据层混在一起 |
| 缺失 Buffer 来源引用 | 298 条引用，影响 109 张 Card | `trace_source` 无法稳定核验一部分关键判断 |

  现有默认论证图不走 `influences` 与 `precedes`。它包含 956 个非领域节点、1,522 条可走边，但仍有 197 个单点连通分量；如果把 `influences` 全部打开，最大的连通块只从 637 增至 644 个节点。可见问题不是“少一条万能连接”，而是存量边的语义过宽、边注和来源不足。

## 3. 图谱应有的四个平面

```text
Card
 ├─ domains[] ───────────────→ 领域归属平面
 │                              仅用于筛选、成员列表与覆盖审计
 ├─ relations[] ─────────────→ 论证平面
 │                              用于解释、反证、机制路径与建构
 ├─ influences / precedes ───→ 情境因果平面
 │                              用于历史链、情景推演；默认不作论据跳转
 └─ sources[] ───────────────→ 来源追溯平面
                                用于回到 Buffer、原文、页码、表格或图像
```

  `domains` 只回答“这张卡属于哪个知识簇”，不表示因果、证据或理论基础。领域成员要通过 `graph_members` 查询；任何 Card 到 domain 的 `relations[]` 都视为错误用法。

  Workspace 中的假设、证据矩阵、尚未解决的问题和本轮路径则是第五类临时运行状态。它们可以引用 Card 和来源，但不是 Card 关系，更不能在任务结束后悄悄沉淀为图谱事实。

## 4. 正式关系的目标语义

  下表中的方向统一写作“源卡 → 目标卡”。“典型对象”是优先组合，不是把正常的跨类型推理一律判错；但偏离典型组合时必须在 `note` 中说清角色，供 Harness 标记复核。

| 关系 | 源卡 → 目标卡的含义 | 典型对象 | OPS 中的用途 | `note` 至少说明 |
|---|---|---|---|---|
| `supports` | 源卡提供能够支持目标判断的观察、证据或机制 | phenomenon / claim / model → claim / model / method | 组成证据链；可作 1～2 跳论证 | 支持哪一项命题、靠什么机制或证据、在哪些条件下成立 |
| `based-on` | 源卡的判断或模型建立在目标卡所述的前提、机制或事实基础上 | claim / model / method → model / claim / phenomenon / method | 追问“这个结论凭什么成立” | 源卡具体采用了目标卡的哪项基础，而不是“主题相近” |
| `extends` | 源卡在范围、条件、机制或结论上扩展、限定或修正目标卡 | claim / model / method → claim / model / method | 比较理论演进与适用边界 | 新增或改变的维度，以及没有推翻的部分 |
| `example-of` | 源卡是目标卡所描述模式的可核验实例 | phenomenon / entity / claim → model / claim / method | 从一般模型落到案例；不能反向把单例当普遍证明 | 实例对应目标卡的哪个模式，并写明时间、对象或条件 |
| `part-of` | 源卡是目标卡中必要的阶段、组件或子机制 | phenomenon / model / method / entity → model / phenomenon / method | 追踪机制链；可作为 1～3 跳的桥接边 | 它在整体中承担的环节及前后接口 |
| `applies-to` | 源卡的分析框架适用于目标卡所述的具体情境 | model / method / claim → phenomenon / entity / 情境型 claim | 适用性核验；默认只在问题确实涉及该情境时走 | 适用条件、迁移限制与尚未验证的条件 |
| `conflicts-with` | 两张论证对象对同一问题给出不能同时成立的核心判断 | claim / model / method ↔ claim / model / method | 反证搜索与争议研判 | 分歧的问题、双方各自坚持什么；按单向存储、双向读取 |
| `involves` | conflict 卡记录的争议明确涉及目标立场、模型、方法或实体 | conflict → claim / model / method / entity | 打开争议两造；不是普通“相关” | 目标在争议中的角色，例如一方立场、机制桥或关键对象 |
| `influences` | 源卡所述的现实过程、制度安排或行为变化对目标所述对象产生影响 | phenomenon / entity / 机制型 claim/model → phenomenon / entity / claim | 历史和情景链；必须显式请求才可走 | 影响方向、传导机制、时间或制度条件；不能只写“相关” |
| `precedes` | 源卡所述事件或阶段在时间上先于目标 | 有明确时间锚点的 phenomenon / entity → 同类对象 | 历史序列与阶段定位；不自动当作因果 | 时间范围、排序依据，以及“先后不等于因果”的边界 |

  `conflict` 是“争议档案”，不是第三种立场。它应保留 `involves` 指向双方及必要的桥接对象；原来从 conflict 发出的 `supports`、`based-on`、`extends`、`influences` 和 `example-of`，应逐条迁回到对应的立场 Card，或改成 Card 之间的关系。这样 `inspect_conflicts` 才能区分“谁主张什么”与“哪些材料支持谁”。

  `influences` 不是“关联边”的收纳箱。现有 506 条中应按下面的规则逐簇改选：确有可追溯的现实传导则保留为 `influences`；若表达的是理论基础改为 `based-on`；若表达证据改为 `supports`；若表达机制组成改为 `part-of`；若表达框架落地改为 `applies-to`；仅为主题相近则删除关系、保留共同领域或记录为建构观察。

## 5. 关系就绪等级：决定 OPS 能否使用

  不再让“关系存在”与“关系可推理”是同一件事。Harness 与 GraphOps 应按以下状态处理边；这是一项运行判断，不要求马上给现有 Markdown 增加新的前置字段。

| 等级 | 条件 | 可被 OPS 如何使用 |
|---|---|---|
| `argument_ready` | 目标存在、非领域；关系签名有效；`note` 说明机制或证据；源卡有可追溯来源或明确标为用户判断 | 可以进入默认 1～2 跳论证；可被最终回答引用 |
| `context_ready` | 符合 `influences` / `precedes` 语义；具备时间、机制或制度锚点 | 只在历史/情景问题显式开启；必须提示它不是自动证明 |
| `legacy_candidate` | 旧边缺 `note`、关系含义不清，或来源仍缺口 | 仅在一跳界面中显示为“待核验联系”；不得进入 2～3 跳或成为回答依据 |
| `invalid` | 目标不存在、指向 domain、签名不合法或与正文直接冲突 | 不能遍历；由建构生成修复候选 |

  新写入的所有正式边都必须达到 `argument_ready` 或 `context_ready`。`involves` 也需要角色说明；不再允许空 `note` 作为“以后再补”的默认状态。

  同时需要确立一个减少摩擦的事实边界：**只有 frontmatter 中的 `relations[]` 才能改变正式图谱。** 正文中的卡片名称、列表、`[[wikilink]]`、案例枚举或“参见”文字只服务人类阅读与检索，不应被 Harness 推断成隐含关系。关系补丁只提交目标、类型和说明，不应要求模型回抄整张长卡正文。

## 6. OPS 如何使用这套关系

| OPS | 读取的平面 | 默认关系或过滤 | 结果边界 |
|---|---|---|---|
| `graph_search` | Card 元数据与正文 | `type`、`domains`、`school`、`applicable_scope`、`maturity`、来源摘要 | 只给候选，不把相似度当作关系 |
| `graph_members` | 领域归属 | `domains[]` | 只列成员，永不走成推理路径 |
| `graph_walk` 1 跳 | 论证平面 | `supports`、`based-on`、`extends`、`example-of`、`part-of`；按需加 `conflicts-with`、`involves`、`applies-to` | 找直接证据、基础、反证或机制组成；返回边说明 |
| `graph_walk` 2 跳 | 就绪论证边 | 至少保留一条 `supports`、`based-on` 或 `part-of` | 找中介机制或共同基础；不混入 legacy 边 |
| `graph_walk` 3 跳 / `graph_path` | 就绪论证边 | 限制路径数、节点数与高连接枢纽比例 | 只用于桥接假设或局部结构探索；路径不是结论，关键卡必须精读 |
| `inspect_argument` | 论证 + 来源 | supports 入边、based-on 出边、冲突、适用条件、来源 | 形成有边界的 Argument View，而非自动裁决 |
| `inspect_conflicts` | 争议平面 | conflict 的 `involves` 与双方 `conflicts-with` | 分离双方立场、证据、限制与未覆盖分歧 |
| `trace_source` | 来源追溯 | `sources[]`、Buffer、Archive 锚点 | 返回原文定位或缺口；不把“有来源”误判为“全部被证明” |
| `applicability_check` | Card 条件 + `applies-to` | `applicable_scope`、适用条件、失效边界 | 返回 matched / partial / mismatched / unknown，不给伪精确分数 |

  路径扩展必须遵守“越远越严格”。一跳允许发现 legacy 候选；二跳只走 `argument_ready`；三跳要求整条路径均就绪，且至少包含一条机制或证据边。`influences` 和 `precedes` 不参与默认路径，只有历史叙事、情景分析或用户明确要求因果/时序时才开启。

## 7. 对当前知识库的修复顺序

  不建议从 2,028 条边开始机械补 `note`。应以可被真实 OPS 调用的局部任务为单位推进，每次只处理一个领域簇或一条问题链，并在写后重跑对应 OPS 验证。

1. **先修论证骨架。** 从高连接模型、活跃 conflict 和常用于回答的领域开始。优先补 `supports`、`based-on`、`extends`、`conflicts-with`、`involves` 的说明与来源锚点；这些边决定解释、比较和反证能否可靠进行。
2. **重整 `influences`。** 506 条边逐簇分流，而不是统一把它们打开进入默认检索。重点检查现有高连接模型和 conflict 容器发出的影响边。
3. **把机制和历史从模糊关联中抽出。** 对确有组件结构的关系改用 `part-of`；对有时间锚点的历史阶段改用 `precedes`。这两类边少而精，优先服务金融危机、货币制度和贸易史的分析链。
4. **修复 conflict 容器。** 先处理 43 张带有非 `involves` 出边的 conflict 卡，把证据和理论基础放回双方立场或模型卡，再保留冲突卡的对立问题与涉及方。
5. **处理孤立卡。** 186 张无关系卡不预设必须连接。每张只在三种结论中选一种：成为某一模型/主张的真实实例或证据、保留为独立资料、或标记为待重写/归档。禁止为消除孤立率添加“主题相关”边。
6. **补来源闭环。** 先修复影响 109 张 Card 的 298 条 Buffer 缺口，优先覆盖高连接模型、核心 claim 与 conflict 双方；没有来源锚点的卡仍可被检索，但不能作为高等级论据。
7. **最后处理样例隔离。** 当前 11 张示例卡和 3 组重复 id 已被正式检索图隔离，不应与事实知识混用；后续决定移出、改名或转正时再单独处理。

## 8. 建构与写入的最小契约

  建构 Thinking Mode 可以发现候选边，但不直接决定它已经成立。每个 `propose_add_relation` 或 `propose_remove_relation` 至少应带：源卡与目标卡、关系类型、关系说明、读过的 Card/来源观察引用、预期改善的 OPS 行为，以及可逆方式。

```json
{
  "op": "propose_add_relation",
  "source": "流动性偏好与利率效应",
  "target": "央行通过制度工具影响而非完全决定市场利率",
  "type": "supports",
  "note": "在短期货币传导正常、价格黏性的条件下，货币需求与供给共同形成利率的机制支持后者的有限影响判断。",
  "evidence_refs": ["obs-read-12", "obs-source-07"],
  "expected_effect": "解释利率问题时可从结论回溯到短期货币需求机制。",
  "rollback_hint": "删除本次关系，不改动两张卡正文。"
}
```

  Harness 应做存在性、领域隔离、关系语义、`note` 完整性、来源可追溯性、重复边和写后 GraphOps 复核。对于成熟卡、枢纽卡、冲突卡或三跳桥接边，自动写入模式也应先通过预检；手动确认模式则在预检后呈现可读的变更摘要。

## 9. 验收标准

| 检验 | 第一阶段标准 |
|---|---|
| 事实完整性 | 保持正式图零幽灵目标、零关系指向 domain、零非法签名 |
| 新边质量 | 新增或修改的关系 100% 有非空、可解释的 `note`；禁止正文推断隐式边 |
| 核心论证簇 | 常用高连接模型、核心 claim 与 conflict 的论证边和来源锚点全部就绪 |
| 冲突质量 | conflict 只承担争议结构；双方证据与基础可沿相关立场 Card 检索 |
| 多跳纪律 | 2 跳与 3 跳结果均返回真实完整路径、每条边说明、截断原因与来源状态 |
| 情景纪律 | `influences` / `precedes` 只能在显式情景或历史请求中使用，并与论证边视觉区分 |
| 回答可核验 | 每个作为结论骨架的 Card 都能回到 Card 槽位和至少一个来源或明确的来源缺口 |

## 10. 后续实现边界

  首先应更新正式关系契约与关系质量校验，再让 GraphOps 按“就绪等级”过滤和返回警告；随后修改建构提示与写入预检，最后才开始按领域簇修复存量边。图谱动画只消费这些真实 Observation：领域成员查询、论证边走读、历史/情景链、来源回查和写后复核应有不同事件，而不应根据模型文字猜测。

  本设计暂不引入图数据库、关系置信度字段、自动大规模补边或更多 Card 类型。现有十种关系和既有 Card 标注足以完成第一轮有效推理；新增概念必须先证明当前关系确实无法表达真实案例。

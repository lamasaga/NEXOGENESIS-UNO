# Card 内部可寻址语义单元设计思路

> 状态：第一阶段试点已实施，正在验证  
> 目的：验证更细粒度的读取和 GraphOps 是否有真实收益，不改变 Markdown 主权，也不取消 Card。

## 1. 要解决的问题

  当前 Card 既是可独立阅读的知识文件，也是图中的基本节点。这个尺度适合长期维护，但当 Agent 只想检查一条主张、一个机制或一项成立条件时，往往仍需读取整张 Card。关系和工具也主要作用于 Card，难以精确指向正文内部的具体内容。

  本设计为 Card 内少量重要内容增加稳定地址，使工具能够索引和单独读取它们。第一阶段只解决“定位与读取”，不把所有段落改造成图节点，也不建立第二套知识事实源。

## 2. 基本判断

  Card 与 Buffer 不是重复层。Buffer 保存某份材料中值得沉淀的质料；Card 保存跨来源整理、修订后的长期理解。Card 仍应是可阅读、可审阅、可版本管理的正式知识对象。

  更细粒度的内容分为两类：能够脱离原 Card 独立理解、会被多处引用和单独修订的内容，应成为正式 Card；主要依附某张 Card、但需要被精确读取的内容，可以成为 Card 内部的可寻址单元。

```text
能够独立存在和长期维护
    → 正式 Card

主要依附某张 Card，只需被精确引用
    → Card 内部可寻址单元

只用于搜索、读取和运行时操作
    → 可删除、可重建的派生索引
```

## 3. 与现有 Card 结构的关系

  Card 继续由三部分组成：frontmatter 管整张卡的身份和卡间关系；正文保存完整、自然的知识表达；少量单元标签为正文中的重要内容提供稳定地址。

```text
Card Markdown
├─ frontmatter：Card 身份、类型、领域、来源和卡间关系
├─ 正文：完整、可独立阅读的知识表达
└─ unit 标签：正文内部少量重要内容的稳定地址
       ↓
   可重建的段落索引或局部图投影
```

  目录仍用于文件分类和人工导航。目录是一棵树，不能表达一个对象同时属于多个领域、一个证据支持多个主张、一个机制受多个边界约束等图关系，因此不应把文件路径当作知识关系本身。

## 4. 建议的 Markdown 表达

  第一版可以在已有语义槽内使用不可见的 HTML 注释保存稳定标识，不增加新的正文标题，也不影响普通 Markdown 阅读器。

```markdown
---
id: 最后贷款人抗挤兑再融资
type: model
domains:
  - 货币金融体系
---

# 最后贷款人抗挤兑再融资

## 核心主张

<!-- unit: claim-liquidity-run -->

当金融机构仍具偿付能力但遭遇短期流动性冲击时，
最后贷款人融资可以降低恐慌性挤兑引发的被迫清算。

## 成立边界

<!-- unit: boundary-solvency -->

接受融资的机构必须仍具有偿付能力。
```

  单元的完整地址由 Card id 和局部 id 组成：

```text
最后贷款人抗挤兑再融资#claim-liquidity-run
最后贷款人抗挤兑再融资#boundary-solvency
```

  局部 id 只需在所属 Card 内唯一。修改正文时保留 id，工具引用便不会因为句子改写或标题调整而失效；真正改变了该单元的含义时，才应新建 id，并让旧 id 失效或留下迁移记录。

## 5. 哪些内容值得标记

  不给每个自然段加标签。只有已经出现精确读取或操作需求的内容才标记：

- 可以被支持或反驳的主张；
- 相对完整的作用机制或因果步骤；
- 明确的假设、成立条件或失效边界；
- 需要跨 Card 核对的关键证据；
- 经常被引用的定义、区分或方法步骤。

  过渡句、解释性补充、写作性段落和普通原文摘录默认不标记。标签密度由真实工具需求决定，不作为 Card 完整度的新指标。

## 6. 派生索引的最小字段

  索引可以从 Markdown 重建，初期无需决定长期存储技术。JSONL 或现有索引机制均可，字段只保留读取所需的信息：

```json
{
  "id": "最后贷款人抗挤兑再融资#claim-liquidity-run",
  "kind": "claim",
  "parent_card": "最后贷款人抗挤兑再融资",
  "section": "核心主张",
  "text": "当金融机构仍具偿付能力……",
  "source_anchor": "claim-liquidity-run",
  "card_revision": "正文版本摘要"
}
```

  这里的 `kind` 只服务检索和工具选择，不是新增正式 Card 类型。派生文件不得成为写入权威；索引损坏或删除后，应能从 Card 重新生成。

## 7. 工具能力的实施顺序

  第一阶段只增加寻址和读取：

```text
list_card_units(card_id)
→ 列出一张 Card 已标记的单元

read_card_unit(address)
→ 读取一个单元及少量必要上下文

search_card_units(query, kind?)
→ 在已标记单元中检索，结果始终返回所属 Card
```

  此时单元不是可独立写入的知识对象，GraphOps 不能绕过 Harness 直接修改它。单元正文仍通过 Card 修订事务变更，并接受修订冲突和 Card 合法性检查。

  第一阶段工具现已落地：`list_card_units`、`read_card_unit`、`search_card_units` 都直接从 Card Markdown 重建结果，不保存第二份语义事实。Card 中没有单元标记时返回空清单，兼容全部存量卡片。

  只有真实案例证明段落级寻址明显改善判断后，才验证第二阶段：让部分单元参与支持、反驳、条件约束或因果链等派生关系。关系仍须能回查到 Card 和具体段落。

## 8. 单元升级为 Card 的条件

  内部单元出现以下情况时，Digest 或 Construct 可以提出“升格为 Card”，但仍需经过正常候选、校验和授权：

- 被多个 Card 独立引用；
- 具有自己的证据、反证或边界；
- 需要单独修订而不应连带改写父 Card；
- 已能脱离父 Card 独立阅读；
- 用户确实会把它作为独立知识对象检索和讨论。

  升格后，父 Card 保留简要说明并用正常关系指向新 Card。不要同时维护两份完整正文。

## 9. 验证方式

  第一轮选择一个真实领域中的 3～5 张 Card，只标记已经发现操作需求的内容，比较整卡读取与单元读取在相同任务中的表现。

  第一组正式验证样本为：`潜在结果反事实因果模型`、`观察研究三项识别条件`、`工具变量识别路径`、`服从者局部平均处理效应`、`弱工具变量偏误放大`。五张卡同时用于验证内部语义寻址、关系就绪检查和图像来源追溯；它们是试验样本，不意味着所有存量 Card 都应立即加标签。

  关注以下结果：

- 是否减少无关正文和重复读取；
- 是否提高反证、边界和机制定位的准确度；
- 单独读取后是否仍保留足够上下文；
- 标签是否频繁因正文修订失效；
- 是否出现大量难以治理的近义单元；
- 人工维护成本是否低于获得的收益。

  若没有明显收益，可以删除派生索引并移除少量标签，Card 内容不会损失。若收益稳定，再把格式和工具写入 `.agent/reference/` 活契约；在完成真实验证前，本文件不构成 Card 格式要求。

## 10. 当前不做的事情

- 不取消 Card，也不把 Buffer 改成长期知识的唯一来源；
- 不建立与 Markdown 并列的 Semantic Object Store；
- 不给所有段落自动编号；
- 不让每个单元都成为正式图节点；
- 不增加大批新的本体类型和关系；
- 不把派生索引写回为第二份长期知识。

  这项设计的价值在于给现有 Card 增加更细的操作尺度，而不是更换知识底座。是否继续扩展，由真实任务中的读取质量和 GraphOps 收益决定。

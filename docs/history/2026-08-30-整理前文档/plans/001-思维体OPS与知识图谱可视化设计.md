# 思维体 OPS 与知识图谱可视化设计

> 状态：设计方案，尚未实施  
> 审视基线：`662d1a2`  
> 日期：2026-08-27  
> 范围：DSH Web 对话、CognitiveRun、Thinking Model、Workspace、Episode、Observation 与中央知识图谱  
> 不在范围：暴露模型隐藏思维链、修改知识卡片契约、重写 DSH Agent Loop、把运行事件升级为知识事实源

## 一、目标与边界

  本设计的目标不是制作一段看起来像“AI 在思考”的装饰动画，而是把思维体已经发生、可以审计的操作投影到界面：它选择了什么 Thinking Model，调用了哪个 OPS，观察到了哪些卡片、关系与来源，Workspace 中增加了什么证据或疑问，为什么继续、换路或结束，以及写入是否经过 Harness 接受。

  用户最终应能直观回答五个问题：

1. 思维体当前在解决什么问题？
2. 它采用了哪种 Thinking Model，这个模型要求哪些观察能力？
3. 它刚刚在知识体上执行了什么真实 OPS？
4. 新观察如何改变了 Workspace 中的假设、证据、反证、冲突与下一步？
5. 最后的回答和写入分别依据了哪些可追溯对象？

  必须坚持一条边界：界面展示的是“可审计认知轨迹”，不是模型隐藏思维链。允许展示目标、操作、结构化 Observation、简短行动理由、Workspace 变化、证据锚点和 Harness 收据；不得生成或声称展示模型内部逐词推理过程。

## 二、现状审视

### 2.1 已经具备的基础

  当前实现不是从零开始，已有四块可以直接利用的基础：

- `CognitiveRun` 已保存任务模式、状态、步数、Thinking Model、checkpoint 与会话关系。
- `Workspace` 已保存目标、范围、假设、证据、反证、开放问题、冲突、候选动作、已观察节点、延后项与预算。
- `Episode` 已记录每一步 action、结构化 Observation、简短 rationale 与 evidence anchors。
- 前端 `ActivationEngine` 已支持检索、种子命中、关系扩散、读卡、写入、完成与失败等基础动效，并已有错峰、缓冲、减少动态效果和高分屏渲染。

  因此，下一步不需要新造一套“思维状态”，而应把这些真实状态接入统一投影链。

### 2.2 当前断点

#### 高优先级：前端看到的是工具名推测，不是真实 Observation

  `packages/nexogenesis-web-host/lib/chat.js:145-240` 使用 `pendingRetrieveQuery` 和 `pendingWalkStart` 临时变量，把 `tool/call` 与随后出现的 `tool/result` 拼成图谱事件。它只识别 retrieve、graph_search、graph_walk、graph_analogize 与 read_card，未覆盖 compare_nodes、inspect_conflicts、trace_source、Thinking Model 选择、Workspace 更新、治理信号和 Harness 收据。

  更严重的是，graph_walk/graph_analogize 的结果被投影为 `edge_ids: []`。界面声称“沿真实关系扩散”，实际却无法点亮真正走过的边。read_card 又在工具刚开始调用时就触发读卡动效，即使工具随后失败也会显示成功读取。

#### 高优先级：真实 TM 与 Workspace 已存在，但前端没有消费

  `packages/nexogenesis-web-host/lib/cognition.js:4-50` 已返回 `projection`、Workspace、Episode 和 Thinking Model。`web/src/api/client.ts:354` 却把认知会话接口收窄为只有 `interaction`；`web/src/App.tsx:140-162` 轮询时也只处理等待用户回答的交互。因此，中央图谱与右侧面板看不到真正的 TM、证据积累、反证、开放问题和下一步。

#### 高优先级：事件缺少稳定关联与恢复能力

  `packages/nexogenesis-web-host/lib/events-bus.js` 是仅在内存中存在的 SSE 广播器，没有 `run_id`、`episode_id`、`tool_call_id`、单调序号或断线补发。刷新、切换对话或短暂断线后，正在进行的可视化无法从 Episode/Workspace 恢复。当前两个单值 pending 变量也可能在重叠工具调用时把结果配错。

#### 中优先级：Workspace 成功更新没有可归因步骤

  `packages/nexogenesis-tools/lib/cognition/tools.js:94-147` 中，成功的 `update_cognitive_workspace` 只更新文件，不记录 Workspace diff；只有契约拒绝才写入 Episode。`packages/nexogenesis-tools/lib/cognition/run-store.js:401-425` 的 step 保存的是动作执行前的 Workspace 摘要，也没有 `workspace_revision_before/after`。这使界面无法准确说明“这次观察让哪个假设或证据发生了变化”。

#### 中优先级：图谱动效语义仍偏单一

  `web/src/graph/render.ts:133-206` 对所有激活边使用统一金色，关系类型颜色完全让位于“信号色”。这能突出流动，但会丢掉“思维体沿什么关系行动”的信息。现有放射扫描也无法区分关键词召回、领域成员展开、冲突检查、节点比较、跨域类比和来源追溯。

#### 中优先级：叙事状态是单槽位，快速操作会互相覆盖

  `ActivationEngine` 只有一个当前 narration。检索、图谱事件和 App 内的 pipeline step 都可能改写它。快速连续调用时，用户看到的标题可能不是当前图上正在播放的动作，也无法回看上一步。

#### 中优先级：大图谱下持续逐帧遍历存在成本

  `web/src/graph/GraphCanvas.tsx:133-135` 持续运行 requestAnimationFrame；激活层和标签层在每帧遍历全部关系束与节点。图谱达到数千卡后，即使没有动作也会产生不必要的绘制成本。新的可视化不能继续用“每新增一种 OPS 就全图多扫一遍”的方式扩张。

#### 实施前应先核对的独立故障

  `packages/nexogenesis-web-host/lib/chat.js:301` 仍以两个参数调用 `resumeCognitiveInteraction(ctx, preparedInteraction)`，而当前定义为 `resumeCognitiveInteraction(ctx, projectRoot, prepared)`。这可能使等待用户选择后的继续执行失败。它不是本设计的可视化问题，但会直接打断需要展示的完整认知轨迹，应在实施首轮先做回归确认。

## 三、方案选择

### 方案 A：继续在前端按工具名解释

  做法是扩充 `chat.js` 的 if/else，为每个工具手写一组 SimEvent。

  这个方案改动小，但会继续复制 OPS 语义；工具返回结构变化后，动画再次失真。它也无法可靠恢复 Workspace 与 TM，不建议采用。

### 方案 B：以 CognitiveRun 为事实基础，增加统一认知事件投影（推荐）

  DSH 工具完成后先产生结构化 Observation，Runtime 持久化 Episode/Workspace，再由轻量投影器生成前端事件。SSE 只负责实时传输；刷新时从 CognitiveRun 当前快照与 Episode 最近步骤重建界面。

  该方案不把系统改造成完整事件溯源架构，也不改变 Markdown 的语义主权。它只统一“真实认知状态如何被前端观察”，正好解决已经存在的问题。

### 方案 C：把所有运行状态改造成事件溯源系统

  完全以事件重放构建 Run、Workspace 和 UI，理论上恢复能力最强，但会引入幂等、重放一致性、版本迁移与事件存储治理。对当前单机 DSH 属于过度设计，不建议采用。

## 四、推荐总架构

```text
DeepSeek / Skill
    │ 真实 tool/call（带 tool_call_id）
    ▼
OPS 执行器 ── transient: op.started ───────────────┐
    │                                              │
    ▼                                              │
结构化 Observation                                │
    │                                              │
    ├─ Runtime.record → Episode                    │
    ├─ Runtime.updateWorkspaceWithDiff → Workspace │
    └─ HarnessGateway → Receipt                    │
                    │                              │
                    ▼                              │
             CognitiveEventProjector ◄────────────┘
                    │
           SSE + 当前快照/最近步骤恢复
                    │
                    ▼
       前端 CognitiveStore（唯一消费入口）
          ├─ GraphEffectProjector → 中央图谱
          ├─ Thinking HUD → TM / 当前 OPS / 预算
          ├─ Workspace Inspector → 证据与问题
          └─ Trace Timeline → 可回看步骤
```

  这里的关键不是再增加一套运行真相。Episode 与 Workspace 仍是可恢复状态；CognitiveEvent 是它们面向 UI 的投影。短暂的 `op.started` 可以只存在于实时流中，`op.observed`、`workspace.updated` 与 Harness 收据必须可以从持久化状态重建。

## 五、统一认知事件契约

  建议把现有宽松的 `SimEvent` 升级为带版本和关联键的 `CognitiveEvent`。字段应保持有限，只包含 UI 真正需要且已能从运行事实取得的信息。

```ts
type CognitiveEventKind =
  | "run.started"
  | "tm.selected"
  | "op.started"
  | "op.observed"
  | "workspace.updated"
  | "interaction.waiting"
  | "interaction.resumed"
  | "proposal.created"
  | "harness.receipt"
  | "governance.signal"
  | "run.completed"
  | "run.failed"
  | "run.cancelled";

interface CognitiveEvent {
  schema_version: "1.0";
  event_id: string;
  session_id: string;
  run_id: string;
  episode_id: string;
  seq: number;
  at: string;
  kind: CognitiveEventKind;
  tool_call_id?: string;
  operator?: {
    name: string;
    capability?: string;
    mode?: "read" | "proposal" | "write" | "runtime-write";
    risk?: "low" | "medium" | "high";
  };
  targets?: {
    node_ids?: string[];
    edge_ids?: string[];
    source_ids?: string[];
    domain_ids?: string[];
  };
  observation?: {
    status: "ok" | "empty" | "rejected" | "failed";
    channel?: string;
    summary: string;
    reason_code?: string;
    on_topic_new?: number;
    truncated?: boolean;
  };
  workspace_delta?: WorkspaceDelta;
  governance?: {
    usage: { steps: number; reads: number; writes: number };
    limits: { steps: number; reads: number; writes: number };
    loop_signal?: string | null;
  };
  presentation: {
    title: string;
    detail?: string;
    tone: "neutral" | "active" | "evidence" | "conflict" | "warning" | "success";
  };
}
```

  `presentation` 只提供稳定的中文动作名称与简短说明，不携带动画参数。动画参数由前端按事件语义统一决定，避免后端控制视觉细节。

### 5.1 WorkspaceDelta

```ts
interface WorkspaceDelta {
  revision_before: number;
  revision_after: number;
  added: Partial<Record<WorkspaceBucket, WorkspaceItem[]>>;
  changed: Partial<Record<WorkspaceBucket, WorkspaceItem[]>>;
  removed: Partial<Record<WorkspaceBucket, string[]>>;
}

type WorkspaceBucket =
  | "hypotheses"
  | "evidence"
  | "counter_evidence"
  | "open_questions"
  | "conflicts"
  | "candidate_actions"
  | "observed_nodes"
  | "deferred_items";
```

  每个 WorkspaceItem 应尽量携带 `card_ids`、`source_anchors` 或 `observation_id`，让用户点击条目时可以回到图谱与来源。无法定位的自然语言条目仍可显示，但不得伪造图谱连接。

### 5.2 关联纪律

- 每个真实工具调用必须有 `tool_call_id`；开始、结果与失败以它关联。
- 每个持久化事件必须有递增 `seq`；前端按 `run_id + seq` 排序并去重。
- `op.started` 只表示请求已发出，不得触发“成功读到卡片”的动效。
- 图谱节点、边与来源必须来自 Observation，不从回答文本或工具名猜测。
- `workspace.updated` 必须在写入成功后产生，并记录 revision before/after。
- Harness 拒绝与失败必须覆盖此前的进行态，不能让节点继续保持“已写入”视觉。

## 六、OPS 到视觉语义的映射

  不建议为每个 OPS 单独写动画。应先按 Observation channel 归为少量稳定的视觉语法，再由具体 OPS 提供真实目标。

| OPS / Observation | 中央图谱 | Thinking HUD | Workspace 变化 |
|---|---|---|---|
| retrieve / graph_search | 一次克制的检索波纹；命中节点按排名 100–120ms 错峰出现 | “检索候选 · 命中 N 张” | 可更新 observed_nodes，不自动写 evidence |
| read_card | 成功结果后聚焦该节点，橙黄色光晕与标题浮现 | “深读：卡片标题” | 由后续 Workspace 更新决定是否成为证据 |
| graph_walk | 沿 Observation 中真实 edge id 逐段传播 | “沿 supports / refines 等关系展开” | 记录新观察节点与关系摘要 |
| inspect_domain_members / graph_members | 领域节点先亮，成员节点由内向外出现；不画不存在的边 | “查看领域成员” | 更新观察范围 |
| compare_nodes | 两个锚点同时聚焦；真实直接关系正常点亮，共同领域形成轻量包络 | “比较 A 与 B” | 可新增相同点、差异或开放问题 |
| inspect_conflicts | 冲突节点使用淡黄色/琥珀警示环，相关 parties 分侧出现 | “检查冲突与覆盖范围” | 新增 conflict 或 counter_evidence |
| graph_analogize | 两个远端簇分别聚焦；使用临时点状比较弧，不冒充知识边 | “跨域类比” | 新增 hypothesis 或 candidate_action |
| trace_source | 卡片聚焦，来源锚点在 HUD/来源抽屉展开；来源不是图节点时不画边 | “追溯来源” | evidence 增加来源锚点或置信说明 |
| update_cognitive_workspace | 图谱只轻触本次 delta 引用的节点，不做全图扫描 | “整理工作区” | 对新增/变更条目做 diff 动效 |
| propose_* | 目标节点/关系使用虚线预览，不并入静态图 | “提出变更，等待确认/校验” | candidate_actions 增加提案 |
| Harness accepted | 预览形态收束为实体；刷新图数据后保持激活连续 | “写入已接受” | candidate_action 移入结果 |
| Harness rejected | 预览撤回，相关对象短暂警示，不闪烁整图 | “写入被拒绝：原因” | 新增修正动作或 deferred item |
| finish_cognitive_run | 当前工作集柔和归位，依据节点保留短暂余辉 | “回答已形成” | 显示最终结果与未解决项 |

### 6.1 连线颜色建议

  推荐采用“双层信号”而不是全金色或完全沿用原色：

- 已存在关系的亮起轨迹保留该关系的基础色，以表达语义。
- 移动前锋使用统一的暖白金色，以表达“Agent 信号正在传播”。
- 冲突仍以协调的淡黄/琥珀表达，不使用高饱和红色。
- 临时比较弧、类比弧使用点状或短划线，并在动画结束后消失，避免被误解为已落盘关系。

  这样用户既能看出“行动发生了”，又能看出“它沿什么关系发生”。

### 6.2 动效参数

| 动作 | 建议参数 | 说明 |
|---|---|---|
| OPS 开始状态 | 160ms，`cubic-bezier(0.23,1,0.32,1)` | 仅透明度与 4px 内位移 |
| 真实关系传播 | 保留约 720ms 前锋；边错峰 100ms | 适合解释路径，不追求点击反馈速度 |
| 节点召回 | 节点错峰 120ms | 与现有偏好一致，同批不同时亮灭 |
| Workspace 新条目 | 180ms，最多 4px 上移；最多三项错峰 50ms | 只动画真实 diff，不随轮询重复动画 |
| TM 切换 | 220ms ease-in-out 淡入淡出 | 低频重要变化，可以稍慢 |
| 成功/拒绝状态切换 | 160–200ms | 不用大幅缩放和闪烁 |
| 退出/归位 | 220ms ease-in-out | 防止所有高亮同时突然熄灭 |

  减少动态效果模式下应取消移动前锋、波纹扩散与位移动画，但保留边框、颜色、标签和步骤顺序，确保信息不依赖运动才能理解。

## 七、Thinking Model 的呈现

  Thinking Model 不应被画成知识图谱中的一个节点。它不是知识事实，而是本轮任务采用的观察约束与停止条件。推荐在中央图谱左上方现有状态卡基础上改造成“Thinking HUD”。

### 7.1 常驻最小态

```text
[TM：bridge-analysis]  第 6 / 24 步
当前：沿论证关系展开
目标：解释 A 与 B 的连接机制
```

  常驻态只占一小块，不遮挡知识图谱。用户可以展开查看：

- TM purpose。
- required capabilities 及完成勾选。
- stop conditions。
- 当前预算：steps / reads / writes。
- loop signal，例如“连续三次读取无新增，应换角度或结束”。

### 7.2 能力完成不是动画猜测

  required capabilities 的勾选必须来自 Episode 中已经成功完成的 operator/capability 证据。工具开始调用时显示进行中，Observation 为 ok 后才完成；empty、rejected 与 failed 不计为已满足，除非对应 TM 契约明确允许。

### 7.3 TM 切换

  如果 Agent 改选 Thinking Model，HUD 应保留一条时间线标记：“第 4 步由 evidence-check 切换为 conflict-mapping”。只显示模型声明的用途与约束，不展示隐藏推理链。

## 八、Workspace 的呈现

  Workspace 不是第二个聊天记录，也不应把全部 JSON 堆到图谱上。推荐在右侧对话工作台增加可折叠的“思维工作区”，中央 HUD 只显示当前焦点和最近一次变化。

### 8.1 信息分组

1. 假设。
2. 依据。
3. 反证。
4. 冲突与开放问题。
5. 下一步与延后项。

  每组默认显示最近或权重最高的三项，其余用“+N”折叠。条目应标注来源类型：知识卡、关系、原文锚点、模型暂定判断。模型暂定判断不得用与已验证证据相同的视觉样式。

### 8.2 交互

- 点击带 card id 的条目：中央图谱聚焦相关节点与真实关系。
- 点击带 source anchor 的条目：打开来源摘要或原文位置。
- 点击 Episode 步骤：进入“回看态”，重放该步的图谱高亮和 Workspace diff，不重新调用模型。
- 回看态顶部明确显示“历史步骤”，点击“返回实时”恢复当前状态。
- 用户可以折叠整个思维工作区，不影响对话和任务运行。

### 8.3 不应呈现的内容

- 不显示未经结构化、可能含有隐藏思维链的长篇 rationale。
- 不把检索候选自动标为证据。
- 不把类比线、比较线显示为已经存在的图谱关系。
- 不把工具开始显示为工具成功。
- 不用“AI 正在深度思考”一类无法核验的泛化文案。

## 九、前端信息层级

```text
顶栏
└─ 当前对话 / 历史 / 收藏 / 帮助

中央知识图谱
├─ Thinking HUD（常驻最小态，可展开）
├─ 真实节点与关系激活
├─ 临时语义覆盖层（比较、类比、提案）
└─ 当前 OPS 一行说明

右侧对话工作台
├─ 对话回答
├─ 可折叠“思维工作区”
│  ├─ 可审计步骤时间线
│  └─ 假设 / 依据 / 反证 / 问题 / 下一步
└─ 来源与 Harness 收据
```

  中央图谱负责回答“刚才操作了哪里、沿什么关系、结果落在哪”；右侧工作区负责回答“这些观察如何组织成结论”。两者通过同一个 `event_id/step` 联动，避免把过多文字压在图谱上。

## 十一、分阶段实施

### 阶段 0：先固定事实边界

  目标是消除“动画说发生了、实际没发生”的情况。

- 核对并修复 interaction resume 参数回归。
- 为 DSH tool lifecycle 引入 `tool_call_id` 关联。
- read_card 只在成功 Observation 后点亮。
- graph_walk 使用 Observation 返回的真实 edge id。
- 为 retrieve → read_card → graph_walk 建一条端到端契约测试。

  验收：一次真实对话中，图谱亮起的每个节点和边都能在 Observation 中找到；工具失败不会留下成功动效。

### 阶段 1：接通 TM、Workspace 与 Episode

- 扩展认知会话 API，不再只返回 interaction。
- 成功 Workspace 更新产生结构化 diff 与 revision。
- 建立 CognitiveStore，支持当前快照 + 实时事件。
- 上线最小 Thinking HUD 与 Workspace Inspector。

  验收：刷新页面后，TM、预算、最近步骤和 Workspace 内容不丢失；不依赖重新跑 Agent。

### 阶段 2：补齐 OPS 视觉语法

- 先实现 graph_search、graph_walk、read_card、compare_nodes、inspect_conflicts、trace_source。
- 再实现 domain membership、graph_analogize、proposal 与 Harness receipt。
- 每种视觉效果都以 Observation channel 为输入，不直接判断工具名。

  验收：六类核心观察在界面上可以被用户仅凭图形与简短中文动作区分；不存在虚构关系。

### 阶段 3：回看、恢复与性能

- 按 seq 补发最近事件，支持 Episode 步骤回看。
- idle 时停止 RAF，活跃集合增量绘制。
- 增加 3000 节点规模测试与 reduced-motion 走查。

  验收：断线恢复后状态一致；3000 节点静止时不持续进行全图动态遍历；回看不触发模型或写入。

## 十二、评测方案

### 12.1 契约正确性

- 每个 tool_call_id 最多有一个最终状态：observed、failed 或 cancelled。
- 100% 的真实关系动效 edge id 存在于对应 Observation 或图数据。
- failed/rejected 工具不会产生 read/commit 成功视觉。
- Workspace delta 的 revision 连续，重复事件不重复新增条目。
- TM required capabilities 的完成状态与 Episode 中成功 Observation 一致。

### 12.2 场景评测

1. 日常问答：retrieve → read → graph_walk → 回答。
2. 冲突问题：inspect_conflicts → 读双方卡 → counter_evidence。
3. 比较问题：compare_nodes → 共同领域 → 差异与开放问题。
4. 来源追溯：trace_source → 原文锚点 → 证据升级。
5. 涌现写入：proposal → 用户确认 → Harness accepted/rejected。
6. Loop 改路：连续低新增 → governance signal → 新检索角度或结束。
7. 等待用户：interaction.waiting → 刷新页面 → 回答 → resume。
8. 断线恢复：执行中关闭 EventSource，再连接后恢复 TM、Workspace 与最近步骤。

### 12.3 用户理解度

  邀请用户在不看调试日志的情况下回答：当前目标是什么、用了什么 TM、刚做了哪个 OPS、得到了什么新证据、下一步为什么发生。五项至少四项可在十秒内定位，才算设计达标。

### 12.4 性能与可访问性

- 活跃动画期间主线程帧耗时 p95 低于 16.7ms，或至少不低于改造前基线。
- idle 状态不保持无意义的全图 RAF。
- 3000 节点下，点击、缩放、拖拽和对话滚动无明显阻塞。
- reduced-motion 模式下，所有状态仍能通过颜色、文本和顺序理解。
- Thinking HUD 与 Workspace Inspector 支持键盘焦点与屏幕阅读器状态文本。

## 十三、实施克制与撤回方式

  这次更新不应同时重写 Agent Loop、OPS 注册体系和图谱渲染器。第一轮只接通真实事件、TM、Workspace 与三种核心 OPS；确认正确后再扩展视觉语法。

  所有新增投影都应可通过一个前端 feature flag 关闭，关闭后保留现有图谱与对话功能。Episode/Workspace 新字段应向后兼容旧运行记录；缺少 delta 时以前后快照只读推导，不回写历史文件。

  如果 CognitiveEvent 投影证明维护成本过高，可以撤回前端新视图而不影响 CognitiveRun、知识卡片、HarnessGateway 与 Agent Loop。该设计不改变 Markdown 事实源，也不形成平行写入系统。

## 十四、最终判断

  当前最值得做的不是继续调亮动画或增加更多粒子，而是把视觉层的输入从“工具名和卡片列表”替换为“Thinking Model + 结构化 Observation + Workspace diff + Harness receipt”。完成这一步后，已有知识图谱动画才会从装饰效果变成 Agent 行为的可信投影。

  推荐从阶段 0 和阶段 1 开始。它们能先解决真实性、关联性和恢复性；只有这些成立以后，compare、conflict、analogy 等更精细的动效才值得投入。

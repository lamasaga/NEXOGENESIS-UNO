# 思维体分析测评台：行业调研、评测设计与实施规划

> 文档状态：现行设计，尚未实现。  
> 适用对象：DSH Web 思维体使用知识图谱完成对话研判、分析与结构化报告的过程。  
> 目标：判断知识图谱和 Agent Loop 是否让输出更可靠、更有分析价值，并能解释提升或退化发生在哪一步。

## 一、结论先行

  DSH 需要的不是一个给答案打“综合分”的小工具，而是一套本地运行的实验与诊断工具。本文暂称它为“思维体分析测评台”。它应在同一问题、同一模型设置、同一知识图谱快照和近似预算下，重复运行若干种系统配置，再比较最终答案、证据使用、OPS 轨迹、成本和稳定性。

  第一版不建议直接接入 LangSmith、Braintrust 等云平台作为核心依赖。这些产品的实验、基线比较和轨迹查看方法值得借鉴，但 DSH 有私有 Markdown 知识体、Typed Card、关系边、TM/OPS、Workspace 与写入主权等特殊约束。先做一个窄而可解释的本地测评台，更容易控制数据边界，也能直接复用现有 Episode 和 Workspace。以后如有需要，再把匿名实验记录导出到通用平台。

  最重要的设计判断有五项：

1. “可靠”与“有价值”必须分开评分；有洞见不能抵消错误引用。
2. 评估不仅看最终答案，也看 Agent 实际读了什么、如何沿图扩展、Observation 是否改变了下一步。
3. 对比必须使用明确基线，而不是只看新版本自己的得分。
4. 开放式分析采用盲化成对比较，并允许平局；不能要求模型复现唯一标准答案。
5. 评测只读知识体，任何情况下都不能因评分自动改写 Card、TM 或 OPS。

## 二、行业实践给出的有效方法

### 2.1 Agent 评测不是单一评分器

  OpenAI 的 Evals 将评测拆为数据来源与一个或多个 grader，并支持把字符串规则、相似度、代码检查、模型评分和多个评分器组合到同一次实验中。LangSmith 与 Braintrust 则把“固定数据集—运行实验—查看轨迹—比较基线—定位回归”作为基本工作单元。这些实践共同说明：复杂 Agent 不能依赖一个 Judge 提示词给出最终分数。

  Anthropic 对研究型 Agent 的建议更接近 DSH：同时检查 groundedness、关键事实覆盖率和来源质量，并用专家评分持续校准模型评分。其核心不是寻找一个万能指标，而是像多层防线一样，让不同 grader 捕捉不同错误。

### 2.2 RAG 评测要区分检索和生成

  Ragas、DeepEval 与 TruLens 都把至少三类问题分开：检索结果是否相关、必要信息是否被召回、最终主张是否得到上下文支持。对 DSH 而言还应再加一层：知识图谱的关系边是否真正带来了有效扩展，而不是仅仅多读了一批卡片。

  因而，“回答看起来正确”不足以证明知识图谱有效。模型可能依靠预训练记忆答对，也可能在召回错误时碰巧给出合理答案。测评台必须能单独比较无知识图谱、平面检索和 GraphOps 三种条件。

### 2.3 长篇分析更适合参考点与成对比较

  DeepResearch Bench 将报告质量拆成完整性、洞见深度、指令遵循和可读性，并另外评估有效引用数量与引用准确率。其后续工作继续把专家报告拆成细粒度、可核验的 rubric，而不是把整篇参考答案当成唯一标准。

  Braintrust 和 LangSmith 的实验比较实践还强调逐案例 delta：先对齐同一输入，再查看候选相对基线在哪些任务上提升、退化或无变化。成对评分时应随机交换 A/B 顺序，减轻 Judge 的位置偏差。DSH 应采用同样方法，并保留“平局”结果。

### 2.4 轨迹有诊断价值，但没有唯一正确轨迹

  Agent 可以通过不同路径得到同样可靠的答案，因此不宜规定唯一 OPS 顺序。轨迹评测应关注约束和有效性：是否读取了声称使用的卡片、是否处理反证、低收益扩展后是否改选、预算耗尽时是否停止、是否产生无效循环。

  这意味着 Episode 适合作为诊断证据，不应被当成必须逐步匹配的“标准思维链”。评测台不保存或展示模型隐式思维，只评估可观察的操作、Observation、Workspace 变化和最终产物。

## 三、测评对象与实验基线

### 3.1 一个实验案例必须固定什么

  每个案例至少固定以下条件：

- 用户任务及其必要背景。
- 知识图谱快照或专用 fixture。
- 模型供应商、模型版本、温度和推理设置。
- 系统表达风格与输出格式要求。
- 最大步骤、读卡、工具调用、token 与时间预算。
- 是否允许外部知识、是否允许写入。
- 评测 rubric、必要证据点、反证点和禁止出现的断言。

  快照必须包含 Card 正文、frontmatter、关系、来源摘要和 revision。否则同一实验在知识体发生变化后无法复现。

### 3.2 建议的五级对照

| 代号 | 运行条件 | 回答的问题 |
|---|---|---|
| B0 裸模型 | 同一模型，不提供知识图谱、检索工具和特定 TM | 模型自身能力有多强？ |
| B1 平面检索 | 关键词或 BM25 Top-K，固定拼接 Card，不允许沿图操作 | 仅“塞入相关材料”能提升多少？ |
| B2 GraphOps | 可使用 Observation OPS 与图关系，但使用通用循环策略 | 图结构本身带来多少提升？ |
| B3 当前稳定版 | 当前稳定 TM + OPS + Agent Loop | 现有完整思维体表现如何？ |
| C 候选版 | 待测 TM、OPS、提示词或 Loop 版本 | 候选相对稳定版是否值得晋升？ |

  可为少量诊断任务增加 O 组“人工证据包上界”：由专家预先选好最充分的 Card 和反证，再交给同一模型生成答案。若 O 明显优于 B3，问题主要在检索与工作区组织；若 O 也不理想，问题更可能在综合、表达或模型能力。O 组不参与日常发布门槛，只用于定位瓶颈。

  B0 与 B1 不要求模拟 DSH 的完整操作流程，它们是消融实验。B3 与 C 才是版本晋升的直接比较对象。所有组必须使用同一题目、模型和输出要求；否则无法把差异归因于知识图谱或 TM/OPS。

## 四、四层评分结构

### 4.1 第一层：确定性硬门槛

  以下任一关键项失败时，本案例的“可靠性”直接不通过，但仍保留其他评分用于诊断：

- 引用的 Card 必须存在，且本轮确实被检索或读取。
- Card revision 与实验快照一致。
- 不得虚构 Card、关系类型、关系目标、来源或工具结果。
- 明确引用的关系必须存在，方向与关系 note 必须一致。
- 用户限制、权限、停止指令和预算必须得到遵守。
- 要求区分“知识卡主张、模型推断、价值判断”时，不得混写。
- 任务要求承认证据不足时，不得把不确定性包装成确定事实。

  这些检查应尽量由代码完成，不调用 Judge。代码无法判定的语义支持关系再交给模型评分器。

### 4.2 第二层：证据可靠性

| 指标 | 建议定义 | 主要实现 |
|---|---|---|
| 主张支持率 | 得到已读 Card 明确支持的外部可核验主张数 / 全部此类主张数 | 主张抽取 + entailment Judge + 人工抽检 |
| 引用精确率 | 引用确实支持其附近主张的次数 / 全部引用次数 | 逐主张核验 |
| 必要证据覆盖率 | 命中案例 rubric 中必要证据锚点的数量 / 全部必要锚点 | 结构化规则 + Judge |
| 反证处理率 | 被召回或 rubric 指定的关键反证中，得到处理的比例 | 规则 + Judge |
| 来源质量 | 是否优先使用高可信、直接和多样来源，而非重复转述 | 元数据规则 + Judge |
| 推断边界 | 是否明确区分原卡主张、关系推演和新增判断 | Judge + 人工校准 |
| 不确定性校准 | 证据不足、冲突或适用范围有限时，措辞是否相称 | Judge + 人工校准 |

  “主张支持率”应借鉴 Ragas 的 faithfulness 思路，但不能原样照搬。DSH 的支持证据不仅是上下文文本，还包括 Card 类型、`applicable_scope`、`theory_status`、关系方向、关系 note 与来源链。评分器必须读取这些结构化信息。

### 4.3 第三层：分析价值

| 维度 | 低分表现 | 高分表现 |
|---|---|---|
| 问题贴合度 | 罗列卡片，未回答用户真正的问题 | 明确处理任务目标、约束和受众 |
| 综合能力 | 各 Card 独立摘要 | 建立有证据的因果、对照、层级或条件结构 |
| 洞见增量 | 重述常识或材料原句 | 从多张 Card 形成可解释的新连接，且标明推断性质 |
| 边界与替代解释 | 单线结论、忽略反例 | 给出适用范围、失效条件、冲突和替代路径 |
| 决策价值 | 只有概念说明 | 能帮助判断、选择、进一步验证或采取行动 |
| 信息密度与可读性 | 冗长、AI 套话、结构混乱 | 重点明确，证据和结论层级清楚 |

  这一层优先采用盲化 A/B 比较：Judge 不知道哪份来自基线或候选，A/B 顺序随机，按每个 rubric 分别给出“候选胜、平、负”和简短证据。开放式分析的绝对分可以保留用于趋势观察，但不作为唯一晋升依据。

### 4.4 第四层：Agent 过程与效率

| 指标 | 要回答的问题 |
|---|---|
| 有效读卡率 | 深读的 Card 中有多少进入了证据、反证或最终判断？ |
| 图扩展收益 | 沿关系边新增的 Card 中有多少带来新证据或改变判断？ |
| OPS 选择质量 | Operator 是否适合当前缺口，参数是否聚焦？ |
| Observation 利用率 | 新 Observation 是否实际改变 Workspace、下一步或答案？ |
| 失败恢复 | 搜索无结果、工具失败或低新颖度时，是否改选而非重复？ |
| 停止质量 | 证据充分、预算不足或继续收益低时，是否合理停止？ |
| 成本与延迟 | 提升是否需要不可接受的 token、调用次数或时间？ |
| 稳定性 | 同一配置重复运行时，硬门槛和关键结论是否稳定？ |

  过程指标用于解释结果，不能凌驾于最终可靠性和价值。例如更少的调用不是天然更好；如果额外一次冲突检查显著降低错误，它就是有效成本。

## 五、评分器组合与偏差控制

### 5.1 推荐的评分器栈

1. `ContractGrader`：检查文件、Card ID、revision、关系、权限、预算和输出格式。
2. `ClaimExtractor`：把最终答案拆成可核验主张、模型推断、建议和修辞性内容。
3. `EvidenceGrader`：逐项判断主张是否被指定 Card、关系或来源支持。
4. `CoverageGrader`：按案例 rubric 检查必要证据、反证和任务要求。
5. `PairwiseValueGrader`：盲化比较候选与基线的综合、洞见、边界和决策价值。
6. `TrajectoryGrader`：从 Episode/Workspace 计算调用收益、循环、改选和停止质量。
7. `CostGrader`：记录模型调用、token、耗时、工具次数和失败次数。
8. `HumanReview`：处理高价值案例、Judge 分歧、边界案例和定期校准样本。

  测评台可以展示一个摘要面板，但不应把以上结果压成单一不可解释总分。版本晋升至少同时满足“可靠性门槛不退化、价值胜率提升、严重回归受控、成本可接受”。

### 5.2 LLM Judge 的偏差控制

- A/B 顺序随机，并对一部分案例交换顺序复评。
- Judge 尽量与被测模型不同；不得让候选模型评价自己后直接决定晋升。
- rubric 使用具体可观察标准，避免只写“有洞见”“质量高”。
- 允许平局，不强迫区分高度相近的答案。
- 同一案例至少运行三次候选，报告均值之外还要报告方差和最差表现。
- 对 Judge 不一致、硬门槛与价值评分冲突的案例进入人工复核队列。
- 定期用专家标注集测量 Judge 与人工的一致率；一致率下降时先校准 grader，而非据此调整 TM。

## 六、评测数据集设计

### 6.1 第一批 24 个分析案例

| 类型 | 数量 | 主要能力 |
|---|---:|---|
| 事实与因果解释 | 5 | 找到关键依据，区分机制与相关性 |
| 冲突与替代解释 | 5 | 主动读取冲突、反例和适用边界 |
| 跨领域综合 | 4 | 沿关系扩展并形成有根据的新连接 |
| 判断与决策支持 | 4 | 将知识转为条件化判断或行动建议 |
| 证据不足与拒答 | 3 | 识别图谱缺口，避免强行得出结论 |
| 对抗与干扰 | 3 | 抵抗标题相似但语义无关的 Card、错误关系和噪声 |

  案例不应全部来自当前最熟悉的金融主题。可采用“金融 12、社会科学 6、跨领域 6”的初始分布，既贴近主要实践，又避免 TM 只适应一类问法。

### 6.2 案例契约

```json
{
  "case_id": "analysis-causal-001",
  "task": "用户原始问题",
  "graph_fixture": "fixtures/analysis-causal-001",
  "allowed_external_knowledge": false,
  "budgets": { "max_steps": 24, "max_reads": 12, "max_seconds": 180 },
  "required_evidence": ["card-id#semantic-anchor"],
  "counter_evidence": ["card-id#semantic-anchor"],
  "forbidden_claims": ["缺乏图内依据时不得断言的内容"],
  "value_rubric": [
    { "criterion": "解释制度层和市场层如何共同决定结果", "weight": 2 }
  ],
  "human_notes": "只供校准者查看，不传给被测 Agent"
}
```

  `required_evidence` 是“一个优秀答案至少应处理哪些证据点”，不是规定唯一措辞。对于存在多种合理结论的任务，应记录可接受的推理范围、必须承认的冲突和不可越过的证据边界，而不是写一篇唯一参考答案。

### 6.3 三类数据集

- `regression`：少量稳定案例，每次提交可运行，主要拦截明确退化。
- `development`：开发时可查看 rubric，用于定位和修复问题。
- `holdout`：题目和评分细节不进入日常提示词调试，只用于版本晋升。

  同一个知识图谱快照不得同时用于大量调参和最终宣称泛化提升。案例需要保留来源、创建时间、修订历史和失败类型标签，防止测试集逐渐变成提示词记忆集。

## 七、适合 DSH 的测评台形态

### 7.1 第一版边界

  第一版应当是 `packages/nexogenesis-eval/` 中的本地 Node 工具，直接依赖 `nexogenesis-tools` 暴露的稳定接口，而不是复制 GraphOps 或 Runtime。它只需要完成：加载案例、创建隔离快照、运行多个 variant、归一化 Episode/Workspace、执行 graders、保存实验和生成 Markdown 报告。

  推荐目录只是实施目标，落码前仍需根据当时仓库结构确认：

```text
evals/
├── cases/                 # 版本化案例契约
├── fixtures/              # 最小知识图谱快照
├── rubrics/               # 公共评分规则与人工校准规则
└── calibration/           # 专家评分样本

packages/nexogenesis-eval/
├── lib/runner/            # 基线与候选运行器
├── lib/graders/           # 硬校验、证据、价值、轨迹、成本
├── lib/report/            # 实验差异与回归报告
└── cli.js

.nexogenesis/evals/
└── experiments/           # 本地运行结果，不是知识事实源
```

  评测结果属于运行证据，不属于知识体。案例与 rubric 可以进版本库；包含真实对话、私有 Card 正文、API 响应和模型轨迹的实验结果默认不入库。

### 7.2 与现有 DSH 结构的接线

  DSH 已经具备可复用基础：

- Episode 保存可观察步骤和 Observation。
- Workspace 保存目标、证据、反证、冲突、候选动作和停止原因。
- CognitiveRun 保存 mode、skill、Thinking Model、状态和写入主权。
- Card 与关系具有结构化字段和 revision。

  测评实现前需要补齐三项稳定契约：

1. 运行开始时记录模型、提示词、TM、OPS 注册表和代码版本指纹。
2. 每次读卡记录 Card revision 与实际使用的语义锚点，而不只是 Card ID。
3. 模型调用记录统一的耗时、token、重试与错误摘要。

  这些字段应作为现有 Episode/CognitiveRun 的有限扩充，不另造第二套轨迹系统。

### 7.3 实验输出

  每次实验至少生成：

- `manifest.json`：案例、快照、variant、模型和版本指纹。
- `runs.jsonl`：每次重复运行的结果、成本和状态。
- `grades.jsonl`：各 grader 的分数、理由与证据锚点。
- `comparison.md`：面向人的基线差异报告。
- `regressions.json`：严重退化和需要人工复核的案例。

  所有评分必须能追到案例、运行、主张、Card revision 或 Episode step。不能只保留“7.8 分”而丢失评分理由。

## 八、用户界面与报告设计

  第一阶段先提供命令行和 Markdown 报告，避免在评分契约不稳定时先投入大量 UI。评分稳定后，Web 顶栏可增加“测评”入口，但它与日常思维体对话分开，防止用户把实验任务误认为正在修改知识体。

  Web 测评页建议包含五个区域：

1. 实验概览：候选、基线、模型、图谱快照、案例数、重复次数。
2. 可靠性门槛：通过率、虚构引用、无依据主张、遗漏反证和权限错误。
3. 价值比较：各维度胜/平/负、平均提升及置信区间。
4. 回归列表：按严重程度列出退化案例，可打开 A/B 答案、证据映射和 Episode。
5. 成本与稳定性：token、耗时、OPS 次数、失败率和多次运行方差。

  最有价值的交互不是排行榜，而是“为什么这个案例退化”：点击后并排查看基线与候选答案，答案中的主张可跳转到实际 Card 与语义锚点，下面显示双方检索轨迹、反证处理和 Judge 理由。

## 九、版本晋升规则

  建议先采用可解释的多条件门槛，而不是加权总分：

- 硬门槛通过率不得低于当前稳定版，且不得新增严重虚构引用。
- 在 holdout 上，分析价值的盲化胜率应显著高于负率；平局单独报告。
- 必要证据覆盖率和反证处理率不得系统性下降。
- 不得出现单一高价值任务的严重回归而被平均分掩盖。
- P95 延迟、平均 token 或 OPS 调用增长超过预设预算时，必须说明价值增量是否值得。
- 三次重复运行中，关键结论和可靠性门槛应保持稳定；一次偶然高分不能晋升。
- 自动结果通过后，仍需人工审核全部严重回归和一组随机案例。

  第一轮不预设“胜率必须达到多少”这类缺乏基线的数据。先用当前稳定版完成一次完整测量，得到波动范围，再确定发布阈值。这比从行业数字直接移植门槛更可靠。

## 十、实施顺序

### 阶段一：可复现实验与硬校验

- 定义 EvalCase、Variant、Experiment 与 Grade 契约。
- 建立 8 个小型 fixture 和 B0/B1/B3 三个运行器。
- 固化模型、TM、OPS、代码和图谱快照指纹。
- 实现 ContractGrader、成本记录和 Markdown 对比报告。
- 用故意植入的幽灵引用、错误关系和越权写入验证 grader 能拦截问题。

  验收标准：同一实验可以重跑；每份输出能追到配置、快照和 Episode；确定性错误被稳定检出。

### 阶段二：证据核验与完整基线

- 扩展到 24 个案例。
- 实现主张抽取、EvidenceGrader、CoverageGrader 和反证检查。
- 加入 B2、C 与可选 O 组。
- 对模型评分器建立专家校准集。

  验收标准：评测台能区分“没有召回证据”“召回但没使用”“使用但过度推断”三类问题。

### 阶段三：盲化价值比较与回归诊断

- 实现随机换序的 PairwiseValueGrader。
- 增加三次重复运行、方差和最差表现。
- 生成逐案例 delta、严重回归列表和成本—价值对照。
- 在 Web 增加只读的实验查看页和人工复核入口。

  验收标准：可以回答“候选是否优于稳定版、优势集中在哪类任务、代价是什么、退化发生在哪一步”。

### 阶段四：进入受控自我迭代

- 将通过评测的 TM/OPS 候选登记为可晋升版本。
- 从真实对话中抽样脱敏失败 Episode，人工审核后转为新案例。
- 保留稳定版回滚点，禁止自动评分直接修改或发布 TM/OPS。

  验收标准：反馈能形成候选与数据集，但发布仍由明确门槛和人工确认控制。

## 十一、当前不做什么

- 不训练奖励模型，也不建设通用 Agent 评测平台。
- 不把 LangSmith、Braintrust 或其他外部 SaaS 设为必需运行条件。
- 不要求唯一 OPS 轨迹或暴露模型私有思维链。
- 不用单个 LLM Judge 总分决定版本晋升。
- 不把实际知识库全量复制进公开测试集。
- 不在评分过程中修改 Card、知识图谱、TM 或 OPS。
- 不先开发复杂 Web 大屏，再补评分契约。

## 十二、与现有评测文档的关系

  《下一阶段评测方案》解决的是 Card 保真、Observation OPS、TM 约束和 Loop 治理的当前回归问题；本文进一步定义“如何比较思维体分析结果与基线”。前者应继续作为底层回归集，本文的分析测评台在其通过后运行。两者不是替代关系。

  《受控反馈与自我迭代：TM、OPS 与评测数据集设计》说明候选如何产生、接受反馈和晋升；本文则提供候选进入晋升前的实验工具、基线和评分证据。测评台完成之前，不应宣称 DSH 已具备可靠的自我改进闭环。

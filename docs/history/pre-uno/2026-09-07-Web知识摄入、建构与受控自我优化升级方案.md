# Web 知识摄入、建构与受控自我优化升级方案

> 日期：2026-09-07  
> 状态：基于近期主题编译、Web 建构与 Codex 定向建构记录形成的下一步实施建议  
> 适用范围：Nexogenesis DSH 的 Web 端知识摄入、主题编译、知识图谱建构与运行经验利用

> 使用说明（2026-09-08）：本文保留早期问题证据与改进假设。面向未来的整合方案以[统一入口方案第十一节](2026-09-07-编译建构思考统一入口与主题组织重构方案.md#十一面向-web-的完整知识工作方案)为准；当前能力仍查运行手册。下文“建构目标表单未实现”、丰富旧卡偏好、试编译卡数、固定结构降幅/抽查比例及“通过项逐项提交”等表述不作为新设计默认规则。建构面板已有实现；新建与修订按对象质量判断；抽查按现行契约与实际风险执行；有依赖的事务不能拆成任意成功子集。保存本说明不修改现行运行契约。

## 一、结论先行

当前 Web 端还不能让不熟悉项目的使用者稳定获得高质量知识体，也不能可靠完成最近由 Codex 完成的复杂定向建构。

它已经具备任务、Workspace、Episode、Harness 校验、暂停与继续等基础设施，也能完成少量局部清理；但真实运行表明，使用者仍需理解编译模式、卡片契约、关系合法性、建构计划、预算和失败原因。复杂建构又需要模型围绕每条边反复执行“读卡—比较—审查—模拟—写入”，Web 端目前缺少适合这类工作的任务入口、批量语义操作、分波执行和清晰反馈。因此，问题不能只靠换一段更强提示词、放宽 Harness 或单纯增加步数解决。

下一步应同时推进三件事：

1. **把专业流程藏到系统内部**：陌生用户只需说明质料和目标，Web 自动完成材料体检、模式选择、试编译、质量门禁与失败修复。
2. **把建构升级为可定向、可分波、可复核的连续过程**：支持从自然语言、卡片、领域或图谱节点直接发起，优先解决用户指定的问题，而不是默认进行一次全库漫游。
3. **建立受控经验回路**：运行中记住已发生的错误并避免重复；跨任务汇总 Episode 形成候选经验；只有通过回放评测和人工批准后，才升级 Skill、Thinking Model、OPS 或 Harness。运行时模型不得自行改规则或降低质量门槛。

建议先用两个真实失败案例做垂直实验，而不是立即建设完整的“自动学习平台”：

- 用 Web + DeepSeek 重放“国际周期同步”枢纽治理任务，验证定向建构能否达到 Codex 已经完成的结果等级。
- 用 Web + DeepSeek 重放本次能源技术主题编译，验证系统能否自行处理来源拆分、稀薄章节、图像尾页、关系拒绝和复核，而不产生低质量卡片。

## 二、本次判断依据

### 2.1 主题编译暴露的问题

本次“能源、技术与长期增长”主题编译最终处理了 3 本书、29 个来源文档和 123 个来源对象，形成 29 张新卡并丰富 6 张已有卡，建立 77 条主题内部关系；最终没有孤立卡，最大单一目标占比为 8.5%。结果可以验收，但过程暴露了系统尚未内化的经验：

- Perez 第 1—3 章不能因为文件名或初始分组方便就视为一个可靠来源对象，需要回到章节内容重新拆分。
- Gordon 第 17 章正文过薄，不能用形式完整掩盖证据不足。
- 图像来源第一次只检查前 160 张时遗漏尾部，需要按材料规模补做尾页复核。
- 正式关系写入仍留下 7 次拒绝：5 次缺少时间锚点，2 次关系签名不合法。这些规则并非新规则，说明错误本可在提交前被发现。
- 最终仍有 16 个“正文较薄”提醒。这里正确的做法是保留谨慎状态，而不是为了通过字数指标注水。

这说明 Harness 收紧有价值，但系统当前仍把许多本应自动完成的前置判断留给了模型临场试错。对于陌生用户，这种试错会直接表现为速度慢、反复退回和结果不可信。

### 2.2 Web 建构与 Codex 定向建构的差距

近期运行记录形成了很清楚的对照：

| 任务 | 运行结果 | 关键事实 |
|---|---|---|
| Web 建构：治理“国际周期同步”单一枢纽 | 阻塞，约 7.6 分钟 | 26 步、12 次拒绝、0 项实际修改，最终耗尽当时的步数预算 |
| Codex：同一目标 | 完成，约 50 分钟 | 处理 74 张卡、148 次关系事务；枢纽入边 98→24，单邻居叶节点 93→10，范围内无孤立卡 |
| Web 建构：全库通用诊断 | 部分完成，约 8.8 分钟 | 能清理 5 张卡，但发生 11 次拒绝，大量待办没有转化为行动 |
| Web 建构：领域归类修正 | 表面完成，实际未修改 | 发现问题，但迁移方案反复被契约拒绝，问题留在待办中 |
| Codex：另外三个定向枢纽治理 | 完成 | 分别处理 26、45、34 张卡，均显著降低单一枢纽集中并保持连通 |
| Codex：孤立节点治理 | 目标基本完成 | 85 个对象中 83 个建立有效连接，2 个明确保留独立；最后因范围外待办仍被标记为阻塞 |

Codex 的成功并不意味着当前流程高效。它依赖大量逐边操作：读两个端点、比较、检查关系案例、模拟补丁、再正式提交。最重的一次运行超过一千步。这个过程足够严谨，却不适合作为 Web + DeepSeek 的默认交互粒度。

因此目前对“我在 Web 端能很好地使用建构吗”的回答是：

- **小规模、边界明确的正文清理：部分可用。**
- **泛化的全库体检：能发现问题，但容易形成很长的待办而没有足够落实。**
- **指定图谱问题的定向建构：目前不可靠。**
- **大规模枢纽解耦、邻域重组、关系逐项裁决：尚未达到可交付状态。**

### 2.3 已实现、部分实现和未实现必须分开

| 能力 | 当前状态 | 判断 |
|---|---|---|
| CognitiveRun、Workspace、Episode | 已实现 | 能保存单次任务状态、观察与事件，是经验回路的基础 |
| HarnessGateway 校验、原子写入与收据 | 已实现 | 应继续作为不可绕过的底线 |
| 暂停、继续、任务列表与基础进度 | 已实现 | 能恢复任务，但信息仍偏向工具轨迹 |

| 建构预算提升到 600/400/100 | 当前工作树已加入 | 能减少过早耗尽，但不能消除逐边调用的成本与错误放大 |

| 跨任务经验提炼、回放、晋升与回滚 | 未实现 | Episode 有记录，但不会自动变成经过验证的执行经验 |
| 批量关系语义裁决与逐项收据 | 未实现 | 是复杂建构效率的主要缺口 |

## 三、升级目标与边界

### 3.1 面向陌生用户的目标

陌生使用者不应被要求知道以下内部概念：普通编译与主题编译的区别、source object、disposition、关系签名、时间锚点、construct plan、probe 或写入预算。

他应该只需要完成三件事：

1. 放入质料。
2. 说明自己想建立什么知识，或者接受系统建议。
3. 对少数真正涉及意义取舍的事项作决定，例如“这两本书是否应放在同一主题”“这两张卡是否表达同一命题”。

其他问题应由系统自动发现、解释并处理；无法可靠处理的质料应被隔离并给出明确原因，不能硬编译成卡片。

### 3.2 不做的事情

- 不允许 DeepSeek 或其他运行时模型自行修改 Harness、放宽校验或删除失败记录。
- 不把“通过字数、连接数、无孤立”等形式指标当成知识质量本身。
- 不根据词面相似度自动批量连边。
- 不为每份文档制造一张卡，也不为了降低孤立率把节点随意挂到大枢纽上。
- 不一次性建设抽象的自我进化平台；先让真实失败案例稳定重放成功。

## 四、面向陌生用户的知识摄入流程

建议把当前流程改为下面的用户体验：

```text
放入质料
  → 自动材料体检与主题建议
  → 生成一小段试编译
  → 自动质量审计并调整策略
  → 按主题分批执行
  → 每批写入前预检
  → 写入后复核知识覆盖与图谱结构
  → 向用户报告结果、谨慎项与未处理原因
```

### 4.1 自动材料体检

进入编译前先生成机器可用、用户可读的材料画像：

- 文件格式、语言、页数或章节数、可提取文本比例。
- 是否是扫描件，是否需要 OCR 或视觉复核。
- 目录、参考文献、图表、脚注和附录位置。
- 材料之间的主题聚类、重复版本和明显冲突。
- 适合普通编译、主题编译，还是应暂缓处理。

如果文本层缺失、章节过薄或版本重复，Web 应直接显示“为何不宜立即编译”以及建议动作，而不是把问题留到卡片写入阶段。

### 4.2 先做试编译，再扩展

长书、多书或混合主题材料默认先处理一个小切片，例如 2—3 个来源对象和 3—5 个卡片候选。试编译要验证：

- 来源边界是否正确。
- 卡片粒度是否足以独立阅读，又没有把整章堆进一张卡。
- 新建与丰富已有卡的比例是否合理。
- 关系类型和方向是否成立。
- 现有图谱中是否已经有更合适的承载位置。

试编译失败时先调整来源切分、卡片策略或主题边界，再展开全量。这正是本次实践中“先实验、逐步优化”真正应落入系统的位置。

### 4.3 写入前预检，而不是依靠正式拒绝学习

正式写入前应使用与 Harness 相同的契约进行预检，至少覆盖：

- 关系签名、方向、时间锚点和目标存在性。
- 新建卡是否与已有卡重复，是否更适合 enrich。
- 来源对象是否都有实际处置，不允许计划状态冒充完成状态。
- 卡片正文是否具有可解释内容、证据边界和来源，而不是标题回声。
- 新卡是否会形成孤立、单邻居叶节点或新的大枢纽依赖。

预检失败应返回“问题—影响—修正建议—能否自动修复”。同一个原因在同一任务中第一次出现后，剩余候选必须使用修正规则重新生成，不得继续向 Harness 提交同类错误。

### 4.4 质量验收不只看形式指标

主题编译和普通编译至少应同时检查四类质量：

| 层面 | 核心问题 |
|---|---|
| 来源覆盖 | 是否真正读到了重要章节、图表与尾页；每个来源对象是否有可核对处置 |
| 卡片质量 | 是否可独立阅读、信息充分、边界明确；是否优先丰富已有卡而非制造重复 |
| 关系质量 | 每条边是否表达真实语义；是否产生孤立、星型挂靠或非法关系 |
| 主题结构 | 是否形成多个可解释的局部中心、桥接与张力，而不是所有内容挂在一个宽泛主题卡上 |

结果页要区分“确定性校验通过”“启发式提醒”“抽样语义复核通过”“尚未验证”。不能把 `ready_with_cautions` 显示成无条件完成，也不能用空洞补写消除谨慎项。

## 五、让 Web 建构真正可用

### 5.1 先改变任务入口

当前通用“新建建构任务”不足以表达真实目标。Web 应提供三个入口：

1. **解决一个具体问题（默认推荐）**：用户用自然语言描述，例如“这个节点成了不合理的大枢纽，请重组其邻域”。
2. **全库结构体检**：只诊断并形成有优先级的候选问题，用户选择后再进入定向建构。
3. **继续上次建构**：恢复原目标、当前波次和剩余范围。

同时在图谱中增加“整理此节点邻域”“检查所选节点”“修复此断裂区域”等入口。系统把节点、选区、领域和当前筛选条件转成明确 scope，用户无需复制卡名或理解内部 ID。

启动前只显示必要选择：目标、允许修改的层面（关系、正文、领域、合并/拆分）、是否自动执行低风险修改。高级契约隐藏在展开区域。

### 5.2 建构改为分波执行

一个建构任务应持续围绕同一目标工作，但不应成为不可理解的长黑箱：

```text
确认目标与范围
  → 建立基线指标
  → 提出第一波改进计划
  → 执行 5—15 个紧密相关对象
  → 复核语义与结构变化
  → 继续下一波或调整计划
  → 达成用户目标后结束，范围外问题进入 backlog
```

每一波都应显示：检查了什么、准备改什么、已经改什么、被拒绝什么及如何修正、指标如何变化、下一步是什么。技术调用轨迹可以折叠查看，不应成为默认进度界面。

对于信任模式，可以按波次授权，不必逐边确认；手动模式允许用户在每波前查看摘要。暂停后必须从已确认收据继续，避免重复写入。

### 5.3 增加集合级关系治理能力

当前复杂建构最大的工程瓶颈不是总预算，而是操作粒度。Codex 为一条边往往需要多次工具调用，数十张卡就会膨胀为数百乃至上千步。

建议增加一个集合级关系治理操作，或在现有工具上扩展等价能力：

- 输入一个明确焦点、候选节点集合和用户目标。
- 一次读取所需端点、当前邻域和相关来源。
- 由模型逐项给出保留、删除、改向或新增的语义判断及依据。
- 服务端对每条候选边分别执行现有关系契约和模拟校验。
- 只提交通过项，每条边仍产生独立收据；失败项返回具体修复建议。
- 一个波次失败不回滚此前已经独立确认的波次，但必须保持可恢复状态。

这不是“自动批量连边”。模型仍负责语义判断，Harness 仍逐边验证；改变的只是把重复的读取、案例检查和模拟合并到一个受控工作集内。该能力应先针对“单一枢纽解耦”这一已经反复出现的真实问题做垂直实现。

### 5.4 修正完成条件与 backlog

当前建构可能已经完成用户指定目标，却因范围外待办仍存在而显示阻塞。应把完成状态拆开：

- **目标已达成**：当前 scope 的验收条件通过。
- **目标部分达成**：有明确剩余项及原因，可继续。
- **目标未达成**：核心指标没有改善或出现质量风险。
- **另有 backlog**：只作为后续建议，不能自动把已达成任务判为失败。

历史 backlog 在新任务中只能作为线索，必须先按当前图谱重验；也不能把所有旧问题一次性灌给模型。系统应按当前目标、影响范围和证据新鲜度排序，只暴露最相关的少量候选。

### 5.5 修正“探针通过”等于“语义完成”的误区

近期 Web 任务曾因为精确短语没有命中而消耗最后一次写入，尽管正文已经表达了相近含义。精确短语适合验证必须原样存在的锚点，不适合单独裁决语义完成。

后续复核应分为：

- 确定性锚点：标题、来源、ID、指定术语和禁止项，使用精确检查。
- 语义目标：观点是否补足、关系是否成立，使用全文阅读、卡片比较和抽样复核。
- 结构目标：度数、孤立、邻域集中和路径变化，使用图算法检查。

三者不可相互替代。

## 六、DeepSeek 所需的能力不是“更长提示词”

Web 端可以继续使用 DeepSeek，但必须给它更适合执行的工作环境：

- 启动时提供清晰目标、范围、允许动作和停止条件，而不是只给通用 `/construct`。
- 每一波提供压缩后的工作集、相关来源和当前图结构，不让模型自行在全库反复寻找上下文。
- 工具返回明确的 `next_actions`、可修复字段和已使用的契约版本。
- 同一失败原因只允许原样发生一次；再次提交前必须经过本地修正或预检。
- 将大任务拆成可复核波次，避免一次上下文承担整个图谱。
- 对已取得的收据、基线和用户决定进行恢复，不能依赖聊天上下文记忆。

是否“DeepSeek 足够”只能由真实 Web 回放证明。单元测试、Codex 成功或预算变大都不能替代这个证据。如果在上述支撑完善后 DeepSeek 仍不能稳定完成特定语义裁决，应明确标注能力边界或把任务缩小，而不是静默降低 Harness 标准。

## 七、受控自我优化：从记住错误到批准升级

项目已经拥有运行记忆，但还没有程序化经验。下一步可以建立四层受控回路：

### 7.1 任务内纠错记忆

Workspace 记录本轮已经出现的 `reason_code`、失败输入的结构特征、有效修法和契约版本。第一次失败后，后续同类候选自动使用修法预检；原样重试直接被本地阻止。

这层应最先实现，因为它能立即减少反复退回，不涉及跨任务修改系统规则。

### 7.2 跨任务经验汇总

从 Episode 中按任务类型、材料画像、工具和契约版本统计：

- 高频失败及首次发生位置。
- 成功修复方式。
- 哪些检查本可提前完成。
- 哪些预算耗尽来自真实规模，哪些来自无效重复。
- 结果是否通过写后复核，用户是否继续返工或取消。

输出的是“候选执行经验”，不是知识卡，也不是直接生效的新规则。

### 7.3 回放评测

候选经验必须在固定案例上比较旧版本和新版本，至少观察：完成质量、拒绝次数、重复错误、首个有效改动时间、总调用量、恢复正确性和语义抽检结果。

本轮已经积累了适合做回放集的真实案例：主题来源切分、稀薄章节、图像尾页、时间关系、领域迁移、精确探针误判、单一枢纽解耦和孤立节点治理。

### 7.4 人工批准后晋升

只有回放通过的候选，才由维护者批准进入版本化的 Skill、Thinking Model、OPS 或 Harness。每次晋升必须记录：解决了什么真实摩擦、适用范围、评测结果、版本和撤回方式。

Harness 的硬约束只因契约本身错误而修改，不能因为模型经常失败就放宽。这样既有自我优化能力，又不会让系统为了少报错而学会规避质量要求。

## 八、建议实施顺序

### P0：先消除重复失败并建立真实基线

范围有限，目标是让后续试验可信。

- 统一记录 Harness 拒绝、工具失败、预算耗尽、分页遗漏、用户取消和修复结果。
- 在 Workspace 增加任务内失败防重试与预检提示。
- 修正语义探针和精确短语探针的职责混淆。
- 修正 scope 完成与全局 backlog 的状态关系。
- 固化两个回放样本及其现有指标。

撤回方式：上述能力只增加观察、预检和状态判断，不改变卡片语义；可按功能开关退回旧行为。

### P1：完成定向建构垂直切片

- 增加 Web 建构目标表单和图谱节点入口。
- 实现单一枢纽邻域的集合级读取、语义裁决、模拟与逐边收据。
- 实现分波进度与波次复核。
- 用 Web + DeepSeek 重放“国际周期同步”任务。

判断标准：不是“任务没有报错”，而是枢纽集中明显下降、邻居之间形成有依据的关系、范围内不新增孤立或幽灵链接，并能安全暂停和继续。

### P2：完成自适应摄入垂直切片

- 增加材料画像、主题建议和处理模式推荐。
- 长材料默认先试编译，审计通过后再扩展。
- 将来源覆盖、第二遍复核、实际处置、卡片/图谱质量集中到一个结果页。
- 用 Web + DeepSeek 重放能源技术主题编译。

判断标准：系统能自行识别并正确处理本次出现的四类异常，不再把明显可预检的关系错误提交给 Harness，也不为消除警告制造空洞内容。

### P3：建立跨任务经验晋升

- 从 Episode 生成候选经验报告。
- 建立版本化回放集和对照执行。
- 提供人工审核、批准、回滚和效果追踪。
- 只有当某类经验在多个真实任务中稳定有效时，才提升为默认策略。

这一阶段之前，不应宣称项目已经具备“自动学习”。

## 九、验收指标

### 9.1 陌生用户可用性

- 用户无需输入内部命令或理解卡片/关系契约即可开始任务。
- 需要用户决定时，界面说明问题、影响和推荐选择，而不是只返回 reason code。
- 运行中至少每个波次显示一次有意义进展；技术轨迹默认折叠。
- 首个有效改动应尽快出现，长任务可以安全暂停、继续和取消。

### 9.2 摄入质量

- 所有来源对象都有实际处置和可追溯卡片收据，计划项不能冒充完成项。
- 扫描件、无文本层或证据不足材料不会直接生成正式卡片。
- 新建卡、丰富已有卡和跳过都有语义理由。
- 不新增幽灵链接和非法关系；除明确独立对象外不新增孤立卡。
- 同一 `reason_code` 的原样重复在单次运行中为 0。
- 抽样检查卡片能回到对应来源，且没有用模板话术填充信息空缺。

### 9.3 建构质量

- Web + DeepSeek 能完成至少一个此前 Web 阻塞、Codex 成功的定向枢纽案例。
- 单邻居叶节点或单一枢纽集中度相对基线显著下降，建议首轮以至少下降 60% 为目标，同时保持范围内连通。
- 所有新增或改向关系均有端点证据、语义理由和独立 Harness 收据。
- 重复契约错误为 0；被拒绝项要么自动修正，要么明确留待处理。
- 用户目标达成后可以正常完成，范围外 backlog 不再把任务错误标成失败。
- 随机抽查不少于变更关系的 10%，确认不是靠词面相似或大枢纽挂靠获得结构指标。

### 9.4 经验升级质量

- 每条候选经验都能追溯到真实 Episode 和契约版本。
- 晋升前有旧版/新版回放对照，不只看成功率，也看语义质量和成本。
- 升级可按版本撤回，不改写历史运行记录。
- 模型不能自行将候选经验提升为硬规则。

## 十、下一步最小实验

建议把“国际周期同步”定向建构作为第一项开发实验。它有同一目标下的 Web 失败记录和 Codex 成功结果，最适合回答关键问题：在不降低 Harness 标准的情况下，通过更好的任务入口、集合级关系治理、任务内纠错记忆和分波复核，Web + DeepSeek 能否用明显更少的无效步骤取得相近的图谱改善。

实验只实现这一条完整链路，不先扩展到所有建构类型。若它通过，再把同一机制推广到孤立节点、领域归类、桥接和正文重写。若它失败，则可根据 Episode 判断瓶颈究竟在模型语义判断、工具粒度、上下文组织还是契约设计，而不是继续用增大预算掩盖问题。

完成该实验后，再重放能源技术主题编译，验证同一套“材料画像—试编译—预检—分批执行—写后审计—经验候选”机制能否同时改善知识摄入。两个案例都通过后，项目才有充分依据进入跨任务经验晋升阶段。

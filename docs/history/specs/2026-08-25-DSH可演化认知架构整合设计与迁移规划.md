## 0. 决策摘要

  NEXOGENESIS-DSH 后续继续坚持一个单体系：Web 是用户入口，DSH 原生 Agent Loop 是唯一模型—工具循环，`talk / compile / digest / construct / emerge / assess / refine / report` 均由同一套 Agent preset、Skill 系统、工具系统和权限系统执行。不恢复 ORG 的 Python Agent Runtime，也不建立 Web Agent 与 Code Agent 两套执行平面。

  单体系不等于所有工作挤在同一个物理会话中。普通对话、编译、消化和建构可以拥有各自的 DSH session 与 `CognitiveRun`，由同一个项目协调器管理；它们共享同一套 persona、Skill、Thinking Model、GraphOps 和 Harness。这样才能在长任务运行时继续对话，并只在重叠写入对象上发生局部协调。

  目标架构不是“DSH 加很多 Skill”，而是：

```text
DSH 提供可持续运行的 Agent Loop
Skill 定义任务目标、边界与完成语义
Thinking Model 组织思考方式
Workspace 保存显式认知状态
Policy 在边界内帮助选择下一步
GraphOps / DomainOps 提供原子认知动作
Harness 保证权限、契约、事务、revision 与恢复
Episode + Evaluation 形成可复盘、可比较的学习材料
Learning Lab 离线产生策略候选，经回放与人工批准后晋升
```

  ORG 中已经成熟的来源覆盖、表图保留、重复图复用、断点账本、消化失败改选、Semantic Patch 编译、关系裁决、原子写入与自然语言进度应迁移。ORG 中固定波次工作流、重复的模型客户端、Python 自研 Agent Loop、全局单任务锁和把大段上下文反复灌给模型的控制流不迁移。

## 1. 对本轮讨论方案的批判性审核

### 1.1 合理且应保留的判断

  本轮方案正确识别了未来认知系统的核心对象：Skill、Thinking Model、Workspace、Policy、GraphOp、Observation、Episode、Evaluation 与 Learning。它也正确坚持了三个关键原则：GraphOps 应少而稳定；Workspace 不应写成知识卡片；学习应先记录与评价，再离线产生候选，不能让运行中的 Agent 静默改写自己。

  “建构 Skill 可以调用多个 Thinking Model，而一个 Thinking Model 可以跨建构、研判和报告复用”是合理的。它避免把 `/construct` 误当成一条固定思维程序，也为未来策略比较和程序组合保留了空间。

### 1.2 必须修正的层级问题

| 原草案倾向 | 风险 | 本文修正 |
|---|---|---|
| 用户任务必然先映射到一个显式 Skill | 简单对话也可能被过度路由；Skill 变成菜单 | `nexo-talk` 是默认能力；只有出现明确任务边界时才加载专门 Skill |
| Policy 是 Workspace 后面的一个单独模块 | 权限、预算、启发式与模型语义选择混成黑箱 | 拆为 Hard Policy、Runtime Policy、Semantic Policy、Learned Hint 四层 |
| GraphOp 声明“可用于哪些 Thinking Model” | Operator 与当前策略双向耦合，难复用和演化 | Operator 只声明 capability tags、前置条件、效果与风险；Thinking Model 依能力选择它 |
| 所有 Workspace 使用同一张大表 | 字段不断膨胀，编译与建构互相污染 | 使用稳定 Core Workspace + mode-specific extension |
| Episode 保存完整思考过程 | 成本、隐私与不可控隐含推理风险 | 只保存结构化 State—Action—Observation、简短行动理由和证据锚点，不保存隐藏思维链 |
| Evaluation 可以直接形成一个总分 | 奖励投机、偏好污染事实、无法解释退步 | 使用多维 rubric、成本维度、用户反馈和任务特定指标；总分仅可作为可选视图 |
| 逻辑模块立即拆成多个 npm package | 迁移初期接口仍在变化，维护成本过高 | 先在现有包内建立清晰目录和接口；协议稳定后再物理拆包 |
| 单体系意味着一个会话承载所有任务 | 长任务会阻塞对话，也无法隔离预算和恢复 | 同一 Agent 系统下允许多个 task session / CognitiveRun |

### 1.3 对“学习”的限定

  本项目近期所说的学习，是案例驱动的外部认知策略优化，不是训练基础模型权重，也不是让 Agent 在一次会话中自改 Persona。学习至少分为三种速度：

| 速度 | 自动化程度 | 允许改变什么 |
|---|---|---|
| 快：每次运行 | 自动记录 | Episode、失败分类、用户反馈、成本和观察轨迹 |
| 中：一批同类案例 | 自动提出候选，人工批准晋升 | Thinking Model 版本、路由偏置、停止条件、上下文预算 |
| 慢：跨任务长期证据 | 必须专门评审 | GraphOps 契约、ontology、记忆结构、长期程序性记忆目录 |

  任何学习候选都不能直接改写正在运行的 Skill、Thinking Model、GraphOp 或知识体。晋升必须有旧版本、候选版本、案例集、隐藏测试、对比结果和撤回点。

## 2. 当前 DSH 基线与真实缺口

### 2.1 已经成立、必须保留的 Agent 能力

| DSH 能力 | 当前落点 | 后续处理 |
|---|---|---|
| 原生多步工具循环 | `session.prompt` 与 DSH agent-loop | 保留为唯一循环所有者 |
| JSON Schema 工具调用 | `nexogenesis-tools` | 扩展统一 Observation / Receipt，不退回文本协议 |
| Skill 按需加载 | `.agent/skills/` + `dsh-skill-filesystem` | 保留，重写 Skill 语义但不另建路由器 |
| 会话与事件 | DSH session/event + web-host SSE 桥 | 保留，增加 CognitiveRun 事件投影 |
| compaction、goal、ask-user、subagent | `presets/nexogenesis/agent.cordis.yml` | 保留；subagent 只在有明确并行收益时使用 |
| Web 兼容层 | `nexogenesis-web-host` | 保留 API 外壳，逐步消除它对“固定管线”的业务拥有权 |
| GraphOps 第一批只读能力 | `graph_search / graph_walk / graph_members / graph_analogize / graph_note` | 纳入 Operator Registry，补状态、预算和结构化回执 |

### 2.2 当前尚未形成的能力

- 没有持久、显式、任务级的 Cognitive Workspace；对话历史与进程内 `seenIds` 被当成了认知状态。
- 没有统一 CognitiveRun；DSH session、pipeline job、用户对话和知识任务之间缺少稳定映射。
- Skill 仍以自然语言 workflow 为主，部分 Skill 会把 Agent 再引向旧 Python 固定管线。
- GraphOps 是一组工具定义，还不是带版本、前置条件、成本、风险、观察契约和回执的 Operator Registry。
- `propose_write → Web confirm` 后，确认或拒绝结果不会自动回到原任务 session；Agent Loop 在人类决策点断开。
- DSH 的卡片确认路径当前通过 JavaScript `commitCard` 直接落盘，与 `AGENTS.md` 规定的统一 `write --batch` 入口不一致。
- 编译只有基础 Inbox/Buffer 工具，没有来源覆盖、表图证据、重复图复用、来源归档和材料级恢复账本。
- 消化虽已移植 enrich 段落补丁，但没有完整 Semantic Patch 编译、关系 disposition、贡献账本、失败改选和 Buffer 结算闭环。
- 没有 Episode、版本化 Thinking Model、Evaluation、案例回放和策略晋升机制。

## 3. 目标架构

### 3.1 总体结构

```text
Nexogenesis Web
  ├─ 普通对话
  ├─ /compile /digest /construct 等任务入口
  ├─ Steering 与 DecisionRequest
  └─ 自然语言状态 + 折叠技术证据
                 │
                 ▼
nexogenesis-web-host
  ├─ API / SSE 兼容
  ├─ CognitiveRun 投影
  └─ 用户决定 → 原 DSH task session
                 │
                 ▼
DSH Agent Runtime（唯一 Agent Loop）
  ├─ session / prompt / tool calls / compaction
  ├─ skill loader / goal / ask-user / subagent
  └─ Cognitive Runtime Middleware
       ├─ RunCoordinator
       ├─ WorkspaceStore
       ├─ ThinkingModelRegistry
       ├─ PolicyResolver
       ├─ OperatorRegistry
       ├─ EpisodeRecorder
       └─ EvaluationService
                 │
        ┌────────┴────────┐
        ▼                 ▼
GraphOps / DomainOps   Harness Bridge
只读、probe、模拟       preflight / receipt / revision
与候选提案             write --batch / Buffer gateway
        │                 │
        └────────┬────────┘
                 ▼
Markdown 知识体 + 可重建索引 + 运行态认知记录
```

### 3.2 单体系与多任务

  同一项目只有一个 Agent preset 和一套能力系统，但可以有多个 DSH session：

```text
普通对话 session ─────────────── 可持续接收用户消息
compile task session ── CognitiveRun C1 ── 独立预算与 checkpoint
digest task session  ── CognitiveRun D1 ── 冻结本轮 Buffer scope
construct task session ─ CognitiveRun K1 ── 独立 Workspace 与写范围
```

  `RunCoordinator` 不替 Agent 做语义决策，只负责启动、暂停、取消、恢复、状态聚合和资源冲突。写入锁只覆盖短事务临界区；模型调用、只读工具和普通聊天不能被全局锁住。

## 4. 核心对象与契约

### 4.1 CognitiveRun

```ts
interface CognitiveRun {
  run_id: string;
  project_id: string;
  session_id: string;
  skill_id: string;
  thinking_model_ids: string[];
  status: "created" | "running" | "awaiting_user" | "paused" |
          "completed" | "failed" | "cancelled";
  workspace_version: number;
  intent_revision: number;
  authorization_revision: number;
  created_at: string;
  updated_at: string;
}
```

  DSH session 是对话与工具执行载体，CognitiveRun 是知识任务状态。二者不能合并为同一个概念：一个 session 可以承接连续 Episode，一个 Run 也必须能在会话重启后根据 checkpoint 恢复。

### 4.2 Cognitive Workspace

  所有模式共享一个小而稳定的核心：

```ts
interface CoreWorkspace {
  goal: string;
  scope: ScopeRef[];
  user_directives: string[];
  hypotheses: Hypothesis[];
  evidence: EvidenceRef[];
  counter_evidence: EvidenceRef[];
  open_questions: OpenQuestion[];
  conflicts: ConflictRef[];
  candidate_actions: ActionCandidate[];
  observed_entities: EntityRevisionRef[];
  deferred_items: DeferredItem[];
  budget: CognitiveBudget;
  stop_reason?: string;
}
```

  每个 Skill 只添加自己的扩展，不得把模式字段塞回 Core：

| Skill | Workspace extension |
|---|---|
| Compile | `source_scope`、`source_agenda`、`semantic_inventory`、`coverage_ledger`、`artifact_ledger`、`committed_buffers` |
| Digest | `buffer_scope`、`contribution_ledger`、`candidate_cards`、`assimilation_hypotheses`、`semantic_patches`、`commit_groups` |
| Construct | `graph_scope`、`structure_signals`、`agenda`、`mutation_candidates`、`impact_sets`、`structure_debts` |
| Assess / Report | `questions`、`lenses`、`argument_map`、`uncertainties`、`output_contract` |

### 4.3 Skill

  Skill 是任务适配器，不是固定 pipeline，也不是所有认知知识的容器。每个 Skill 应声明：

- 任务目标与明确非目标；
- 默认触发语义和显式命令；
- Workspace extension；
- 需要的 capability tags；
- 允许的读取、probe、shadow、写入权限；
- 可选 Thinking Model；
- 完成、defer、暂停和请求用户的条件；
- 面向用户的状态投影规则。

  Skill 不应写“第一步必须调用 A，第二步必须调用 B，失败三次结束”一类僵硬脚本。真正不可变的顺序由 Harness 前置条件保证；语义上的下一步由 Agent 根据 Workspace 与 Observation 判断。

### 4.4 Thinking Model

  Thinking Model 是可版本化的程序性记忆单元。早期使用声明式 YAML + Markdown 说明，不立即设计通用 DSL：

```yaml
id: competing-explanations
version: 0.1.0
purpose: 比较多个解释，避免过早收敛
applicable_when:
  - workspace.hypotheses >= 2
requires_capabilities:
  - evidence.read
  - counterevidence.search
  - graph.argument_walk
preferred_observations:
  - support_balance
  - boundary_difference
stop_conditions:
  - decisive_evidence_found
  - evidence_budget_exhausted
evaluation_dimensions:
  - counterargument_coverage
  - boundary_awareness
```

  Thinking Model 不直接拥有文件写权限，也不绑定具体工具名。它请求能力，Operator Registry 在当前项目、权限和预算下解析为可用 GraphOp 或 DomainOp。

### 4.5 Policy 的四层结构

| 层 | 职责 | 是否可学习 |
|---|---|---|
| Hard Policy | 宪法、写入权限、路径、ontology、revision、预算上限 | 不由案例自动修改 |
| Runtime Policy | 并发、重试退避、checkpoint、上下文裁剪、工具调用上限 | 可配置，修改须回归测试 |
| Semantic Policy | LLM 根据 Workspace 选择 Thinking Model、读取与下一动作 | 每轮动态判断 |
| Learned Hint | 基于历史案例形成的候选偏置、停止建议、模式选择建议 | 离线评测、人工晋升 |

  Learned Hint 只能影响候选排序，不能越过 Hard Policy，也不能直接生成授权。

### 4.6 Operator Registry

```ts
interface OperatorDescriptor {
  name: string;
  version: string;
  capabilities: string[];
  mode: "read" | "probe" | "simulate" | "propose" | "commit";
  preconditions_schema: JsonSchema;
  input_schema: JsonSchema;
  observation_schema: JsonSchema;
  estimated_cost: CostProfile;
  risk_class: "none" | "low" | "medium" | "high";
  idempotency: "pure" | "keyed" | "non_idempotent";
}
```

  当前 `graph_search / graph_walk / graph_members / graph_analogize / graph_note` 继续保留工具名，先通过注册描述符升级。新增工具必须解决反复出现的真实摩擦，并优先补足以下能力：

- `inspect_domain_members`；
- `simulate_split_domain`；
- `reassign_members`；
- `propose_domain_retirement`；
- `inspect_argument_support`；
- `inspect_causal_claim`；
- `compare_candidate_cards`；
- `audit_source_coverage`。

  `rewrite_node` 只允许修改标题和正文；领域归属、关系、来源和生命周期必须使用专用 Op。工具说明、JSON Schema、Harness 校验和正例必须由同一契约源生成，禁止再次出现示例与实际签名矛盾。

### 4.7 Observation 与 Harness Receipt

```ts
interface ToolObservation {
  observation_id: string;
  run_id: string;
  operator: string;
  status: "ok" | "partial" | "rejected" | "failed" | "no_progress";
  summary: string;
  evidence_refs: EvidenceRef[];
  affected_scope: ScopeRef[];
  new_information: boolean;
  alternatives?: ActionAlternative[];
  technical_detail_ref?: string;
}
```

  Harness Receipt 是 Observation 的严格子类型，必须包含原因码和可行动替代项：

```ts
interface HarnessReceipt extends ToolObservation {
  proposal_id: string;
  reason_code: string;
  violations: ContractViolation[];
  legal_alternatives: ActionAlternative[];
  retry_same_payload: false;
}
```

  拒绝后回到同一 Agent Loop。模型下一轮只接收“拒绝原因、相关字段、两个以内合法替代动作和必要证据引用”，不得重新注入整批正文与全部失败历史。

### 4.8 Episode

```ts
interface Episode {
  episode_id: string;
  run_id: string;
  task_signature: string;
  model_fingerprint: string;
  skill_version: string;
  thinking_model_versions: string[];
  initial_state: WorkspaceSummary;
  trajectory: EpisodeStep[];
  outcome: OutcomeSummary;
  user_feedback?: UserFeedback;
  evaluation_refs: string[];
}
```

  `EpisodeStep` 记录状态摘要、动作、Observation、简短行动理由、证据锚点、成本和停止判断。不得记录或要求模型输出隐藏思维链。大体量工具结果只保存内容哈希、路径和截断摘要；保留策略必须可配置。

### 4.9 Evaluation 与 Learning Candidate

  Evaluation 至少区分四类来源：确定性 Harness 指标、任务特定行为指标、用户反馈、独立评审模型或人工 rubric。不同来源不能伪装成同一种客观事实。

```ts
interface EvaluationRecord {
  evaluation_id: string;
  episode_id: string;
  evaluator_type: "deterministic" | "user" | "rubric_model" | "human_review";
  rubric_version: string;
  dimensions: Record<string, number | string | boolean>;
  evidence_refs: string[];
  limitations: string[];
}

interface LearningCandidate {
  candidate_id: string;
  target_type: "thinking_model" | "runtime_policy" | "routing_hint";
  base_version: string;
  proposed_patch: unknown;
  derived_from_episodes: string[];
  replay_results: ReplayComparison[];
  status: "draft" | "testing" | "rejected" | "approved" | "promoted";
  rollback_ref: string;
}
```

## 5. 状态、记忆与事实源边界

| 内容 | 初期存储 | 权威性质 | 删除影响 |
|---|---|---|---|
| Card、Buffer、Profile、来源 | 既有 Markdown 目录 | 长期语义事实 | 不可作为普通缓存删除 |
| Workspace checkpoint | `.nexogenesis/cognition/runs/<run_id>/` | 运行状态 | 可中止恢复能力，不改变知识事实 |
| Episode 与 Evaluation | `.nexogenesis/cognition/episodes/` | 派生经验记录 | 初期可清理；删除会丢失学习材料 |
| Thinking Model 基线 | `schemes/default/thinking-models/` | 随产品版本发布的程序性基线 | 由 Git 版本管理 |
| 项目级候选策略 | `.nexogenesis/cognition/candidates/` | 未批准候选 | 可删除、不可自动生效 |
| 已晋升项目策略 | 初期使用经批准的项目 overlay | 程序性资产 | 必须有版本与撤回点 |
| 图、向量与媒体索引 | `.nexogenesis/indexes/` 等可重建目录 | 派生索引 | 可重建 |

  Horizon 1 不新增长期语义目录。只有 Episode 和 Thinking Model 在真实使用中证明值得跨模型、跨时期继承后，才单独提出“程序性记忆事实源”的宪法修订；不能在本规划中偷渡一个新的长期目录。

## 6. ORG 成熟能力迁移地图

### 6.1 应优先迁移的确定性能力

| ORG 能力 | 来源 | DSH 目标形态 | 迁移策略 |
|---|---|---|---|
| Semantic Inventory + Coverage Ledger | `ingest/compile_ledger.py` | `inspect_source_map`、`audit_source_coverage` | 保留数据契约与测试；改为 Agent 可按需调用的工具 |
| 表格、图、图题和注释保留 | `ingest/artifacts.py` | `inspect_artifact`、Buffer preflight | 先由 Python Harness Bridge 复用，避免 JS 重写漂移 |
| 重复图感知哈希与多位置注明 | `ingest/figure_reuse.py` | `detect_figure_reuse`、`commit_artifact_reference` | 保留同源边界、阈值、缓存和回滚测试 |
| 文档提取、附属页过滤、结构信号 | `docx_extractor.py`、`pdf_extractor.py`、`paratext.py`、`structure_signals.py` | Source Adapter 工具 | 作为确定性预处理，不放入 Skill 提示词 |
| 材料级清单、来源指纹和断点 | `compile_planner.py`、`compile_service.py`、checkpoint/run contracts | Compile Workspace + Source Ledger | 迁移状态语义，不迁移波次调度循环 |
| 高价值材料定向复核与无进展停止 | `application/workflows/compile.py` | fidelity/repair receipt + Runtime Policy | 把错误指纹和停止条件迁入回执协议 |
| enrich 段落补丁 | `card_overlay.py` | 现有 DSH enrich 合并器 | 以 ORG 测试补齐 DSH 已移植能力，消除双实现 |
| Semantic Patch 编译 | `ingest/semantic_patch.py` | `compile_semantic_patch` | 模型提交意图；Harness 编译事务、关系 disposition 与 deferred |
| 关系签名、本体、来源范围校验 | `relation_semantics.py`、`transaction_gate.py`、写入契约 | Harness Bridge preflight | 作为统一契约源，工具示例从契约生成 |
| 消化失败后排除并改选 | `application/workflows/digest.py` | Contribution Ledger + Agent Observation | 迁移 skip/deferred 状态与行为测试，不复制 `while wave` |
| 原子写入、revision、幂等与写后复核 | `write --batch`、run contracts | 唯一 Commit Gateway | DSH JS 只做代理，不再自行实现第二套语义写入 |
| 选材、总览、暂停恢复和自然语言进度 | ORG Web 组件与 pipeline 状态 | DSH CognitiveRun UI | 迁移信息结构和体验，不迁移全局 `pipelineBusy` |

### 6.2 必须改造成 Agent 工具循环的能力

| ORG 当前形态 | 改造原则 |
|---|---|
| CompileWorkflow 遍历阅读窗 | Agent 读取 SourceAgenda，自主回读、前瞻、扩大上下文、形成 Buffer 或 defer |
| DigestWorkflow 按波路由与提案 | Agent 按贡献选择候选卡，比较、改搜、形成 Semantic Patch、拆 CommitGroup |
| Construct 内部单 JSON action 循环 | DSH 原生多工具循环；一次可并行只读，Mutation Gate 一次只接一个微小提案 |
| 固定次数 repair | Harness 返回结构化缺口；Agent 决定定向修复、换方向或停止；Runtime Policy 防止同错空转 |
| pipeline 进度字符串 | CognitiveRun 事件 → Status Projector → 用户自然语言状态 |

### 6.3 禁止迁移的部分

- ORG 的 Python LLM 客户端、DSML 文本工具协议与自研 Agent Loop；
- 让 Python Workflow 拥有模型下一步选择权的外层循环；
- 固定“预览—生成—检查—apply”的 Skill 剧本；
- 每轮重新注入整批正文、完整失败动作和全部历史；
- 全局单任务 `pipelineBusy`；
- 通过窗口数、波次、上下文字数冒充认知进度；
- 绕过 DSH session/event/compaction/ask-user 另建平行会话系统；
- 在 JavaScript 和 Python 中长期维护两套卡片、关系和写入校验器。

## 7. Harness Bridge 与唯一写入权威

### 7.1 近期决策

  实施审计发现，当前 DSH 仓并不包含可独立运行的 ORG Python 写入包，宿主环境也没有可用 Python 解释器。继续把 Python CLI 写成唯一入口会让 DSH 在架构图上统一、运行时却依赖仓外隐式环境。因此 P0 经用户本轮授权作如下修订：保留“唯一写入权威”不变，将其实现为 DSH 内部 `HarnessGateway`；ORG Python Harness 作为语义契约、算法和回归样例的迁移来源，而不是 DSH 的运行时硬依赖。

  Card、Profile、关系、生命周期与 Buffer 等写入必须进入 `HarnessGateway`。该 Gateway 统一执行预检、关系签名、领域引用、修订基线、批次提交/回滚、Journal 和结构化 Receipt；`cards.js::commitCard` 只能作为 Gateway 内部的低层文件原语，Web handler、Skill 和模型工具不得直接调用。

  Buffer 写入由同一 Gateway 的 `commitBuffer` 入口处理；消化结算写入 Contribution Ledger，只有确认提交或显式 skip 的 Buffer 才能结算。`AGENTS.md` 已在 2026-08-25 本轮开发授权下同步修订，不再保留两套并行写入真相。

### 7.2 决策与确认回流

```text
Agent 提出 MutationProposal / SemanticPatch
  → Harness preflight
  → low-risk receipt 或 DecisionRequest
  → Web 显示自然语言影响摘要
  → 用户确认 / 拒绝 / 修改范围 / 继续观察
  → 决策作为 ToolObservation 发回原 task session
  → Agent 更新 Workspace 并继续，而不是结束整个任务
```

  用户确认只授权该 proposal、scope 与 revision。用户 Steering 改变目标、写范围或执行模式时，旧授权立即失效。

## 8. 上下文与防空转设计

  每轮默认只进入以下内容：任务目标、Workspace 摘要、索引级候选、最近 Observation、当前 Thinking Model 约束和剩余预算。正文必须通过 `read_card`、`read_source_slice` 等工具按需读取。

  初期建议硬边界：

| 项 | 建议值 | 说明 |
|---|---:|---|
| 每轮系统注入的项目上下文 | 12–16k 中文字符 | 不含模型历史压缩摘要 |
| 单次全文精读 | 1–2 张卡或一个有限来源片段 | 多读必须有新问题或新假设 |
| Harness 拒绝回流 | 原因 + 相关字段 + ≤2 个合法替代动作 | 不回灌整批正文 |
| 连续无新信息 | 2 次 | 强制换动作、defer、问用户或停止当前焦点 |
| 单次 Mutation Gate | 1 个语义层面的微操作 | 多个微操作组成一次任务，不组成一个巨型事务 |

  compaction 只负责压缩会话历史，不能替代 Workspace。Workspace 由结构化状态维护，compaction 后仍必须能恢复目标、证据、冲突、候选和停止原因。

## 9. Skill 与 Thinking Model 的目标形态

### 9.1 Skill 组合

| Skill | 主目标 | 典型 Thinking Model | 主要写权限 |
|---|---|---|---|
| `nexo-talk` | 基于知识体讨论与分析 | 竞争解释、边界检查、类比探索 | 默认无 |
| `nexo-compile` | 理解来源并形成可追溯 Buffer | 语义覆盖、忠实度审查、表图证据审查 | Buffer Gateway |
| `nexo-digest` | 把贡献同化到最合适知识对象 | 候选比较、重复判别、关系意图审查 | Semantic Patch |
| `nexo-construct` | 主动改善局部图结构并蕴思 | 领域过载、冲突辨析、桥接诊断、论证检查 | Mutation Proposal |
| `nexo-emerge` | 将对话中的高价值内容形成候选 | 可复用性检查、归因审查 | 用户确认后的 Semantic Patch |
| `nexo-assess` | 多透镜研判 | 竞争解释、反论证、因果审查 | 默认无 |
| `nexo-refine` | 修订已有知识对象 | 证据忠实度、边界检查、信念修订 | 定向 Semantic Patch |
| `nexo-report` | 形成可追溯产物 | 论证组织、证据覆盖、受众适配 | OutBox，知识写入另行授权 |

### 9.2 Persona 应只保留什么

- 系统身份与服务对象；
- Markdown 与用户主权；
- 来源、归因和不可捏造原则；
- 统一 Harness、授权和写入纪律；
- 工具结果是观察，不是绝对事实；
- 默认使用中文和面向用户的表达边界。

  GraphOps 的具体使用顺序、精读张数、停止规则、冲突处理方法和领域诊断策略应迁入 Thinking Model 或 Runtime Policy，不继续堆积在总 Persona。

## 10. 前端与用户体验

  按钮保留，但只负责创建或聚焦对应 CognitiveRun，并向 task session 发送 `/compile`、`/digest`、`/construct` 等明确意图。按钮不拥有业务流程。

  主界面固定回答四件事：

1. 正在关注什么；
2. 刚发现了什么；
3. 下一步准备验证或操作什么；
4. 是否需要用户决定。

  技术证据层可折叠展示 tool、schema、run id、路径、原始 Receipt 和事件轨迹。界面不能显示或声称展示模型隐藏思维过程，只显示系统可审计的行动理由与观察摘要。

  任务结束必须呈现：

- 本次改变；
- 本次未改变及原因；
- 已留下的待办、结构债或待复核项；
- 是否存在需要继续的 Episode；
- 用户可提供的结果反馈。

## 11. 实施阶段

### P0：冻结基线与统一权威

**目标：** 在继续扩展前消除双写入权威和契约漂移。

- 为 DSH 当前 GraphOps、卡片解析、enrich、proposal/confirm、chat stream 建立基线测试；
- 引入 Harness Bridge，卡片语义提交改走 ORG `write --batch`；
- 生成式工具示例、参数 Schema 与 Harness 校验使用同一契约源；
- 明确 Buffer Gateway 与 `AGENTS.md` 写入入口的关系；
- 保留现有 DSH loop、skill loader、events、compaction、goal 与 ask-user。

**验收：** 同一合法/非法写入在 DSH 工具层与 Python Harness 得到一致结果；不存在 JS 成功而 Python 契约拒绝的分叉；现有对话和 GraphOps 冒烟不退化。

### P1：CognitiveRun、Workspace、Observation 与恢复

**目标：** 让 DSH Loop 第一次拥有可恢复的显式认知状态。

- 实现 RunCoordinator、CoreWorkspace、mode extension 和 checkpoint；
- 建立统一 ToolObservation / HarnessReceipt；
- 用户确认、拒绝和自由输入回到原 task session；
- 建立 Episode Recorder，但暂不做自动策略更新；
- 普通聊天与一个长任务可以并存。

**验收：** 一个 construct 测试任务能完成 `read → compare → rejected receipt → alternate read → proposal → confirm receipt → post-write read`，中途重启后从同一 Workspace 恢复。

### P2：Operator Registry 与 Construct 纵向样板

**目标：** 用建构证明 DSH 原生循环确实取代固定管线。

- 把现有 GraphOps 纳入 Registry；
- 增加领域专用只读、模拟和提案 Op；
- `nexo-construct` 从 Python CLI workflow 改为任务边界 + Thinking Model 组合；
- 单次 Harness 只接一个层面的微操作；
- 连续微操作形成一个 CognitiveRun，写后重新观察。

**验收：** 非法领域关系不终止任务；Agent 能根据 Receipt 缩小范围、换 Op 或记录结构债。一次真实建构至少产生安全改变、可复核候选或有解释力的无写入结论之一。

### P3：迁移 Compile 的成熟保障

**目标：** 保留 ORG 编译质量，同时把阅读方向交给 DSH Agent。

- 迁移 Source Adapter、Semantic Inventory、Coverage Ledger、artifact 保留、figure reuse；
- 建立 Compile Workspace 与来源指纹、材料级 checkpoint；
- Agent 可调用前瞻、回读、扩大上下文、图表检查、忠实度审查和 defer；
- 选材与整体进度接入 CognitiveRun UI；
- 完成来源必须由 coverage 证明，而不是由模型自报。

**验收：** 一本长文档暂停重启不重复 Buffer；含表图论文不丢图表；重复图只形成一份主 Buffer 并注明多次出现；高价值缺口可定向补回。

### P4：迁移 Digest 的成熟保障

**目标：** 从批次消化改为贡献级同化循环。

- 迁移 Contribution Ledger、Semantic Patch compiler、relation disposition；
- Agent 按需检索、精读、比较和改选候选卡；
- 引入 CommitGroup，单个关系失败不拖垮无关 enrich；
- 失败贡献转 deferred 后继续其他贡献；
- 成功提交后确定性结算 Buffer 状态。

**验收：** 连续两个贡献失败后仍会尝试第三个合法贡献；不存在重复新建与幽灵关系；一次失败不丢失已提交成果，也不把未处理 Buffer 标为已消化。

### P5：Thinking Model Registry 与多维 Evaluation

**目标：** 把思考方式变成可版本化、可回放、可比较对象。

- 从 Persona 和 Skill 中抽出 3–5 个高频 Thinking Model；
- 建立版本、能力依赖、停止条件与评价维度；
- 对同一案例支持模式重放与局部消融；
- 增加确定性、用户、rubric model 和人工评价记录；
- 固定基础模型、prompt、工具版本和预算以控制实验变量。

**验收：** 能说明一个结果差在知识缺口、Operator 选择、停止条件、Thinking Model 还是综合表达；不同版本差异可复现，不以无限增加 token 换取表面提升。

### P6：Learning Lab 与策略晋升

**目标：** 在不自改运行系统的前提下形成受控学习闭环。

- 聚合同类 Episode 和失败分类；
- 由人工或模型提出 Thinking Model / Runtime Policy 候选变体；
- 在训练案例、验证案例和隐藏案例上回放；
- 输出多维比较、成本变化、退化案例与回滚点；
- 只有人工批准后才晋升版本。

**验收：** 候选在隐藏案例上产生可复现净收益；撤回后可恢复旧行为；无自动 ontology 演化、无运行中自改 Persona、无奖励投机。

## 13. 测试与评价基线

### 13.1 协议测试

- Workspace schema、版本迁移和 checkpoint 恢复；
- Operator input / observation schema；
- Harness Receipt 原因码与合法替代动作；
- DSH session、CognitiveRun、Episode 的映射；
- 用户决定回流与 authorization revision；
- compaction 后 Workspace 不丢目标与未决项。

### 13.2 事务测试

- 写入范围、关系签名、来源、ontology 和 revision；
- 幂等提交与重复确认；
- 暂停、取消、重试和崩溃恢复；
- 两任务不相交写入可并存，重叠写入返回 conflict Observation；
- JS 适配器与 Python Harness 结果一致。

### 13.3 行为测试

- 工具拒绝后继续判断，不直接结束；
- 连续无进展后换动作或停止，不机械重试；
- 信息不足时回读、改搜、defer 或询问用户；
- 高风险修改只形成 shadow 候选；
- 用户 Steering 在下一安全边界生效；
- 无写入运行也留下发现、盲区、债务或待验证问题。

### 13.4 真实材料回归

- 一本长书：上下文扩展、暂停恢复、覆盖结算；
- 一份报告：数字、限制与来源锚点；
- 一篇含表图论文：artifact 保留和重复图复用；
- 一组新旧 Buffer：enrich、新建、skip、关系 deferred 与失败改选；
- 一个真实领域图：领域过载、桥接、冲突与关系修订。

### 13.5 体验测试

  用户不打开技术轨迹，也能回答：系统正在关注什么、刚发现什么、准备做什么、是否需要决定、已经改变什么、为什么没有改变。系统不能把 token、上下文字数、波次或模型内部推理当作主要进度。

## 14. 风险、撤回与停止条件

| 风险 | 防线 | 撤回方式 |
|---|---|---|
| DSH 与 Python Harness 双权威 | 单一 Harness Bridge + parity tests | 禁用新适配器，回到只读 DSH |
| Workspace 变成第二知识库 | 核心字段闭集、TTL/归档策略、不得作为知识事实引用 | 删除运行态，不影响 Markdown 知识体 |
| Thinking Model 再度变成固定管线 | 只声明目的、能力、偏置和停止条件；下一步仍由 Agent 选择 | 回退为软 Skill，不启用结构化模式 |
| Operator 快速膨胀 | capability tags、真实摩擦证明、近义工具合并 | 下架 Operator descriptor，保留 Episode |
| 评价模型自我偏爱 | 多来源 rubric、隐藏案例、人工复核、成本维度 | 拒绝候选，不晋升版本 |
| 策略过拟合 | 冻结模型、验证/隐藏集、跨任务回归 | 回滚到 base version |
| 多任务互相覆盖 | scope + revision + 短写锁 + conflict Observation | 暂停冲突 Run，不影响其他任务 |
| Episode 体积和隐私失控 | 不存隐藏思维链、工具结果引用化、保留策略 | 清理派生 Episode，保留知识事实 |

  若 P1 不能稳定证明“拒绝回流、恢复、用户决策继续同一 Episode”，不得进入自动策略学习。若 P2 的 DSH Construct 仍主要依赖一次大上下文和单 JSON 输出，应停止迁移并修正 Loop，而不是继续增加 Thinking Model。若 P5 没有可复现评价，不启动 P6。

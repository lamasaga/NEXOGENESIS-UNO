# 思维体 Skill 流程、知识图谱调用现状与 Agentic 升级设计

> 状态：设计审查稿
>
> 审查基线：开发仓 `992cad8`（2026-08-13）
>
> 日期：2026-08-14
>
> 范围：Web 思维体、知识摄入流水线、STM、Graph/RAG、认知事件与后续评测
>
> 目的：为下一阶段 Skill、Harness 与多轮推理循环重构提供事实基线和验收标准

## 1. 结论先行

  当前项目已经具备一个 Agent 的必要零件：技能路由、统一检索、图遍历、RAG、短期记忆、原生工具调用、有限轮循环、写入预检、原子事务、修复重试和认知事件。但这些零件还没有组成一个完整的“认知执行系统”。

  现在的思维体更接近“强制首轮检索 + 模型自行决定是否继续读卡 + 最多十轮工具调用”。它能够多轮调用工具，却没有显式维护任务模型、调查计划、假设、反证、证据覆盖度和停止理由。因而，多轮不必然意味着深入思考；模型也可能只消费第一次召回的少量摘录便直接作答。

  下一阶段不应通过无限增加提示词或一次塞入更多卡片来制造“深思感”。目标应改为：让思维体像优质 Code Agent 处理大型代码库一样，先形成任务模型，再以小步、可观察、可校验的方式在知识图谱中定位、展开、精读、比较、反证、综合和复核；每一轮都根据上一轮观察决定下一步，而不是照固定剧本机械执行。

  工程上无法也没有必要证明模型具有某种不可观察的主观思维。项目可以可靠追求的是“可验证的思考行为”：

- 能把用户问题拆成待证实的子问题；
- 能说明当前缺少哪类证据，而不是泛化地继续检索；
- 能形成多个竞争性解释，并主动寻找削弱自身结论的材料；
- 能根据工具观察更新计划；
- 能引用真正读过且实际支撑结论的卡片；
- 能在证据不足、边界未明或收益递减时给出明确停止理由；
- 能把本轮焦点、用户立场、未决张力和证据足迹更新进讨论记忆；
- 写入前能通过独立校验，而不是让同一段生成文本自证正确。

## 2. 术语与计数口径

  “思维体调用了多少张卡片”至少包含四个不同数字。如果不区分这四层，就会把图上亮过的节点误认为模型全文读过，也会把检索候选误认为最终依据。

| 口径 | 含义 | 当前实现 |
|---|---|---|
| 候选召回数 | 检索阶段找到并允许后续精读的卡片 | 每次统一检索按注意力槽位选出有限工作集 |
| 上下文卡数 | 以标题、关系和正文摘录进入模型上下文的卡片 | `Context Package.structure.nodes` |
| 全文精读数 | 模型显式调用 `read_card` 读取较完整正文的卡片 | 每个用户请求最多 6 张不同卡片 |
| 最终依据数 | 回答正文实际引用，并在来源区标为 evidence 的卡片 | 与已读/召回轨迹合并后最多显示 12 张 |

  “图谱调用”也不只等于读卡。本文将其分为：查询、种子定位、关系扩展、冲突分支、全文读取、目录读取、结构诊断和写回更新。

## 3. 当前总体架构

```text
用户消息
  │
  ├─ 精确命令 /compile /digest /construct
  │    └─ 后台知识摄入流水线
  │         ├─ Harness 生成局部任务
  │         ├─ LLM 生成或修订产物
  │         ├─ Harness 校验/修复循环
  │         └─ write --batch / Buffer apply
  │
  └─ 其他消息
       └─ Web 思维体 Agent
            ├─ Skill 路由
            ├─ Harness 强制首轮统一检索
            ├─ 最多 10 轮模型—工具循环
            ├─ retrieve / read_card / list_domains / 提案工具
            └─ 最终回答、来源轨迹、可选确认写入
```

  项目名称上共有九个 Skill，但运行时并非九个 Skill 都进入同一种循环：

| Skill | Web 实际入口 | 运行形态 |
|---|---|---|
| `nexo-talk` | 默认消息 | Web Agent 工具循环 |
| `nexo-assess` | 研判、深判、`/assess`、`/judge` | Web Agent 工具循环 |
| `nexo-emerge` | 记一下、涌现、落盘等 | Web Agent 工具循环 + 候选确认 |
| `nexo-refine` | 精修/润色既有卡 | Web Agent 工具循环 + 单卡确认 |
| `nexo-report` | 专题报告/结构化报告 | Web Agent 工具循环 + 可选 OutBox 确认 |
| `nexo-judge` | 旧入口 | 重定向到 `nexo-assess`，不独立演进 |
| `nexo-compile` | 仅精确 `/compile` | 后台确定性流水线 |
| `nexo-digest` | 仅精确 `/digest` | 后台多波流水线 |
| `nexo-construct` | 仅精确 `/construct` | 后台诊断 + 单镜头流水线 |

  这一区分非常重要：`.agent/skills/` 描述的是执行剧本和纪律，而 `nexogenesis/runtime/` 决定 Web 端实际上执行了什么。后续审查必须分别回答“Skill 希望它做什么”和“运行时是否强制它做到了”。

## 4. Web 思维体的共用运行循环

### 4.1 当前真实流程

```text
1. route_skill(message)
2. 读取对应 SKILL.md 作为 playbook
3. 拼接 system + 最近 10 条 user/assistant 消息 + 当前问题
4. Harness 自动调用一次 retrieve(message)
5. 将压缩后的 Context Package 作为 tool 结果交给模型
6. 模型选择：
   - 直接回答；或
   - 再次 retrieve；或
   - read_card；或
   - 调用当前 Skill 允许的提案工具
7. 执行工具，将 observation 追加进 messages
8. 重复，最多 10 个模型轮次
9. 输出来源，按回答正文是否出现卡 id/标题区分 evidence/read/retrieved
10. 发布 session.idle；失败则发布 session.failed
```

  这已经是一个真实的工具循环，而不是一次性 Prompt。但循环缺少显式的认知状态，因此本质上仍是“模型自由选择下一个工具”，不是 Harness 管理的计划—观察—修正循环。

### 4.2 当前卡片调用数量

  默认注意力配置总卡位上限为 12，但实际单次统一检索由各 profile 的槽位之和决定：

| 模式 | core | expansion | conflict | 单次最多进入结构工作集 |
|---|---:|---:|---:|---:|
| talk | 3 | 6 | 2 | 11 |
| answer | 继承 core=3 | 5 | 2 | 10 |
| judge / assess | 3 | 4 | 3 | 10 |
| digest 注意力 profile | 继承 core=3 | 4 | 1 | 8 |

  `emerge`、`refine` 和 `report` 在运行时都映射到 talk 检索模式，因此单次统一检索同样最多约 11 张结构卡。每张结构卡向模型提供最多约 800 字符摘录；同时最多提供 6 个 RAG 质料摘录，每个在 Web Agent 工具载荷中截为 300 字符。

  模型可以在后续轮次再次 `retrieve`，每次检索形成新的局部工作集并扩大本轮允许精读的候选集合。当前没有独立的 `retrieve` 调用次数上限，也没有总候选卡硬上限；它只间接受“最多 10 个模型轮次”约束，而且一个模型轮次理论上可以产生多个工具调用。因此，多次检索后的累计候选数并不严格等于 10×11，也没有被 Harness 精确控制。

  不论检索多少次，每个用户请求最多全文精读 6 张不同卡片。`read_card` 只允许读取已经进入本轮某次统一检索上下文的卡片，单卡正文最多返回 4000 字符。最终前端来源列表最多 12 张。

  因此，当前系统在一次复杂讨论中通常是：先看约 10 张卡的摘录，再全文读 0–6 张。真正的缺点不是固定读得太少，而是没有机制保证模型会根据问题复杂度用完合理预算，也没有判断“当前 6 张是否覆盖了核心机制、冲突、反证和边界”。

### 4.3 当前记忆如何参与

  当前上下文同时有两种记忆：

- 对话历史：最近 10 条 user/assistant 消息直接进入模型；
- STM：当前/近期会话的焦点、张力、已引卡和 bridge hints 参与检索种子与排序。

  但 Web 对话运行路径目前只读取 STM，没有在每轮回答后自动把本轮焦点、用户主张、系统假设、张力、引用和 RAG 足迹回写 STM。`memory update` 能力存在于 CLI 和 `STMStore`，却没有形成 Web Agent 的自动闭环。

  此外，压缩给模型的 `_context_payload` 不直接包含 STM 槽位。STM 会影响“召回哪些卡”，但模型通常看不到“为什么这些卡因为上一轮张力被召回”，也无法显式检查自己是否解决了上一轮未决问题。

  这正是“结合其讨论的记忆”目前最需要补齐的部分：记忆不能只是一个隐式召回偏置，而应成为模型可读、Harness 可更新、用户可审计的讨论状态。

### 4.4 当前认知事件

  Web Agent 已发布以下事件，可驱动知识图谱动画：

| 事件 | 含义 |
|---|---|
| `skill.trigger` | 进入某个 Skill |
| `retrieve.query` | 发起一次知识体查询 |
| `context.ready` | core/conflict/expansion/material 工作集组装完成 |
| `graph.hit(role=seed)` | 种子节点被定位 |
| `graph.hit(role=expand)` | 沿关系扩展 |
| `graph.hit(role=conflict)` | 冲突分支被拉入 |
| `lens.begin` | assess/judge 开始一个分析透镜 |
| `card.read` | 模型全文精读一张卡 |
| `catalog.read` | 读取领域目录 |
| `write.applied` | 已确认写入完成 |
| `session.idle` / `session.failed` | 本轮结束或失败 |

  事件已经能表达“检索和读卡”，但还不能表达计划、假设形成、证据支持/削弱、盲区发现、反证检索、覆盖检查和结论复核。用户看到的动画因而仍主要是“亮了哪些卡”，还不是“Agent 如何改变了对问题的理解”。

## 5. 各 Skill 当前流程与知识图谱调用

### 5.1 `nexo-talk`：日常讨论与分析

**设计剧本**

1. 复用或开启记忆会话；
2. 双轨检索；
3. 区分结构卡与 RAG 质料及其归因；
4. 结合 Profile 透镜回答；
5. 更新焦点、张力和引用；
6. 出现强信号时建议涌现。

**Web 当前执行**

- 强制首轮 talk 模式统一检索；
- 单次约 11 张结构卡摘录 + 最多 6 个质料摘录；
- 允许最多精读 6 张卡；
- 允许模型按盲区再次检索；
- 不提供写入工具；
- 最近 10 条消息进入模型；
- STM 影响检索，但本轮不会自动更新 STM。

**主要缺口**

- 没有先形成问题模型，宽泛提问可能只靠同一句查询；
- 没有强制区分“解释问题”“事实问题”“规范问题”“决策问题”；
- 没有竞争性假设和反证步骤；
- 没有证据覆盖检查；
- Skill 中“仍不足再定向读 5–15 张”与运行时全文精读上限 6 张不一致；
- 对话结束没有形成结构化的认知增量写回 STM。

### 5.2 `nexo-assess`：多维研判

**设计剧本**

1. 界定研判对象、时间范围和用户承担的决定；
2. 选择 2–4 个有区分度的透镜；
3. 每个透镜至少执行一次定向检索；
4. 关键卡读全文；
5. 区分事实、作者观点、系统推断和价值判断；
6. 输出条件式定位，不替用户裁决。

**Web 当前执行**

- 强制一次 judge 模式首轮检索；
- 单次最多约 10 张结构卡，其中 conflict 槽位提高到 3；
- 后续 `retrieve` 会被表现为 `lens.begin`；
- 最多全文精读 6 张；
- 工具层只读，不允许写卡。

**主要缺口**

- “2–4 个透镜”和“每个透镜至少一次检索”只写在 Skill 中，运行时没有状态机强制；
- 没有检查各透镜是否真的不同，模型可能换名称重复同一角度；
- 没有证据矩阵，无法看到某张卡支持/削弱哪个透镜；
- 没有强制反事实或相反证据；
- 没有研判完成度和未解决分歧的终止闸门。

### 5.3 `nexo-emerge`：从讨论中形成候选

**设计剧本**

1. 判断来源归因；
2. 形成不超过 3 个候选；
3. 查重、核对 Domain、关系目标和正文结构；
4. 用户选择；
5. Harness 预检；
6. 用户确认后统一写入。

**Web 当前执行**

- 强制首轮 talk 检索；
- 候选前必须至少完成一次统一检索；
- 关系目标必须进入本轮某次检索上下文；
- 最多提出 3 个候选；
- 新候选会先在服务端预检，再进入用户选择和写入确认；
- 领域 id 会确定性检查，但“必须先调用 list_domains”主要依赖提示词纪律，并非所有路径都由状态强制。

**主要缺口**

- “查重”目前等价于普通相关性检索，没有独立的近义/重复检索通道；
- 关系目标只需进入上下文，不要求全文读取或证据说明；
- 没有候选与最近讨论记忆的差异说明；
- 没有生成“为何 enrich 而非新建”的可审计决策记录；
- 预检验证契约，不验证候选是否确实构成知识增量。

### 5.4 `nexo-refine`：既有卡片精修

**设计剧本**

1. 确认目标卡 id并全文读取；
2. 与用户对齐修改性质；
3. 保持身份、类型、来源和创建时间；
4. 说明保留、澄清、新增、删除和关系变化；
5. 提交一张完整替换记录；
6. 用户确认后写入。

**Web 当前执行**

- 首轮普通检索后，目标卡必须进入上下文才能读取；
- 必须 `read_card` 后才能提交精修；
- 一次只能精修一张既有卡；
- 确定性禁止悄然改变 `type`、`origin`、`created`；
- Harness 预检后由用户确认。

**主要缺口**

- 没有自动读取目标卡的一跳关系、来源相邻卡和冲突卡；
- 没有语义 diff，只能展示完整替换记录；
- 没有“语言澄清不得改变主张”的语义等价校验器；
- 用户在多轮讨论中提出的修改意图没有形成结构化 edit brief；
- 没有修订后回归检查：关系是否仍成立、正文是否与邻卡重复、来源归因是否被改变。

### 5.5 `nexo-report`：专题报告

**设计剧本**

1. 确定对象、问题、范围、时间边界和受众；
2. 建立提纲；
3. 分机制、证据、反证/冲突检索；
4. 精读关键依据；
5. 形成结构化报告；
6. 用户要求保存时进入 OutBox 确认。

**Web 当前执行**

- 使用 talk 模式首轮检索，单次约 11 张结构卡；
- 最多精读 6 张卡；
- 保存报告时，`linked_cards` 中每张卡都必须已被全文读取；
- 因此当前单轮可保存报告的真实依据卡上限实际上不超过 6；
- 报告只写 OutBox，不自动写知识卡。

**主要缺口**

- 提纲不是持久状态，模型可能一边检索一边漂移；
- 不能为不同章节维护独立证据槽；
- 最多 6 张全文依据对复杂专题往往过窄；
- 没有章节覆盖检查、相反证据检查和引文—结论一致性检查；
- 没有长任务压缩和恢复点，达到十轮后只能被迫收束。

### 5.6 `nexo-compile`：Inbox → Buffer

**设计与 Web 当前执行**

1. Harness 扫描 Inbox、识别体裁并生成阅读窗；
2. 每个阅读窗单独调用模型提炼 Buffer；
3. 图书、论文、金融报告进行第二阶段语义审稿；
4. Harness 质量闸门失败时再定向返修一次；
5. 每窗独立校验并写入 Buffer；
6. 已完成阅读窗不会因后续失败回滚。

**知识图谱调用**

  编译阶段原则上不读取知识卡，也不调用图遍历。它只把原始材料编译成 Buffer；写入 Buffer 后索引层可刷新 RAG。这个边界是合理的，因为过早引入现有卡片会让编译阶段把原文改造成迎合既有知识结构的摘要。

**主要缺口**

- 阅读窗之间缺少材料级的跨窗记忆，长报告/书籍的前后论证可能被割裂；
- 审稿重点是单窗质量，不检查整份材料的概念一致性和遗漏覆盖；
- 没有文档级计划、章节完成度和全局术语表。

### 5.7 `nexo-digest`：Buffer → Card

**Web 当前执行**

1. 每波选择最多 3 片相关 Buffer；
2. 最多连续执行 8 波；
3. 每波通过图检索选择默认最多 6 张深读卡；
4. Prompt 还包含全部 Domain、最多 24 张实例目录、RAG 质料摘录和 Buffer 全文；
5. 模型每波最多提出 3 项 writes；
6. Harness 做事务/关系/语义槽校验；
7. 失败后按结构、引用、语义或契约分类，最多修复 3 次；
8. 每波原子提交并回读 Markdown 验证；无进展则熔断。

**知识图谱调用**

- 图用于从 Buffer 术语定位深读卡；
- Domain 骨架被优先 pin；
- RAG 用于补充 Buffer/archive/discussion 质料；
- 写入后重建图与刷新索引。

**主要缺口**

- 每波只有一次主要语义生成，不是 Agent 根据查重结果动态追加调查；
- 图检索确定深读集后，模型没有可用工具继续读取其他卡；
- “新建还是 enrich”没有独立 novelty/duplicate 验证步骤；
- 波与波之间只通过已写入事实源间接衔接，没有消化任务级计划和已处理主题记忆；
- 到 3000 卡时，单次局部工作集可以保持有限，但候选召回精度和增量校验会成为核心瓶颈。

### 5.8 `nexo-construct`：结构诊断与单镜头建构

**Web 当前执行**

1. Harness 全库诊断结构信号；
2. 确定性 seed-links 可先执行；
3. 从建议镜头中只取第一个；
4. Web 固定使用最多 5 张深读卡和 3 片 Buffer；
5. 模型生成一个小批量结构事务；
6. Harness 分类修复、写入并验证；
7. 一次后台任务只执行一个镜头。

**知识图谱调用**

- 全库图分析发现孤儿、冲突缺口、过载 Domain、枢纽和跨域信号；
- 单镜头只把局部深读卡、相关信号和少量 Buffer 交给模型；
- 模型写回关系、合并状态、必要枢纽或冲突结构。

**主要缺口**

- 全库信号先被枚举为大报告，再从中取局部，规模增长时噪声和文件体积迅速膨胀；
- 只取第一个建议镜头，没有优先级、影响范围、成本和依赖排序；
- 没有持久化结构问题队列，已发现但未处理的问题每次重新扫描；
- 模型不能在单镜头内根据观察主动扩展图、比较候选或寻找反例；
- “建构完成”只代表一个小事务完成，不代表结构问题被真正关闭。

### 5.9 `nexo-judge`：兼容入口

  `nexo-judge` 不应继续形成独立逻辑。所有路由、配置、测试、事件和文档应逐步统一到 `nexo-assess`，只保留 `/judge` 和旧称“深判”的兼容解析。

## 6. 为什么当前还不够 Agentic

### 6.1 有循环，但没有显式任务状态

  当前 `run_agent_stream` 将工具观察追加到消息，然后再次请求模型。这是 ReAct 式循环的基础，但没有独立于对话文本的任务状态。模型无法可靠维护：

- 当前目标和成功标准；
- 已拆出的子问题；
- 当前假设及其置信度；
- 哪些证据支持或削弱哪个假设；
- 哪些卡已读、为什么读；
- 尚未覆盖的证据槽；
- 下一步为何优于其他工具动作；
- 当前停止是因为完成、预算耗尽、证据不足还是收益递减。

### 6.2 多轮上限不是多轮推理策略

  `MAX_ROUNDS = 10` 只是安全边界，不是思考计划。简单问题可能不需要 10 轮，复杂报告可能远超 10 轮。没有复杂度分级和动态预算时，模型会在“过早作答”和“无目的反复检索”之间摆动。

### 6.3 工具粒度仍偏粗

  当前核心只读工具是 `retrieve`、`read_card` 和 `list_domains`。缺少成熟代码代理中常见的、可组合的小工具等价物：

| Code Agent 常用动作 | 知识体所需等价能力 |
|---|---|
| 文件/符号搜索 | 按标题、类型、Domain、来源、关系、时间和正文搜索卡片 |
| 查看引用/调用者 | 展开 incoming/outgoing 关系和关系路径 |
| 读取精确代码区间 | 按卡片章节/语义槽读取，而非总是整卡 |
| 比较实现/查看 diff | 多卡按维度对比，或查看精修前后语义 diff |
| 运行测试 | 检查结论覆盖、反证、来源和关系目标 |
| 查看失败日志 | 返回结构化失败类型、可修复字段和下一动作 |

### 6.4 没有独立验证者

  Harness 很擅长验证卡片结构和事务合法性，但日常分析的语义质量主要由生成答案的同一个模型自己决定。缺少独立的最终检查：

- 结论是否由已读证据支撑；
- 是否遗漏了检索到的关键冲突；
- 是否把 document/system/user/nascent 混为一谈；
- 是否回答了用户真正的问题；
- 是否把相关性误写成因果；
- 是否存在未说明的适用边界。

### 6.5 讨论记忆没有闭环

  STM 已能存储正确类型的信息，但 Web Agent 不会在每轮后自动形成“认知提交”。这类似 Code Agent 每次读完仓库却不更新计划、不记录已完成步骤，下轮只能重新从聊天文本猜测状态。

### 6.6 内部推理配置与目标不匹配

  当前 Web Agent 调用模型时显式发送 `thinking: disabled`。这不等于模型完全不能分析，但意味着运行时主动关闭了提供方可能提供的额外推理模式。是否开启不能凭直觉决定，必须在真实任务集上比较质量、延迟和成本；更重要的是，即使启用模型推理，也不能替代外部可观察的计划、工具、验证和记忆状态。

## 7. 可迁移的优质 Code Agent 范式

  本节参考的是成熟代码代理中可观察、可迁移的工程范式，而不是复刻任何模型不可见的内部思维过程。

### 7.1 目标契约，而不是步骤堆叠

  优质 Code Agent 先确定要实现什么、哪些文件/系统在范围内、什么算完成、哪些动作需要批准。知识思维体也应先建立：问题、范围、时间、所需证据、允许的写入和完成标准。

### 7.2 先定位，再精读

  Code Agent 不会先把全仓库全部文件塞进上下文，而会搜索符号、定位关键文件、沿调用链扩展、只读取相关区间。知识思维体应对应为：领域路由 → 候选卡 → 关系路径 → 少量全文卡 → 必要原始质料。

### 7.3 计划是可变状态，不是一次性作文

  计划应包含少量可验证步骤，并在工具观察后更新。计划不是为了向用户展示“我想了很多”，而是为了防止重复工作、目标漂移和遗漏验证。

### 7.4 观察必须改变下一步

  如果一次检索已经回答了问题，就不应机械执行第二次；如果出现冲突，就应转向反证或边界；如果某张卡只是宽泛相关，就应缩窄查询。每次工具调用都应有目的、观察和状态更新。

### 7.5 验证是终止条件的一部分

  Code Agent 不以“代码写完”作为结束，而以测试、构建或差异审查通过作为结束。思维体不应以“生成了一段回答”作为结束，而应以问题覆盖、证据支撑、反证检查、归因检查和用户目标回应通过作为结束。

### 7.6 失败恢复要分类

  当前 digest/construct 已有分类修复，这是正确方向。思维体也需要区分：无召回、召回噪声、关键卡不可读、证据互相冲突、上下文预算不足、模型工具格式错误和服务故障。不同失败应采取不同恢复动作，而不是统一“再试一次”。

### 7.7 压缩的是历史，不是未完成状态

  长任务需要压缩旧观察，但必须保留目标、用户约束、已确认事实、未决假设、关键证据 id、失败教训和下一步。不能简单截断最近消息，也不能保存冗长思维文本。

### 7.8 提示词要瘦，能力放进状态与工具

  OpenAI 官方模型指导建议减少重复指令，只暴露当前任务相关工具，并用代表性评测验证精简是否真的提高成功率；它也建议把可确定的过滤、连接、排序、去重和验证放入程序化工具，把会改变下一决策的语义判断保留给模型直接观察。[Model guidance](https://developers.openai.com/api/docs/guides/latest-model)

  对本项目的含义是：不要继续把所有规则、样本、目录和流程塞进一个 Prompt；应让 Harness 负责候选生成、排序、去重、预算、状态和验证，让模型负责提出假设、判断意义、选择下一步和综合表达。

## 8. 目标架构：认知执行循环

### 8.1 总体循环

```text
Orient 任务定向
  ↓
Plan 建立可变调查计划
  ↓
Retrieve 多通道定位候选
  ↓
Inspect 精读关键卡与关系
  ↓
Hypothesize 形成竞争性解释
  ↓
Challenge 主动寻找反证、边界和替代解释
  ↓
Synthesize 综合为机制链或条件式结论
  ↓
Verify 检查覆盖、归因、引用与用户目标
  ├─ 未通过 → 更新计划并回到 Retrieve/Inspect
  └─ 通过 → Answer / Propose
                    ↓
              Commit Memory
```

  这不是固定要求每轮执行九步。Harness 应根据任务复杂度和当前状态选择最小充分路径：简单事实查询可以 Orient → Retrieve → Inspect → Verify → Answer；复杂研判才需要完整循环。

### 8.2 可持久的 Agent Run 状态

```yaml
run:
  id: "..."
  skill: assess
  objective: "回答什么问题"
  scope:
    time: "..."
    domains: []
    exclusions: []
  success_criteria:
    - "解释机制"
    - "覆盖主要反证"
    - "区分事实与推断"
  plan:
    - id: q1
      question: "..."
      status: in_progress
      evidence_need: mechanism
  hypotheses:
    - id: h1
      statement: "..."
      status: provisional
      supports: []
      weakens: []
      unknowns: []
  evidence_ledger:
    - card_id: "..."
      read_level: excerpt
      role: support
      applies_to: [h1]
      attribution: document
  memory_context:
    focus: "..."
    user_claims: []
    prior_tensions: []
  budget:
    model_rounds_used: 0
    retrievals_used: 0
    deep_reads_used: 0
    context_chars_used: 0
  stop:
    reason: null
    unresolved: []
```

  这里保存的是结构化的工作状态，不保存或展示模型私密的逐词思维链。用户可以看到简化后的计划、证据进展和未决问题；系统则用完整状态保证恢复和评测。

### 8.3 建议的新工具层

| 工具 | 作用 | 返回重点 |
|---|---|---|
| `search_cards` | 按 query、type、domain、source、time、maturity 检索 | 候选、分数、命中字段、召回通道 |
| `expand_graph` | 从节点沿指定关系/方向展开 | 路径、hop、关系类型、截断原因 |
| `read_cards` | 批量按章节或槽位读取少量卡 | 正文片段、来源、未读取部分 |
| `compare_cards` | 按机制、假设、边界、证据、冲突比较 | 共识、差异、不可比项 |
| `find_counterevidence` | 针对假设寻找 conflict、失效边界和反例 | 削弱证据、替代解释、盲区 |
| `inspect_domain` | 查看领域摘要、成员簇和邻域 | 领域边界、过载、子主题 |
| `update_run_state` | 更新计划、假设、证据账本和停止理由 | 新状态版本 |
| `verify_answer` | 检查引用、归因、覆盖、矛盾和目标 | 通过项、失败项、建议下一动作 |
| `commit_memory` | 写回焦点、用户主张、系统假设、张力和足迹 | STM 变更摘要 |

  其中搜索、图展开、过滤、排序、去重、计数和格式验证应由 Harness 确定性完成；“这份证据意味着什么”“哪个解释更强”“是否值得改变结论”仍交给模型。

## 9. 卡片调用预算的升级原则

### 9.1 不以“读得多”为目标

  卡片数量应是任务复杂度和证据覆盖的结果。一次读取 30 张摘要可能不如精读 4 张机制卡和 2 张反证卡。建议同时限制：

- 单轮活跃工作集；
- 累计候选数；
- 累计全文字符；
- 重复检索率；
- 无新增证据的连续轮数；
- 每类证据的最低槽位。

### 9.2 建议的自适应预算

| 任务 | 累计候选卡 | 全文精读 | 建议工具回合 | 最低证据结构 |
|---|---:|---:|---:|---|
| 简单 talk | 6–10 | 1–3 | 1–2 | 直接依据 + 边界 |
| 复杂 talk | 12–24 | 4–8 | 2–4 | 机制 + 冲突/替代解释 |
| assess | 20–40 | 6–12 | 3–6 | 每透镜至少一条依据，至少一条反证 |
| emerge | 12–24 | 3–8 | 2–4 | 近义卡 + Domain + 关系目标 |
| refine | 目标卡 + 2–6 邻卡 | 目标卡 + 2–4 | 2–4 | 当前卡 + 来源/冲突/邻卡 |
| report | 30–80（分章节） | 8–20（分批） | 可恢复长任务 | 各章节证据槽 + 反证 + 边界 |

  上表是累计预算，不代表一次全部塞进 Prompt。任何一个模型轮次的活跃结构工作集仍建议控制在约 8–12 张；旧观察应压缩进证据账本，只在需要时重新展开。

### 9.3 动态停止条件

  满足以下条件可以停止检索并进入综合：

- 所有必需子问题已有至少一个可信证据；
- 关键结论至少经过一次反证或边界检查；
- 最近一次检索没有带来新的高相关卡或改变假设；
- 已说明仍无法解决的盲区；
- 继续检索的边际收益低于延迟和上下文成本。

  以下情况必须继续或明确降级：

- 只有 Domain 或标题级相关卡，没有机制正文；
- 支持结论的卡全部来自同一来源且题目需要判断；
- 已发现 conflict，却未读取对立双方；
- 用户要求报告，但某个核心章节没有证据；
- 结论引用了未读卡，或证据归因不明。

## 10. 各 Skill 的目标态 Agentic 流程

### 10.1 talk

```text
识别问题类型 → 读取讨论记忆 → 建立 1–3 个子问题
→ 首轮多通道检索 → 选择关键卡精读
→ 若有多种解释，建立竞争性假设
→ 定向找冲突/边界 → 综合 → 验证 → 回写 STM
```

  简单问题保持轻量；只有复杂度、争议性或用户明确要求深入时才扩大循环。

### 10.2 assess

```text
明确决策对象 → 生成 2–4 个非重复透镜
→ 为每个透镜建立证据需求
→ 分透镜检索与精读 → 建证据矩阵
→ 交叉检查透镜冲突 → 反事实/边界检索
→ 条件式定位 → 独立覆盖验证 → 回写未决张力
```

  Harness 应强制每个透镜至少有一条实际证据，并检查不同透镜是否重复消费同一组卡而没有新增视角。

### 10.3 emerge

```text
抽取候选思想 → 近义/重复专用检索
→ 判断 enrich / new / skip
→ 定位 Domain → 验证关系目标
→ 读取关键近义卡和冲突卡
→ 形成 ≤3 候选及差异说明
→ Harness 语义增量检查 → 用户选择/确认
```

  候选提案应新增 `novelty_reason`、`nearest_cards`、`why_not_enrich` 或 `enrich_target`，使“为什么新建”可审计。

### 10.4 refine

```text
读取目标卡 → 形成 edit brief
→ 读取一跳关系、关键来源邻卡和冲突卡
→ 生成语义 diff → 检查身份字段与来源
→ 回归验证关系和主张是否被意外改变
→ 展示差异 → 用户确认
```

### 10.5 report

```text
建立任务契约与提纲 → 为各章节建证据槽
→ 分章节检索/精读 → 维护证据矩阵
→ 对核心判断主动找反证和失效条件
→ 先写章节结论，再跨章节综合
→ 检查覆盖、重复、引用和归因
→ 对话交付；用户确认后保存 OutBox
```

  报告应成为可暂停、恢复和压缩的长任务，而不是把所有研究压在一个十轮对话请求中。

### 10.6 compile

```text
文档级地图 → 分阅读窗处理 → 窗内 Buffer 提炼
→ 高价值材料审稿 → 更新文档级术语/论证地图
→ 跨窗覆盖检查 → 缺口返修 → 归档
```

  编译仍不应调用知识图谱，但应拥有“材料内部图”：章节、作者命题、证据、情景和限制之间的临时结构，用于跨窗一致性检查。该临时结构不直接写入 Cards。

### 10.7 digest

```text
Buffer 聚类 → Domain 路由 → 近义卡/候选 enrich 检索
→ 深读已有卡 → 判断 new/enrich/skip
→ 检查 conflict 与 Profile 增量
→ 小批量事务 → Harness 校验/修复 → 原子提交
→ 更新消化任务状态 → 下一波
```

  模型应能在判断阶段追加一次定向检索，而不是被首次深读集永久锁定。Harness 应记录每片 Buffer 的处置理由，避免后续波重复理解同一材料。

### 10.8 construct

```text
增量结构分析 → 结构问题队列
→ 按影响/置信度/依赖选择问题
→ 读取局部子图 → 提出候选操作
→ 反向检查受影响邻居 → 模拟事务
→ 写入并验证 → 关闭/降级问题 → 下一项
```

  建构的核心产物应从“大型诊断报告”升级为持久化问题队列。每个问题应包含稳定 id、证据、相关卡、优先级、首次/最近发现时间、处理状态、结构指纹和关闭条件。

## 11. 讨论记忆的目标设计

### 11.1 三层记忆

| 层级 | 保存内容 | 生命周期 |
|---|---|---|
| Run working state | 当前计划、假设、证据账本、预算、失败和下一步 | 单次任务，可暂停恢复 |
| Conversation STM | 焦点、用户主张、系统假设、未决张力、已引卡、指令 | 多轮讨论卷 |
| Knowledge body | 经确认的 Card、Profile、Buffer、OutBox | 长期事实源 |

  运行时状态和 STM 都是辅助记忆，不得取代 Markdown 知识事实源。它们可以删除；删除只影响连续性，不得造成知识内容损失。

### 11.2 每轮认知提交

  回答结束前，Agent 应生成一个结构化且受 Harness 限制的 memory delta：

```yaml
focus: "本轮真正讨论的问题"
claims_user:
  - "用户明确表达的立场"
claims_system:
  - "系统当前暂定、未写卡的综合"
tensions:
  - "仍未解决的分歧"
cited_cards:
  - "实际作为依据的卡 id"
rag_footprints:
  - "关键原始质料锚点"
bridge_hints:
  - "下轮值得继续连接的卡"
user_directives:
  - "不要记录/偏好某种表达等"
```

  Harness 应根据本轮真实轨迹过滤：不能把未检索卡写进 cited，不能把系统推断写成用户立场，也不能用冗长回答全文污染 STM。

## 12. 认知过程与知识图谱动画的目标映射

  后续图谱动画不应展示模型的私密思维链，而应展示可验证的外部认知动作。

| Agent 状态 | 建议事件 | 图谱表现 |
|---|---|---|
| 定义任务 | `reasoning.orient` | 图谱轻微聚焦，显示任务标题 |
| 建立计划 | `reasoning.plan` | 顶部/侧栏出现 2–4 个调查槽，不必点亮节点 |
| 发起查询 | `retrieve.query` | 扫描波纹 |
| 定位种子 | `graph.hit seed` | 种子先亮 |
| 关系展开 | `graph.hit expand` | 沿真实边分批传播 |
| 冲突展开 | `graph.hit conflict` | 保留原边颜色，冲突节点使用协调的黄色提示 |
| 精读卡片 | `card.read` | 节点橙黄色光晕，阅读顺序错峰 |
| 建立假设 | `reasoning.hypothesis` | 只标记涉及节点组合，不虚构新图边 |
| 证据支持/削弱 | `reasoning.evidence` | 节点旁短暂显示 support/weaken 标记 |
| 发现盲区 | `reasoning.gap` | 搜索未命中区域/状态提示，不点亮伪节点 |
| 覆盖验证 | `reasoning.verify` | 已覆盖路径收束，未覆盖槽保留弱提示 |
| 写入 | `write.applied` | 新建/丰富使用不同节点手势，随后恢复静息态 |
| 记忆提交 | `memory.committed` | 不改图结构，只提示“本轮焦点已保留” |

  所有动画必须来自真实事件和真实卡 id。若模型只形成一个语言假设但尚未写卡，不得在知识图谱中永久生成节点或关系。

## 13. 规模化到 3000 卡时的约束

  Agentic 升级不能重新走回“扩大上下文”的老路。3000 卡规模下应坚持：

- 单轮活跃卡片约 8–12 张；
- 累计研究通过多轮、分章节和证据账本扩展；
- Domain 先路由，不把全部 Domain 一次送给模型；
- 图 API 按需返回局部子图，前端默认显示聚合图；
- 检索使用多通道融合和去重，而不是只放大 top-k；
- 写入和校验增量化；
- construct 使用问题队列，不重复生成全库自然语言报告；
- 长报告和长期研判支持暂停、恢复和状态压缩。

## 14. 实施路线图

### P0：建立可观察的认知状态

  目标：不大改检索算法，先让循环可审计、可停止、可评测。

- 新增 `AgentRunState`：目标、计划、证据账本、预算、停止理由；
- 将首轮检索结果、后续检索、精读和最终依据写入 run state；
- 新增结构化 `commit_memory`，完成 Web STM 回写闭环；
- 为每轮记录 `context_chars`、候选卡、全文读卡、重复查询和无新增证据次数；
- 最终回答前执行轻量 `verify_answer`；
- 新增 reasoning/memory 认知事件，但不暴露私密思维链；
- 保留现有 Agent 路径作为 feature flag 回退。

  建议涉及：

- `nexogenesis/runtime/agent.py`
- `nexogenesis/runtime/agent_tools.py`
- `nexogenesis/runtime/cognitive_events.py`
- `nexogenesis/thinking/stm.py`
- `nexogenesis/thinking/assemble.py`
- Web 的运行状态与动画适配层

### P1：扩充知识调查工具

  目标：让模型能像 Code Agent 搜索代码一样组合知识调查动作。

- 增加元数据过滤搜索、定向图展开、批量分段读卡、多卡比较和反证检索；
- 检索结果返回命中原因、通道和截断原因；
- 对 assess/report 提供证据矩阵；
- 对 emerge 提供近义/重复专用通道；
- 对 refine 提供邻域和语义 diff；
- 让工具集按 Skill 最小暴露，避免每轮携带无关工具描述。

### P2：升级 Skill 策略和长任务

  目标：把 Skill 从提示剧本升级为运行时策略。

- talk：复杂度分类和自适应预算；
- assess：强制 2–4 个非重复透镜与每透镜证据槽；
- report：可暂停、恢复、分章节研究；
- emerge：新增/丰富/跳过决策记录；
- refine：edit brief、语义 diff 和回归验证；
- compile：文档级地图和跨窗覆盖；
- digest：波间任务状态与追加检索；
- construct：持久化结构问题队列。

### P3：3000 卡规模化

  目标：让知识库规模增长不改变单轮上下文上限。

- Domain 路由 → 候选卡 → 深读卡三级检索；
- 图/RAG/校验增量化；
- 图 API 局部子图和前端语义缩放；
- 3000/10000 卡合成压力测试；
- 长任务状态压缩与崩溃恢复；
- 检索与回答质量评测成为发布门槛。

## 15. 评测体系与验收标准

  “感觉更智能”不能作为唯一验收标准。建议为每个 Skill 建立代表性任务集，并测量以下指标：

| 指标 | 含义 |
|---|---|
| Retrieval Recall@k | 应用卡是否进入候选工作集 |
| Deep-read precision | 全文读卡中真正被答案采用的比例 |
| Evidence precision | 标为依据的卡是否真的支撑相应结论 |
| Counterevidence coverage | 争议任务是否读取至少一个削弱或边界证据 |
| Attribution error | user/document/system/nascent 混用率 |
| Unsupported claim rate | 回答中无法由依据或明确系统推断支持的主张比例 |
| Duplicate proposal rate | emerge/digest 重复建卡比例 |
| Enrich decision quality | 应 enrich 时误新建、应新建时误 enrich 的比例 |
| Memory continuity | 下一轮能否正确延续焦点、约束和未决张力 |
| Plan adaptation | 工具观察后是否改变了下一步而非机械重复 |
| Verification catch rate | 最终验证器能否拦住遗漏反证、错引和未回答问题 |
| Tool efficiency | 在通过质量门槛前提下的轮数、卡数、token、延迟 |
| Recovery success | 工具/模型失败后恢复并完成任务的比例 |

  每类 Skill 至少准备：简单任务、复杂任务、零命中任务、误导性近义卡任务、存在冲突任务、记忆连续任务和 3000 卡噪声规模任务。只有在成功率和证据质量提升时，增加轮次、卡数或推理成本才算有效。

## 16. 建议的第一轮实现边界

  第一轮不建议立即重写全部 Skill。最小而高价值的切口是：

1. 给 Web Agent 增加 `AgentRunState` 和明确停止理由；
2. 自动把本轮认知增量提交到 STM；
3. 增加 `find_counterevidence` 和 `compare_cards` 两个只读工具；
4. 对 `assess` 强制透镜证据槽，对 `report` 强制章节证据槽；
5. 最终回答前增加独立的结构化覆盖验证；
6. 把这些状态映射为新的认知事件和可视化反馈；
7. 用一组真实金融问题做 A/B 评测，再决定是否提高模型 reasoning 或全文读卡上限。

  这一切可以不改变 Markdown 事实源、不改变卡片类型、不放宽写入权限，也不要求立刻引入多 Agent。它会先把现有十轮工具循环从“可调用工具”升级成“有目标、有状态、有反证、有验证、有记忆的知识调查循环”。

## 17. 最终设计原则

1. Skill 定义策略和完成条件，不把全部步骤硬编码成机械流水线。
2. Harness 管状态、预算、检索候选、权限、确定性处理和验证。
3. LLM 管问题理解、假设、意义判断、下一动作选择和综合表达。
4. 记忆保存结构化认知增量，不保存冗长私密思维链。
5. 多轮必须由观察驱动；无新增信息时停止，而不是为了 Agentic 外观继续调用。
6. 读卡数量服从证据覆盖，不以数量本身代表智能。
7. 反证、边界和未知是完成条件，不是回答末尾的装饰。
8. 所有可视化来自真实工具和状态事件，不表演不存在的思考。
9. 所有长期知识写入仍通过用户授权和 `write --batch`。
10. 所有优化通过代表性任务和规模测试证明，不以更长 Prompt 或更高 token 消耗自证有效。

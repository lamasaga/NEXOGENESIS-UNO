# 知识卡分类契约：有序单主类型与多个领域

本文件与运行时代码 `packages/nexogenesis-tools/lib/uno/card-classification.js` 表达同一套语义。新建、编译、建构、审核、检索与界面均只使用两个分类字段：

- `type`：卡片的单一主结构，决定正文骨架；
- `domains`：卡片所属的长期知识问题空间，可多选。

新卡不得写入 `tags` 或 `topics`。历史卡中的旧字段只用于识别旧数据，不再参与新卡写入、筛选或领域成员计算。

## 一、先确定知识对象，再分类

一张卡回答一个可长期复用的问题。先判断卡片主要在做什么，再严格按 `conflict → entity → case → concept → method → mechanism → model → claim → phenomenon → undetermined` 的顺序逐项检查。只有满足全部最低条件才能命中，命中第一个合格类型后停止。

类型判断针对整张卡的主要知识功能。正文顺带出现案例、观点、实体名或因果词，都不构成对应类型；不得为了套入类型而补写来源没有的结构。类型不是关键词，也不是质量评价。

| type | 中文 | 主要问题 | 必须具备的结构 |
|---|---|---|---|
| `conflict` | 争议 | 哪些真实立场围绕同一问题发生了什么不相容分歧 | 至少两个可识别立场、确实不相容的分歧点、各自证据或代价、调和可能、来源与证据边界 |
| `entity` | 实体 | 这个稳定对象是谁／是什么 | 稳定指称、身份边界、关键属性、来源、来源与证据边界 |
| `case` | 案例 | 某个具体对象在何种情境下实际经历了什么 | 可识别主体、时空或制度情境、实际过程、结果与证据、可迁移启示、限制与边界 |
| `concept` | 概念 | 这个概念是什么、与近邻概念怎样区分 | 定义、关键特征、适用范围、边界与辨析、来源与证据边界 |
| `method` | 方法 | 别人应如何复用地执行分析、研究或操作 | 明确目标或输入、有顺序或规则的可执行步骤、输出、适用边界、来源与证据边界 |
| `mechanism` | 机制 | 条件如何经中间环节产生结果 | 起点与条件、至少一个可说明的中间作用或传导环节、结果、失效边界、来源与证据边界 |
| `model` | 模型 | 如何用一套简化结构解释、比较或推演现实 | 明确组件或变量、显式关系或运行规则、可复用的推理用途、失效边界、来源与证据边界 |
| `claim` | 观点 | 谁在什么条件下主张什么、依据是什么 | 归属对理解必不可少的可争论命题、依据、已知限制、来源与证据边界 |
| `phenomenon` | 现象 | 观察到了什么状态、趋势、分布、差异或反复模式 | 可观察模式、观察范围／时期／样本／具体实例中的至少一项依据、反例与失效条件、来源与证据边界 |
| `undetermined` | 未定 | 这个完整知识单元保存了什么 | 知识对象、核心内容、依据、限制与边界、来源与证据边界；且上述九类经严格检查均不成立 |

`undetermined` 只用于完整、可独立阅读且可复用的知识单元。它不是未读完、内容空洞或编译失败的占位符。

### 三个容易混淆的类型

- `method` 是行动程序：人按照它做事，并产生可判定输出。政策目标、发展方向、原则口号或任务清单都不是方法。
- `mechanism` 是现实生成过程：在特定条件下，中间作用如何使结果出现。相关性、原因名单或“A 导致 B”的压缩句都不足以成立。
- `model` 是研究者对现实的简化表示：用变量或组件及其明确规则支持解释、比较或推演。分类表、指标清单、章节目录、政策任务体系和只有方框的“框架”都不是模型。

### 类型正反例

原文说明“数量考核使工作人员优先处理容易完成的事项，复杂事项因此积压”。正确类型是 `mechanism`，因为正文有条件、行为反应和结果链条。即使正文引用一个城市窗口，也不改成 `case`。

原文只记录“数量考核上升时复杂事项积压也上升”，没有解释中间过程。更适合 `phenomenon`；不能由模型补写激励链条后标为 `mechanism`。

原文叙述某港口停工协商的主体、过程和结果，并用它讨论信息公开。若卡片主要保存这段具体过程，类型是 `case`；若卡片主要解释信息公开如何改变协商，案例只作为证据，类型可为 `mechanism`。

原文给出一组未实施的政策任务和目标，却没有可复用步骤、生成机制、模型规则、可归属主张或可观察结果。它不能因为有“体系”就标为 `model`，也不能因为有行动动词就标为 `method`；若该单元仍有独立保存价值，标为 `undetermined`。

## 二、领域是长期问题空间

领域是跨材料、可长期扩充、具有明确核心问题和边界的知识组织空间。它不是一本书、一个章节、一个作者、一个临时关键词，也不是论证关系。

新卡的 `domains` 只能从当前知识库 `01-Cards/_meta/domains/*.md` 的既有领域 ID 中选择：

- 通常选择 1–2 个，最多 3 个；
- 一张卡确实服务多个长期问题空间时可以多选；
- 选择最具体的适用领域；若已选择子领域，不再重复选择其父领域；
- 当前没有合适领域时使用 `[]`，允许保存并记录为待组织；
- 编译制卡请求不能临时发明领域。新增领域由有界领域治理检查点提出，默认经用户逐项确认；本次编译显式授权自动领域建设时，可自动批准通过确定性校验的提案。

领域 Markdown 里的 `representative_card_ids` 只是帮助理解领域的代表卡，不是成员清单。成员归属的唯一事实源是每张卡自己的 `domains`。

### 空库与领域生长

`domains: []` 会进入 `.nexogenesis/domain-governance/state.json` 的可重建未组织池。该文件是运行投影，不是第二份知识事实源。

编译在 10 个有效阅读单元、20 张新未组织卡，或一本书处理结束且累积已足够时进入一次检查点。每次最多处理 20 张卡，其中最多 5 张提供完整正文，其余只提供 ID、标题、类型、摘要和现有关系；不重发原书或 Buffer。

检查点可以将卡片挂靠到已有领域，也可以产生新领域提案。新领域至少要有三张候选成员，并说明核心问题、纳入边界、排除边界、与最近既有领域的差异及替代处置。提案不是正式知识；默认由用户逐项批准，或由本次任务明确授予自动批准权。批准后，领域文件和首批成员的 `domains` 必须在同一个 Gateway 事务中成功或全部回滚。

领域的合并、拆分、改父级和退役是后续库级治理能力，不能用编译检查点或历史建构残留入口冒充完成。

### 领域正反例

正确：`{"type":"mechanism","domains":["state-governance"]}`，正文解释行政压力如何经层级传导改变基层行为。

正确：`{"type":"case","domains":["venture-capital","corporate-governance"]}`，具体案例同时服务风险投资和公司治理两个问题空间。

正确：`{"type":"concept","domains":[]}`，当前目录无合适领域，先如实留空。

错误：`{"type":["claim","mechanism"],"domains":["第八章"]}`。`type` 不能多选，章节名不是领域。

错误：同时选择父领域 `finance` 与其子领域 `venture-capital`。只保留更具体的子领域。

错误：把“官僚制、政府谈判、激励”全部当成自由标签塞入卡片。前两者若是长期问题空间，应从既有领域中选择；“激励”若只是正文主题，无需另建元数据。

## 三、审核规则

审核按以下顺序进行：

1. 确定整张卡的主要知识功能；
2. 按 `conflict → entity → case → concept → method → mechanism → model → claim → phenomenon` 顺序检查每类的全部最低条件，不允许跳过在先且已成立的类型；
3. 若九种实质类型都不成立，检查卡片是否仍是完整、可独立阅读且可复用的知识单元；是则使用 `undetermined`，否则是成卡资格问题；
4. 检查选定类型的正文骨架是否完整且非占位；
5. 逐个检查 `domains` 是否来自允许目录并受正文支持，以及是否超过三个、重复或同时选择父子领域；
6. `domains: []`、没有关系、没有可选扩展，都不是阻止保存的错误。

审核问题必须指出卡片、错误位置、具体改法和可由当前材料验证的理由。例如：

> `type` 应从 `model` 改为 `undetermined`：正文只列出政策目标与任务，没有变量或组件间的显式关系、运行规则和可复用推理用途；其他实质类型也均不成立，但该单元仍可独立阅读和复用。

以下不是合格问题：

> 可以考虑增加更多标签；领域可能还不够丰富；建议补充更多案例。

这些只是可选建议，不能触发自动返工。

## 四、历史兼容

旧卡的 `tags/topics` 不做批量静默迁移。系统可以用旧字段推断一个只读展示类型，但任何新保存都写入明确的 `type` 与 `domains`。需要迁移存量卡时，应先生成预览，再由建构任务逐批审核；不得把旧标签直接一对一转换为领域。

# UNO 对话与分析报告功能实施计划

> 文档性质：待评审实施计划
>
> 适用范围：新对话、对话知识积累、定向完善、深度分析报告与 PDF 下载
>
> 相关设计：[对话积累与思考技能设计](UNO-对话积累与思考技能设计.md)、[按方向建构与效果验证](UNO-按方向建构与效果验证.md)、[领域治理方案](UNO-领域治理方案.md)、[当前实现与验证](UNO-当前实现与验证.md)

## 1. 目标与产品决策

UNO 的对话功能不应表现为一组要求用户预先理解和切换的“工作模式”。用户面对的是一条连续对话；系统在内部根据问题、证据需求和用户动作选择不同处理路径，并在需要产生持久结果时进入明确、可恢复、可审阅的任务。

本计划建设四项相互衔接的能力：

1. **日常对话**：快速回答；需要知识依据时，从当前项目关联的知识库中检索并形成有边界的回答。
2. **知识积累**：识别对话中值得保留的知识候选，区分新建、完善既有卡、暂不处理和跳过；只有用户明确确认后才通过 `HarnessGateway` 写入。
3. **定向完善**：围绕用户指定的观点、卡片或问题，补充条件、反例、机制、证据或关系，不以增加卡片数量为目标。
4. **分析报告**：启动独立、持久、默认只读的深度研究任务，经过问题拆解、证据探索、竞争解释、内容审计和版面验证，生成可下载 PDF。

核心边界如下：

- 对话路线是内部执行策略，不是用户必须管理的模式。
- 对话回答、知识写入、分析报告是三种不同结果，不能用一次模型输出混在一起完成。
- 图谱关系用于发现、导航和提出问题，不能自动充当证据。
- 模型提出“新知识”不等于新知识成立。候选必须保留证据、反证、适用条件和不确定性。
- 报告生成默认不修改知识库；报告完成后可以提出知识候选，但仍须单独确认和写入。
- Markdown 继续作为知识语义事实源；任务状态、索引、报告清单和渲染产物均不得成为另一套知识事实。

## 2. 当前基础与缺口

| 能力 | 当前基础 | 主要缺口 |
| --- | --- | --- |
| 普通对话 | 新对话默认使用快速思考；可直接回答或先判定检索意图，再组合知识库上下文回答 | 尚未在真实知识库上形成固定问题集的语义验收；现有检索质量、两次请求成本与延迟需要基线数据 |
| 项目知识检索 | 可读取项目关联的多个知识库；支持卡片、领域、关系和 Buffer 片段的有限组合 | 仍以词法匹配和有限关系扩展为主；跨库同名、证据独立性、反例召回和覆盖判断需要加强 |
| 对话知识积累 | 已有设计文档、历史技能与 Gateway 写入基础 | 快速对话运行时尚未形成统一的候选、预览、确认、恢复和收据流程 |
| 定向完善 | Gateway、草稿和卡片版本机制可复用 | 缺少面向对话的“完善既有卡”事务，以及局部变化的审核与回滚契约 |
| 分析流程 | 存在早期协调测试和报告概念 | 尚无独立报告任务、证据账本、正式 OutBox 产物、PDF 渲染、下载与视觉验收链路 |
| 会话恢复 | 原生会话与事件机制可承载归属和冷恢复 | 产出事务与报告任务不能依赖前端临时状态；需明确权威状态和恢复入口 |

第一阶段不把“已有局部代码”视为“能力已上线”。每项能力分别验收源码、程序测试、真实模型效果、实际服务加载和用户可见交互。

## 3. 总体架构

### 3.1 四层职责

| 层级 | 职责 | 不承担的职责 |
| --- | --- | --- |
| 会话层 | 保存对话归属、用户消息、回答、任务入口和事件引用 | 不直接写卡，不把聊天历史当作知识来源 |
| 证据层 | 判断是否需要检索，冻结检索范围，返回卡片、来源、关系和缺口 | 不宣称检索结果已证明结论，不直接产出知识写入 |
| 产出事务层 | 管理知识候选、定向完善、用户确认、Gateway 提交、收据和恢复 | 不承担长篇报告排版，不绕过授权和版本冲突 |
| 报告产物层 | 管理深度研究、论点证据账本、内容审计、Markdown、PDF、下载与版本 | 默认不修改知识库，不把 PDF 变成知识事实源 |

### 3.2 主流程

```text
用户消息
  ├─ 无需资料 ───────────────→ 直接回答
  ├─ 需要资料 ─→ 有界检索 ───→ 有依据的回答
  ├─ 用户要求保留/完善知识 ──→ 产出事务 ─→ 预览 ─→ 用户确认 ─→ Gateway
  └─ 用户要求深度分析报告 ──→ 报告任务 ─→ 研究/审计 ─→ Markdown ─→ PDF ─→ 下载
                                                        └→ 可选知识候选
```

### 3.3 路线与能力分离

“直接回答、知识库检索、领域辅助、关系探索、反证搜索”属于内部思考路线；“保存为知识、完善卡片、生成报告”属于会改变持久状态或生成正式产物的能力。前者可以自动选择，后者必须有清楚的用户动作、进度、结果和失败边界。

## 4. 用户体验设计

### 4.1 日常对话

默认界面保持一个输入框，不要求用户选择“快速、深入、涌现”等模式。

回答呈现遵循以下规则：

- 无需知识库时直接回答，不制造检索过程。
- 使用知识库时，回答应能展开查看本次实际使用的卡片与来源。
- 证据不足时明确区分：已有支持、合理推断、待验证假设和未知。
- 多库检索时显示证据来自哪个知识库，避免跨库同名卡片混淆。
- 回答下方最多提供与当前结果直接相关的动作，例如“整理为知识”“完善已有卡”“生成分析报告”，不常驻展示复杂路线控制。

### 4.2 对话中的知识候选

系统可以自动判断本轮是否存在值得保留的内容，但只显示轻量提示，不自动建立草稿或写卡。用户点击“整理为知识”后，才创建可恢复的产出事务。

候选必须先判断处置方式：

- **新建**：形成了知识库中没有的、完整且可复用的知识对象。
- **完善**：主要价值是为既有卡补充条件、反例、证据、机制或关系。
- **暂缓**：有潜在价值，但证据、边界或来源仍不足。
- **跳过**：只是重复、聊天性表达、无稳定对象，或不值得进入知识库。

预览必须展示：

- 候选标题、主类型和建议领域；
- 核心陈述与适用边界；
- 支持证据、反证或竞争解释；
- 来源角色；
- 拟新建或拟修改的卡片；
- 拟建立的关系及其依据；
- 写入目标知识库；
- 本次修改前的版本以及预计变化。

用户确认后，事务通过 `HarnessGateway` 提交。版本冲突、权限变化或来源失效时返回预览重新处理，不静默覆盖。

### 4.3 定向完善

用户可以从回答、卡片详情或候选预览中发起“完善这张卡”。完善任务只修改明确范围，例如：

- 增加适用条件；
- 补充反例或失败情形；
- 解释因果机制；
- 补充原始来源锚点；
- 修正关系含义；
- 将一个过宽陈述拆成更准确的知识对象。

完善任务冻结目标卡 ID、版本、允许修改的字段和证据范围。模型只生成拟修改部分；审核只检查实际变化；最终仍由用户确认和 Gateway 提交。

### 4.4 分析报告

“生成分析报告”不是把当前聊天打印成 PDF，而是启动一个独立任务。启动面板至少确认：

- 核心问题；
- 报告用途和读者；
- 研究范围与不包含内容；
- 使用的项目知识库；
- 时间截点；
- 报告类型；
- 可用请求预算；
- 是否允许使用外部资料。第一版默认不允许，除非已经接入并能保存真实来源状态。

任务卡持续显示阶段、已检查范围、关键缺口、请求消耗和可恢复状态。用户可以离开页面、冷启动后继续查看，也可以暂停、继续或取消。停止意图到达后不得再发起新请求或写入产物版本。

## 5. 关键数据契约

### 5.1 对话产出事务 `ConversationOutcomeOperation`

```json
{
  "operation_id": "stable-id",
  "kind": "capture | refine",
  "conversation_id": "conversation-id",
  "request_message_id": "message-id",
  "project_id": "project-id",
  "read_knowledge_base_ids": ["kb-id"],
  "write_knowledge_base_id": "kb-id",
  "status": "preparing",
  "allowed_actions": ["create_card", "update_card", "create_relation"],
  "request_budget": { "limit": 4, "used": 0 },
  "evidence_anchors": [],
  "candidate": null,
  "target_revisions": {},
  "draft_hash": null,
  "receipts": [],
  "created_at": "ISO-8601",
  "updated_at": "ISO-8601"
}
```

事务状态是可重建运行记录，不是知识事实。候选正文尚未提交时不得进入正式卡片目录、检索或领域治理。

### 5.2 知识候选 `InsightCandidate`

```json
{
  "disposition": "create | enrich | deferred | skip",
  "knowledge_object": {
    "title": "...",
    "type": "claim",
    "domains": [],
    "statement": "...",
    "conditions": [],
    "counterevidence": [],
    "unknowns": []
  },
  "source_roles": [
    { "role": "knowledge_card | source_material | user_contribution | model_synthesis", "ref": "..." }
  ],
  "target_card_id": null,
  "proposed_relations": [],
  "novelty_basis": "...",
  "limitations": []
}
```

`model_synthesis` 只能说明内容由模型综合形成，不能替代支持证据。用户在对话中的新陈述可以保存为 `user_contribution`，但不能冒充原材料或已有卡片中的事实。

### 5.3 证据锚点 `EvidenceAnchor`

每个可核验论点使用稳定锚点，而不是只保存一段容易漂移的引用文本：

```json
{
  "knowledge_base_id": "kb-id",
  "source_kind": "card | archive_unit | buffer | external",
  "source_id": "stable-id",
  "revision": "revision-or-hash",
  "locator": "section-or-page",
  "role": "support | counter | boundary | context",
  "excerpt_hash": "sha256",
  "availability": "available | missing | valid-empty",
  "captured_at": "ISO-8601"
}
```

外部资料尚未接入时不生成伪造的 `external` 锚点。来源缺失保持 `missing`，不能用旧资料或模型常识静默回填。

### 5.4 报告任务 `ReportJob`

```json
{
  "report_id": "stable-id",
  "conversation_id": "conversation-id",
  "project_id": "project-id",
  "goal": "...",
  "audience": "...",
  "purpose": "...",
  "report_type": "decision | research | comparison | diagnostic",
  "scope": { "included": [], "excluded": [], "cutoff": "..." },
  "knowledge_snapshots": [],
  "request_budget": { "limit": 12, "used": 0 },
  "scope_status": "draft",
  "research_status": "pending",
  "content_status": "pending",
  "render_status": "pending",
  "delivery_status": "pending",
  "claims": [],
  "unresolved_questions": [],
  "artifact_version": 0,
  "created_at": "ISO-8601",
  "updated_at": "ISO-8601"
}
```

研究完成、内容完成、PDF 渲染完成和下载可用是四个不同事实。不得以其中一个状态替代其他状态。

### 5.5 报告产物 `ReportArtifact`

每个版本不可变，建议保存为：

```text
04-OutBox/reports/<report-id>/<version>/
  报告.md
  报告.pdf
  manifest.json
  sources.json
```

- `报告.md`：报告正文的权威可编辑产物。
- `报告.pdf`：由该版本 Markdown 确定性渲染的下载产物。
- `manifest.json`：任务、范围、版本、生成时间、哈希和渲染状态。
- `sources.json`：实际使用的证据锚点、可用状态和论点引用映射。

知识库后续变化不能静默改写已完成报告。用户要求更新时创建新版本，并重新运行受影响的研究与审计步骤。

## 6. 状态机与恢复

### 6.1 知识产出事务

```text
preparing
  → awaiting_confirmation
  → committing
  → completed

任一阶段可进入 needs_attention / cancelled
```

- `preparing`：冻结范围、检索证据、形成候选和预览。
- `awaiting_confirmation`：禁止写入，等待用户确认或修改。
- `committing`：Gateway 原子提交；重复请求必须幂等。
- `completed`：保存真实收据并关联回对话消息。
- `needs_attention`：版本冲突、权限、来源或格式问题需要处理。

### 6.2 报告任务

```text
scoping → researching → synthesizing → auditing → rendering → completed
    └──────────────→ paused / needs_attention / cancelled / failed
```

恢复规则：

- 所有阶段从已保存快照继续，不重新消耗已经完成的请求。
- 暂停和继续不重置预算、论点账本或来源状态。
- 内容审计只返修有明确问题的章节或论点，不整份无限重写。
- 渲染失败不触发重新研究；只修复模板、字体、分页或文件生成问题。
- 下载失败不把报告改为研究失败；保留已完成产物并单独恢复交付。

## 7. 对话检索与知识涌现方法

### 7.1 普通对话保持轻量

现有快速路线在建立真实基线前不整体替换。先记录：

- 是否判断需要检索；
- 实际读取了哪些知识库与卡片；
- 使用的字符、token、请求次数和延迟；
- 回答中的主要结论能否回到证据；
- 是否漏掉关键反例、条件或既有相近卡片。

随后对比两种实现：

1. 当前“意图判断请求 + 检索 + 回答请求”；
2. 宿主确定性判断候选范围，模型一次完成有依据回答。

只有在同一问题集、同一模型、同一知识快照下证明质量不降，并显著减少延迟或 token，才切换默认路径。

### 7.2 “涌现”分为四类结果

对话和报告中发现的潜在知识统一归为：

1. **重组**：把分散卡片组合成更可用的解释，但不产生超出证据的新断言。
2. **边界发现**：找到一个结论成立或失败的条件、反例和适用范围。
3. **关系发现**：发现两张知识对象间有明确用途的关系，并能说明关系依据。
4. **新主张或机制**：形成原库中没有的可检验解释，必须明确标记综合性质、不确定性和验证要求。

前三类通常优先完善既有卡或关系。第四类才更可能新建卡片，但不能因“听起来新颖”自动写入。

### 7.3 图谱只提供发现信号

共享来源、显式互指、关系路径、领域和语义近似可以帮助召回候选；它们不证明候选之间存在因果、支持或挑战关系。关系写入必须有独立的关系陈述与依据，并区分 `basis=source` 和 `basis=navigation`。

### 7.4 报告采用问题驱动的有界研究

报告任务不固定遍历整张图谱，而是维护“论点—证据—缺口”账本：

1. 把核心问题拆成有限的决策相关子问题。
2. 为每个子问题形成初步论点和需要的证据类型。
3. 优先检索能改变结论的支持、反证、边界和替代解释。
4. 每轮根据未解决问题决定下一次检索，而不是重复扩大上下文。
5. 达到充分性门槛、预算上限、无新有效证据或用户停止时结束研究。

“充分探索”不是遍历全部卡片，而是满足：

- 主要结论有可追溯支持；
- 至少检查重要竞争解释和反证；
- 关键适用边界被说明；
- 仍然未知的内容被保留；
- 新一轮检索已很难改变核心判断，或预算边界已经明确到达。

默认只使用一条主分析路线，并在高风险结论上增加一次挑战性检查。第一版不建设多个代理重复阅读同一材料的常驻二审队列。

## 8. 分析报告内容规范

### 8.1 通用结构

1. 封面与报告信息；
2. 执行摘要；
3. 问题、用途、范围与时间截点；
4. 核心结论、置信程度与决策含义；
5. 分主题分析章节；
6. 竞争解释、反证与适用边界；
7. 未知项、风险与后续观察信号；
8. 方法、材料范围与限制；
9. 来源与附录。

### 8.2 报告类型

| 类型 | 重点 | 典型附加结构 |
| --- | --- | --- |
| 决策报告 | 可选方案、取舍和行动条件 | 方案矩阵、触发条件、退出条件 |
| 研究报告 | 解释、证据和知识缺口 | 文献/知识分布、论点图、待验证问题 |
| 比较报告 | 统一维度下的差异 | 对比表、共同点、不可比项 |
| 诊断报告 | 症状、原因和验证 | 原因树、证据强弱、排查顺序 |

### 8.3 论点引用

正文中的重要结论必须映射到 `sources.json` 中的锚点。多个卡片都来自同一原始材料时，报告不能把它们误算成多个独立来源。若只是模型推断，应在正文以“推断”或“假设”表达，并在限制部分给出验证条件。

## 9. PDF 生成与下载

### 9.1 渲染原则

- 先完成和冻结该版本 `报告.md`，再进行排版；模型不直接生成二进制 PDF。
- 渲染器必须嵌入可分发的中文字体，并记录字体、模板和渲染器版本。
- 长表格、代码块、脚注、链接、标题孤行和跨页段落应有确定性规则。
- PDF 生成不消耗模型请求；渲染错误不能触发内容重写。
- 下载文件名使用可读中文标题、日期和短报告 ID，并对不安全字符做确定性清洗。

### 9.2 技术验收

每个 PDF 版本完成以下检查：

1. 使用 PDF 解析器检查页数、元数据、可提取文本和文件完整性。
2. 使用 Poppler 将每一页渲染为 PNG。
3. 检查缺字、乱码、文字溢出、重叠、裁切、空白页、孤立标题和表格断裂。
4. 检查目录、页码、内部链接与来源链接。
5. 对桌面下载、重复下载和冷启动后下载进行实际交互验证。

建议使用工作区已提供的 Python 运行时和 `reportlab`、`pypdf`、`pdfplumber`，以 Poppler `pdftoppm` 完成逐页渲染。实现前固定字体许可和随程序分发方式。

### 9.3 交付状态

前端分别显示：

- 内容已完成；
- PDF 正在生成；
- PDF 生成失败，可重试；
- 文件可下载；
- 下载交付失败，但产物仍保留。

不得在只生成 Markdown 时显示“PDF 已完成”，也不得在浏览器开始下载时宣称用户已成功保存文件。

## 11. 分阶段实施

### 阶段 0：建立可复现基线

**目标**：在当前大量并行改动存在的情况下，确定本功能的可验证起点。

实施内容：

- 使用隔离工作副本或冻结文件清单，记录本计划涉及的代码、测试、运行目录和端口。
- 修复或隔离现有测试夹具与实际凭据接口不一致的问题，使对话专项回归结果可解释。
- 建立普通对话固定问题集和当前性能记录，不改变默认行为。
- 确认实际服务健康标记、构建产物和前端入口来自同一工作区。

验收：

- 同一提交、同一配置能够重复运行专项测试。
- 固定问题集保存输入、知识快照、模型、请求数、token、延迟、回答和人工判定。
- 不访问或修改真实知识实例。

撤回：仅删除本功能的测试产物和隔离运行目录，不覆盖工作区其他改动。

### 阶段 1：对话证据基线与可观测性

**目标**：先知道当前对话何时好、何时漏、成本多少。

实施内容：

- 为快速对话记录路线、检索范围、证据 ID、上下文字符、请求数、token 和耗时。
- 建立 24–32 个固定问题，覆盖无需检索、单卡、多卡、关系、反例、跨库、证据不足和历史污染。
- 增加回答证据展开界面，但不改变知识写入。
- 对比两次请求与一次请求候选方案。

验收：

- 每个引用都能回到本轮实际读取的卡片或材料。
- 未读取的信息不能在界面中显示为“来自知识库”。
- 多库结果保留库 ID，不发生同名覆盖。
- 基线报告能同时呈现质量、token 和延迟，不只统计成功率。

### 阶段 2：知识积累与定向完善纵向切片

**目标**：打通“对话发现 → 候选 → 预览 → 确认 → Gateway → 冷恢复后可使用”的最小闭环。

实施内容：

- 实现产出事务、知识候选和证据锚点契约。
- 实现新建、完善、暂缓、跳过四类处置。
- 新建与完善共用确认界面，但使用不同 Gateway 操作。
- 保存版本冲突、幂等、回滚和真实收据。
- 增加冷启动恢复和取消行为。

初始请求上限设为每个事务最多 4 次，属于可用上限而非固定消耗：候选准备、必要审核和一次局部修复。无问题时不得为耗尽额度而增加请求。

验收：

- 未点击确认时，正式知识目录零变化。
- 同一确认请求重复发送不会重复建卡或重复修改。
- 完善任务只改变预览中列出的字段与关系。
- 冷启动后仍可确认、取消或查看已完成收据。
- 新知识在后续对话中能被正确召回；它的条件、反例和来源角色没有丢失。

### 阶段 3：报告研究任务与 Markdown 产物

**目标**：先证明研究流程和内容结构成立，再进入 PDF 排版。

实施内容：

- 实现报告任务状态、知识快照、问题拆解和论点证据账本。
- 建立决策、研究、比较和诊断四类模板。
- 实现支持、反证、边界、未知和来源独立性检查。
- 实现一次独立内容审计与有问题章节的局部返修。
- 输出版本化 `报告.md`、`manifest.json` 和 `sources.json`。

初始默认上限为 12 次模型请求，建议分配为：范围与计划 1 次、证据探索与综合最多 8 次、成稿 1 次、独立审计 1 次、必要局部修复 1 次。具体使用量由任务需要决定，恢复不重置历史消耗。

验收：

- 核心结论逐项映射到证据或明确标记为推断。
- 重要竞争解释至少被检查一次，找不到材料时记录为缺口。
- 同源卡片不会被误计为多份独立证据。
- 达到预算上限时能产出明确的部分报告或需求关注状态，不伪装成充分研究。
- 任务暂停、继续和冷恢复不重复已完成请求。

### 阶段 4：PDF 渲染、视觉质检与下载

**目标**：把冻结的 Markdown 版本稳定转换为可交付 PDF。

实施内容：

- 固定中文字体、页面模板、目录、页眉页脚和引用样式。
- 实现 Markdown 到 PDF 的确定性渲染。
- 使用解析器和逐页图片执行自动检查。
- 增加报告预览、下载、失败重试和版本列表。
- 将渲染器、模板和字体版本写入 manifest。

验收：

- 相同 Markdown、模板和字体生成相同内容哈希的稳定产物。
- 每页都能渲染为图片，中文可提取且无缺字。
- 长标题、长表格、链接、脚注、代码和连续中文段落均无裁切或重叠。
- Windows 常用 PDF 阅读器和浏览器下载均可打开。
- 渲染失败可以单独恢复，不重新调用模型。

### 阶段 5：报告到知识的可选转化

**目标**：让报告发现可以进入长期知识，但不让报告自动污染知识库。

实施内容：

- 报告完成后最多展示 1–3 个高价值知识候选。
- 每个候选重新执行新建/完善/暂缓/跳过判断。
- 卡片继承原始证据锚点；报告只作为综合产物引用，不能替代原始来源。
- 复用阶段 2 的确认和 Gateway 提交流程。

验收：

- 完成报告不会自动创建或修改卡片。
- 候选被拒绝或暂缓不影响报告版本与下载。
- 写入后的卡片能够追溯到报告使用的原始材料，而不是只指向 PDF。

### 阶段 6：检索与方法优化

**目标**：在已有固定评测和真实使用记录后，优化成本与效果。

候选方向：

- 领域辅助召回和反例专用召回；
- 一次请求替代普通对话的意图判断请求；
- 更好的跨库去重和来源独立性判断；
- 从用户确认、修改和跳过中形成可审计偏好，但不自动改写核心提示词或审核规则；
- 对报告充分性门槛进行类型化调整。

只有通过同题、同模型、同快照对比后才进入默认路径。方法学习只记录可解释偏好，不保存隐藏思维链，不建设无人监督的自我修改系统。

## 12. 测试与验收体系

### 12.1 程序测试

- 契约解析、状态迁移、非法状态拒绝；
- 幂等提交、版本冲突、原子回滚和真实收据；
- 多库 ID、来源角色和证据锚点；
- 请求预算、暂停、继续、取消和迟到响应；
- 报告版本不可变、路径范围和下载授权；
- Markdown、manifest、sources 与 PDF 哈希一致性；
- PDF 文本提取、逐页渲染和错误分类。

### 12.2 前端测试

- 普通回答、证据展开和证据不足状态；
- 候选提示、预览、确认、冲突、取消和完成收据；
- 报告设置、任务进度、暂停/继续、局部失败和下载；
- 页面刷新、应用冷启动和会话切换后的恢复；
- 桌面宽屏与窄屏交互；
- 键盘操作、焦点、屏幕阅读器名称和减少动态效果。

### 12.3 真实模型评测

评测必须在隔离知识库副本上执行，并保存模型、请求、原始响应、快照和人工判定。

| 能力 | 核心指标 |
| --- | --- |
| 日常对话 | 问题相关性、证据支持率、关键遗漏、反例/边界召回、延迟、token |
| 知识候选 | 新建/完善/暂缓/跳过判断、重复率、边界保留、来源角色准确性 |
| 定向完善 | 局部性、事实忠实度、版本安全、关系含义准确性 |
| 分析报告 | 核心论点支持、竞争解释覆盖、未知项保留、来源独立性、结构可读性、成本 |
| 报告转知识 | 候选价值、原始来源继承、确认后检索可用性 |

模型审核通过不等于语义质量得到证明。关键样本需要人工盲审，并保留反例和失败样本。

### 12.4 端到端验收场景

至少通过以下场景：

1. 用户提出无需知识库的问题，系统一次回答且不产生伪引用。
2. 用户提出需要多张卡片的问题，回答能展示实际证据和不确定性。
3. 对话形成有条件的新假设，系统建议完善既有卡而非盲目新建。
4. 用户确认完善，Gateway 写入；重复确认不重复提交；冷启动后可见收据。
5. 用户要求深度分析，任务中途暂停并冷启动恢复，已完成研究不重复。
6. 报告在预算内完成 Markdown、审计、PDF 和下载，逐页视觉检查通过。
7. 报告存在证据缺口时，正文明确披露且状态不伪装为全面证明。
8. 用户从报告选择一个候选写入，卡片追溯到原始证据；其余候选保持未写入。

## 13. 安全、权限与不可做事项

- 不自动写卡、不自动建域、不自动修改正式知识关系。
- 不把整个对话历史当作来源材料；只保存经用户确认的贡献和实际证据。
- 不保存或展示隐藏思维链，只保存问题拆解、检索记录、论点、证据、缺口和结果。
- 不无界遍历知识图谱，不用连边数量作为涌现或研究质量指标。
- 不在第一版伪装已使用外部网络资料；外部检索必须另有真实接入、来源状态和许可。
- 不把报告 PDF 当作知识库唯一事实源，也不从 PDF 反向覆盖 Markdown。
- 不为新功能迁移、改签或自动重放历史会话、历史编译任务和历史建构任务。
- 不默认建立多代理并行二审；先证明单主线、独立审核和有界挑战检查的效果与成本。
- 不因报告渲染失败重新消耗模型请求，不因下载失败重写内容。
- 不以生成卡片数、报告页数或调用次数作为完成标准。

## 14. 首个纵向切片

建议先完成一个能同时验证产品边界和底层契约的闭环：

1. 用户在普通对话中提出一个需要两到三张现有卡片才能回答的问题。
2. 系统给出带来源、条件和未知项的回答。
3. 回答中出现一个有价值但尚未成立的新假设，系统只显示“可整理为知识”。
4. 用户点击后，系统判断应完善一张既有卡，展示局部修改、证据和版本。
5. 用户确认，Gateway 完成幂等写入并返回收据。
6. 应用冷启动后，对话、事务、收据和新版本仍然一致。
7. 用户基于同一问题启动分析报告，任务生成 Markdown、来源清单和 PDF。
8. 用户下载 PDF；报告提出的其他候选保持未写入，除非用户再次确认。

这个切片同时覆盖普通回答、检索证据、知识处置、写入边界、状态恢复、报告研究、PDF 交付和报告到知识的权限隔离。通过后再扩展到更多报告类型、跨库复杂检索和方法学习。

## 15. 完成定义

本计划所描述的对话能力只有在以下条件同时满足时才算完成：

- 用户无需理解内部路线即可连续对话和发起明确产出；
- 普通回答在固定问题集上具有可接受的质量、成本和延迟；
- 知识候选能够可靠区分新建、完善、暂缓和跳过；
- 所有知识写入都经过预览、明确确认和 Gateway 收据；
- 报告任务可以暂停、恢复、审计、版本化和下载；
- 报告的重要结论可追溯，反证、边界和未知项没有被抹平；
- PDF 已通过解析与逐页渲染验收，而不只是文件成功生成；
- 冷启动、重复请求、冲突、失败和用户停止均有确定行为；
- 真实模型评测和实际运行服务分别通过验证，程序测试结果不代替它们。

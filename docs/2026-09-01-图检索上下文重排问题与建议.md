# 2026-09-01 图检索上下文重排问题与建议

> 核对日期：2026-09-01  
> 状态：第一版联合召回与可解释上下文计划已于 2026-09-01 实施；向量召回与来源层统一竞争尚未实现
> 范围：思维体在检索知识卡片、沿图扩展并组装回答上下文时的候选排序，不改变 Markdown 事实源、卡片契约或 Harness 写入主权

## 一、结论

  当前项目已经把 `retrieve` 与 `graph_search` 接到同一个首轮引擎：直接召回后沿 ready 的 argument/context 关系扩展最多两跳，再结合当前问题、有限正文语义、关系说明、距离、论证角色和冗余形成上下文计划。模型能够看到入选理由、临时角色、阅读槽、来源下钻提示、角色缺口与排除理由；`graph_walk` 继续负责对候选路径做真实核验。

  这构成第一版确定性的二阶段重排与上下文编排，但还不是完整语义检索系统：没有向量召回，章节来源尚未与卡片进入同一候选竞争，临时角色仍由卡片类型、章节标题和关系类型推断，真实 Precision 与 Recall 仍需固定案例验证。

  近期不应为了这个问题直接引入向量数据库。更直接的改进已经落实为基于现有 Markdown、语义词片和图关系的轻量、可解释重排；只有评测证明第一阶段存在稳定的语义漏召回，再增加向量召回通道。

## 二、这里所说的“重排”是什么

  排序与重排不是同一件事。首次排序是在全库或指定范围中快速找到候选；重排是在较宽候选集已经产生以后，使用更丰富但成本更高的信号重新判断哪些内容最适合进入本轮有限上下文。

  对本项目而言，完整过程应当区分为：

1. **召回**：由词面检索、领域成员检索、图邻居和后续可选的语义检索产生候选。
2. **重排**：根据当前问题以及候选的正文语义、关系含义、证据状态和来源覆盖重新打分。
3. **上下文编排**：避免只返回同类、重复或高连接节点，按回答需要选择核心命题、机制、证据、冲突、边界和待追溯来源。
4. **深读与追溯**：读取被选卡片；涉及数字、历史事实、经验结果或争议判断时继续追溯章节来源或图像说明。

  只有第二步和第三步稳定存在，才适合称为“图检索的上下文重排”。

## 三、第一版已经具备什么

| 当前机制 | 实际作用 | 是否属于查询相关二次重排 |
|---|---|---|
| 查询分句与词片 | 去除提问套语并切开连接关系，保留有限中文 2～4 字侧面 | 召回前处理 |
| 直接候选召回 | 对标题、别名、有限正文和元数据进行查询相关评分 | 首次排序 |
| 最多两跳图扩展 | 从高相关非领域卡沿 ready argument/context 边形成候选，保留路径 | 候选扩展 |
| 联合重排 | 同时考虑问题相关性、图亲和度、关系说明、距离和枢纽惩罚 | 是 |
| 上下文编排 | 按核心命题、机制、证据、反方、边界和情境覆盖选取并抑制重复 | 是 |
| 来源下钻提示 | 对数字、多来源或证据性候选标记 `source_trace_required` | 是，属于执行计划 |
| `graph_walk` | 对计划建议的关系平面与 1～3 跳真实路径做核验 | 否，属于后续结构观察 |

  当前实现可在 [`graph-ops.js`](../packages/nexogenesis-tools/lib/graph-ops.js) 的 `retrieveContext` 与 [`index.js`](../packages/nexogenesis-tools/lib/index.js) 的 `retrieve`、`graph_search` 注册中核对；现行使用边界见 [`.agent/reference/retrieval-design.md`](../.agent/reference/retrieval-design.md)。

## 四、当前缺口及其影响

### 4.1 查询相关图扩展已经建立，但精度尚待真实案例校准

  第一版已经让扩展节点重新接受问题相关性、关系说明和距离评分，不再只按发现顺序截取。当前真实回放能够在商品周期问题中保留一至两跳候选，同时避免 legacy 旧边参与扩展。

  尚未闭合的是 Precision 校准：通用正文可能因同时包含多个查询概念而取得较高分；图候选也不能仅因关系真实就强制占位。`graph_walk` 仍然只负责回答“沿合法关系实际走到哪里”，不能替代查询相关重排。

### 4.2 临时论证角色已经输出，但仍是启发式判断

  当前上下文计划已区分以下临时角色：

- 直接回答问题的核心命题；
- 解释命题如何成立的机制；
- 支持或挑战命题的证据；
- 实质冲突和反方观点；
- 成立条件、适用范围和失效边界；
- 必须继续追溯的章节来源或知识图像。

  这些角色来自卡片类型、正文标题和关系类型，只用于本轮阅读编排，不是永久本体，也不等于语义裁决。真实回放仍可能把带有“限制”章节但对题较弱的卡片选为 boundary，因此后续评测必须同时检查角色存在与角色相关性。

### 4.3 已有基础去重与覆盖约束，尚无来源级多样性

  第一版会抑制语义词片高度重复且没有新增角色的候选，并在计划中报告角色与查询侧面缺口。它还不能可靠判断同源转述、跨书独立性或证据口径差异；这些仍由后续 `inspect_evidence_set` 验收，而不是在首轮检索中伪装完成。

### 4.4 来源层尚未进入统一候选竞争

  主题编译已经把章节来源和图像说明保存在 `05-Buffer/themes/<theme>/`，但当前图检索重排不会让“知识卡片候选”和“章节来源候选”在同一问题下比较。思维体必须先命中或读取卡片，再根据来源指针主动下钻；若卡片粒度不足或来源追溯未被触发，原书中可引用的细节就不会自然进入上下文。

### 4.5 工程计划已经提供，但模型仍须执行

  Agent 现在可以直接消费 `context_plan` 的入选理由、阅读槽、覆盖缺口和 `graph_walk` 参数，不必从两个首轮工具和零散邻域中自行拼接上下文。但计划不会自动代替路径核验、正文精读、来源追溯和证据验收；这些是否发生仍由 CognitiveRun 与 Skill 完成门检查。

## 五、已实施的最小实现

  当前实现把只读的候选重排与上下文计划直接接入现有 `retrieve`，并让 `graph_search` 复用同一引擎。它不创建新的事实层，不自动改写卡片，只为本轮阅读顺序和上下文预算提供可解释建议。

### 5.1 输入

- 当前问题及可选的问题类型，例如解释、比较、评估、历史追溯或政策判断；
- 词面检索直接命中；
- 受控图遍历产生的邻居和关系路径；
- 候选卡片的必要 OPS 语义单元或短摘录；
- 卡片来源指针，以及可选的章节来源、图像说明候选；
- 模式预算，例如最大精读卡数、来源下钻数和允许的图跳数。

### 5.2 第一版可使用的信号

  第一版采用现有数据即可，不需要向量库，也不应先引入不可解释的总分。建议保留分项分数和选择理由，再用有限规则产生最终顺序。

| 信号 | 判断对象 | 目的 |
|---|---|---|
| 问题词与标题、OPS 单元、正文摘录的匹配 | 卡片或来源片段 | 判断直接相关性 |
| 关系类型、方向与关系说明 | 图邻居 | 判断这条边为什么对当前问题有用 |
| 卡片类型与问题类型的适配 | 命题、模型、证据、冲突等 | 避免所有候选承担同一角色 |
| relation readiness 与来源可追溯性 | 卡片、边和来源 | 优先使用可核验材料 |
| 适用范围、时间、地区、样本和口径 | 证据与政策结论 | 防止条件性结论被普遍化 |
| 与已选候选的语义槽重复度 | 全部候选 | 减少同义重复占位 |
| 学派、来源、证据方向和关系角色差异 | 全部候选 | 保留冲突和互补结构 |
| 枢纽惩罚与距离成本 | 图候选 | 防止通用节点和远距离弱相关路径吞噬预算 |
| 本轮是否已读及 `on_topic_new` | 全部候选 | 减少循环读取 |

  OPS 语义单元已有稳定定位价值，应优先用于正文匹配和选择理由。第一版只读取少量候选的必要单元，避免为了重排先把大量全文塞入上下文。

### 5.3 输出

  输出不应只是一个总分列表，而应是可供 Agent 执行和检查的上下文计划：

```yaml
query: "本轮问题"
selected:
  - card_id: "..."
    role: "core_claim"
    reasons:
      - "OPS:mechanism 与问题中的因果条件直接对应"
      - "通过 ready supports 边连接到证据卡"
    read_units: ["claim", "mechanism", "boundary"]
    source_trace_required: false
  - card_id: "..."
    role: "counterevidence"
    reasons:
      - "与核心命题存在显式 conflicts-with 关系"
    read_units: ["evidence", "limitations"]
    source_trace_required: true
excluded:
  - card_id: "..."
    reason: "与已选核心卡内容高度重复，且没有新增证据或边界"
coverage:
  core_claim: true
  mechanism: true
  evidence: true
  conflict: true
  boundary: false
gaps:
  - "缺少适用于中国市场样本的边界材料"
```

  `role` 名称只是输出示例，不要求立即扩展卡片本体类型或关系本体。它描述的是本轮上下文中的临时用途，不应写回 Markdown 成为永久事实。

### 5.4 当前执行顺序

1. 普通首轮统一使用 `retrieve`；只有高级元数据筛选才使用 `graph_search`。
2. 引擎内部以高相关非领域卡为种子，沿 ready argument/context 边扩展最多两跳。
3. 引擎对直接与图候选联合重排，输出角色覆盖、缺口、阅读槽、排除理由和路径建议。
4. Agent 用 `graph_walk` 核验建议路径，只精读计划入选且对结论必要的卡片。
5. 对数字、历史事件、经验结论、政策效果、关键争议或卡片信息不足之处，下钻到章节来源或图像说明。
6. 若重排结果明确显示召回缺口，再换查询角度或扩展检索；不要用远距离弱边填满预算。

## 六、为什么暂不先上向量数据库

  向量检索主要改善“字面不同但语义接近”的候选召回，它不能自动保证候选之间不重复，也不能天然识别一张卡在本轮承担的是证据、冲突还是边界角色。若没有重排和上下文编排，增加向量召回可能只是把更多近义候选送入有限上下文。

  当前已知问题首先发生在候选扩展后的判断和组合阶段，因此先实施可解释重排更直接，改动范围也更小。后续若黄金案例稳定显示：正确卡片或来源片段根本没有进入候选集，而且主要原因是中文同义表达、概念别名或跨领域措辞差异，再增加向量召回。向量索引必须可删除、可重建，Markdown 继续作为唯一语义事实源。

## 七、验收方法

  重排不能只用“结果看起来更聪明”验收。应从真实报告、比较和研判问题中建立小规模固定案例，并分别标注：应召回对象、应进入上下文对象、必须保留的冲突或边界、必须追溯的来源，以及不应占用预算的弱相关枢纽。

### 7.1 最低行为验收

- 同一候选输入与同一问题产生稳定顺序和稳定选择理由；
- 扩展节点能够因与问题无关而被降权，而不是只因关系真实就入选；
- 至少能保留一个与核心命题有实质关系的反证、冲突或失效边界；
- 重复表述不会同时占据多数上下文席位；
- 关系说明为空、关系未 ready 或目标不存在时，不能作为高置信图证据入选；
- 高连接领域卡不能挤占本应留给具体命题和证据的主要预算；
- 数字、历史、经验和政策类回答能够触发来源下钻要求；
- 重排只影响读取和上下文选择，不发生知识卡片写入。

### 7.2 比较指标

| 指标 | 要回答的问题 |
|---|---|
| Recall@候选集 | 正确对象是否在第一阶段被找到 |
| Precision@上下文 | 进入有限上下文的对象是否真正有用 |
| 论证角色覆盖率 | 核心命题、机制、证据、冲突和边界是否按问题需要出现 |
| 冗余率 | 入选对象是否重复表达同一知识 |
| 来源追溯命中率 | 需要原始依据时是否选择了正确章节或图像说明 |
| 关系解释率 | 每个图扩展入选项是否能说明“为什么通过这条边进入” |
| 回答归因正确率 | 最终输出是否区分卡片内容、原始来源与模型推论 |

  评测应把失败定位到召回、重排、深读、来源追溯或生成五个环节。只有 Recall 明显不足，才能把引入向量检索视为有证据的下一步；如果 Recall 已足够而 Precision、角色覆盖或来源追溯较差，应继续修复重排与上下文执行。

## 八、实施边界与撤回方式

  第一版没有新增永久卡片类型、关系类型、领域结构或数据库，没有修改 HarnessGateway 写入契约，也不把重排判断写回知识事实源。它作为 GraphOps 的只读能力和现有检索 Observation 扩展存在，所有排序理由对模型可见。

  若固定案例证明重排没有提高上下文精度，或者读取成本明显高于收益，可以关闭该步骤并退回现有 `retrieve → graph_walk → read_card` 路径；知识卡片、章节来源和关系不会受到影响。这个撤回边界也是第一版优先保持轻量和只读的原因。

## 九、下一步验证

  下一步不继续扩张检索架构，而是从真实思维体任务补一组冻结案例，分别标注应召回、应进入上下文、必须保留的反证或边界、必须追溯的来源和不应占位的弱相关枢纽。第一轮验证联合重排、角色相关性、重复抑制、路径核验和来源下钻是否在真实模型运行中发生。

  完成该基线后，再依据分层指标决策：召回不足则评估向量通道，候选充足但上下文质量不足则继续修复重排，来源细节不足则完善主题来源检索与深读工具。这样能够把不同问题分开处理，避免用一个更大的检索系统掩盖上下文选择缺陷。

# UNO 策略建构服务

> 现行新建构契约：`construction_profile=strategy-driven-v2`、`workflow=uno-construction-v1`、`strategy_contract=construction-strategy-v1`、`review_policy=construction-review-v2`。历史 `direction-driven-v1` 任务保持原协议，不自动改签。

## 入口与策略阶段

用户选择建构侧重、允许操作、知识范围并直接说明目标。宿主先根据用户目标、锚点卡片的词义、来源、领域和既有关系，从当前有效卡片中生成最多 32 张的候选目录；用户明确选择的卡片标为不可丢弃的锚点。候选目录只含 ID、标题、主类型、领域、精简摘要、有限来源标识、有限关系摘要与冻结 revision，不携带整库正文。直接说明为空时仍使用所选主要侧重生成的目标，不得退化为无查询目录。

普通策略建构的第一次模型请求没有工具和历史，只负责制定建构策略与选卡策略。该阶段采用 24,000 Unicode 字符的独立输入上限，不借用执行阶段的 60,000 字符上限；模型只能选择候选目录中的 ID，返回目标、预期改善、允许操作的使用方式、判断规则、证据要求、停止条件、选卡理由、必要的排除理由与最多六张卡的工作包。宿主拒绝未知 ID、丢失锚点、重复选择、越权操作和不完整分组，随后冻结策略、选卡、卡片版本、用户要求和原始响应。没有充分候选时允许不进入写入阶段。全库与领域范围无需用户预选卡片；只有“以指定卡片为锚点”才提交 `card_ids`。

## 持续关系编织

主要侧重为“发现联系”或“综合整理”，并允许新建关系时，新任务启用 `random-focus-semantic-retrieval-v2`。它仍属于同一个 `strategy-driven-v2` 建构服务，不另建 Agent 循环或知识写入通道。历史 `incremental-relation-weaving-v1` 任务继续按原来的孤立卡后知识岛顺序恢复，不在任务中途改签。

新协议把“检查哪里”和“应该与谁比较”明确拆开：

1. 焦点抽样：宿主用任务 ID 作为随机种子，从当前范围内尚未检查的有效卡片中无放回抽取一张焦点卡。相同任务在暂停、失败、重启后保持同一抽样顺序，不同任务产生不同顺序。指定卡片模式只从指定焦点中抽取；全库和领域模式不要求用户预选卡片。
2. 端点召回：焦点冻结后，宿主用 `all-cards-integration-candidates-v1` 从全部有效知识卡中检索端点，不受焦点范围、领域或连通分量限制。召回按共享来源、正文显式互指、语义单元重合、候选关联、类型兼容与既有路径惩罚等信号排序，最多交付五个端点。召回分数只决定比较对象，不是关系成立证据。
3. 拓扑观察：宿主仍计算孤立卡、连通分量、知识岛和最大分量数量，但这些指标只用于诊断、结算展示和独立的拓扑治理，不参与焦点抽样，也不参与端点排序。
4. 模型判断：宿主直接冻结一张焦点卡和最多五个只读端点，不再调用模型复述选卡策略。模型只进行一次关系判断与拟稿，再进行一次独立审核。每轮只允许修改焦点卡，不做对称回写或批量补边。
5. 结算与推进：成功建立关系时，焦点和实际关系端点都视为本任务已经完成一次有效比较；审核拒绝或证据不足时，同一焦点排除已经尝试的端点，最多再换一组候选。第二组仍不能成立时标记 `deferred-exhausted` 并继续其他随机焦点。

没有召回端点时，本轮不调用模型，记录可审计的 `no-selection` 结果并继续下一张焦点卡；这只能说明当前检索闸门没有找到值得比较的候选，不能宣称该卡天然独立。随机抽样、同一领域、标题相似、主图位置和减少孤立数量都不是关系证据，也不能为清空队列制造关系。

连续处理关闭时，每轮结算一张焦点卡后暂停；显式继续从已冻结的随机序列和最新知识版本继续。连续处理开启时，服务逐轮运行，直至当前焦点范围已经无放回检查完毕、用户要求暂停、出现版本或权限冲突，或剩余额度不足以完整启动下一轮执行与审核。完成只表示本任务的随机焦点范围已经检查，不表示全库成为单一连通图，也不证明未命中候选之间不存在语义联系。

## 专用执行流程

每个工作包依次执行：

1. 作者请求：只携带冻结策略、本组完整卡片、必要领域定义和有界来源片段；无工具、无会话历史。工作包不再嵌套重复的策略、选卡和主图 ID 清单。
2. 确定性预检：绑定当前 revision，在任何暂存前完整检查本包的写入范围、操作权限、关系端点、来源引用和字段组合。若有可局部修复问题，只送出问题卡和具体问题；修复后仍不通过的卡延期，不阻塞同包其他卡。
3. 独立审核：只携带策略、作者结论、修改前版本、拟议差异和实际引用附近的有界来源片段，不重复整份修改后正文、整段来源或作者历史，也不重新选卡。
4. 局部修复：每个工作包最多进行一次。若额度已用于作者结论的预检问题，独立审核不再启动第二次修复；否则审核明确拒绝时只修复被拒绝对象及问题，并进行一次独立复核。关系修复只返回被拒绝卡，但宿主仍以原冻结工作包的完整端点集合执行预检；只读端点不会因此变成可写对象。
5. Gateway 结算：审核通过的独立变更组经 `HarnessGateway` 原子提交；未通过对象保留为延期或待修，不能计为完成。

正常工作包使用一次作者请求和一次审核请求。请求分别记录策略、作者、审核、修复和复核阶段；每次请求重新从持久化状态构造，模型推理、回复和工具历史不会进入下一次请求。请求上下文按 Unicode 字符计量，超过 60,000 字符时在外发前停止，不通过提高旧 128 KB 累积历史阈值继续运行。

## 关系、正文与领域边界

- `basis=source` 的新增或修改关系必须给出本次实际交付的当前绑定来源原句。来源标记 `unavailable` 或没有交付 `text` 时禁止输出 `basis=source`；只由两端卡片形成的检索用途使用 `basis=navigation`，不声称原作者已建立该联系。
- 关系起点与目标都必须属于冻结选卡范围。关系从当前修改卡指向 `target`：`specialization` 为当前卡具体化目标卡，`supplement` 为当前卡补充目标卡，`challenge` 为当前卡质疑目标卡，`example` 为当前卡是目标卡的实例，`application` 为当前卡把目标知识用于具体情境；`contrast` 与 `analogy` 为对称比较但仍只保存一条边。作者与审核请求使用同一方向定义。标题相似、同一领域或章节相邻不能独立构成关系。
- 关系单独修改只校验关系差异与端点。旧卡中与本次修改无关的摘要、boundary 或正文结构缺口不阻塞合法关系更新，也不会在发布时被自动补写。
- 正文、主类型、摘要、边界或合并修改必须给出本工作包实际交付的来源原句；不能引入未提供来源。
- 领域归属调整必须单独提交，不能与正文、关系或合并混在同一草稿；仍使用独立领域治理事务。
- 新建卡片、新建领域、领域拆分／合并／改定义不属于当前入口。

## 状态、恢复与兼容

任务阶段为 `strategy_pending → authoring → reviewing → repairing/verifying → publishing → batch_done → done`。任务、策略、模型原始响应、草稿、审核结论、请求预算和 Gateway 收据分别持久化。恢复时复用已经完成的阶段响应和幂等收据，不重放成功模型请求或知识写入。审核后的局部修复若已完整保存但在端点预检中断，更新后的宿主允许显式继续：重新执行确定性预检后只为当前轮进行一次独立复核，不重新请求作者、首次审核或修复；本轮结算后仍按任务原有的连续处理设置运行。若第一步在产生完整策略 JSON 前达到输出上限，失败响应保留；因尚未发生知识写入，用户显式继续后可使用新的恢复轮次重新请求策略，重复无进展仍熔断。

作者、审核、修复或复核返回不符合局部 JSON 契约时使用 `construction-response-recovery-v1`。宿主先做无需语义判断的确定性归一化，例如为明确批准但漏写 `issues` 的审核项补空数组；仍有歧义时，最多追加一次只含失败响应、校验错误和本阶段 Schema 的恢复请求，不附带卡片正文、来源材料、其他候选或历史。恢复结果必须重新通过原检查器；仍失败时任务保留在当前阶段，界面提供“修复执行／审核格式并继续”，显式继续复用已保存的失败响应，不重做已完成阶段。

新服务与图书编译共用模型适配器、供应商请求账本、提示词查看器、任务生命周期、事件总线与 `HarnessGateway`，但不进入原生 Agent 工具循环。当前采用同一 Web Host 内的独立领域服务，不另启端口或复制权限、预算和知识写入基础设施。

界面只有在准备接口同时声明 `uno_construction_service=1`、默认 `strategy-driven-v2`、`relation_weaving_contract=random-focus-semantic-retrieval-v2`、`relation_weaving_focus_selection=job-seeded-random-without-replacement-v1`、`relation_weaving_endpoint_retrieval=all-cards-integration-candidates-v1`、`construction_repair_scope=construction-repair-endpoint-scope-v1`、`construction_response_recovery=construction-response-recovery-v1`、`relation_weaving_max_focus_attempts=2` 和可计数模型时才允许新建任务。健康接口声明相同能力。源码、构建或测试通过不证明当前运行服务已经加载这些标识。

## 验收

- 第一次请求只产生策略和选卡，没有工具、历史或知识写入。
- 关系编织不发送独立策略请求；一轮正常成功只使用作者与独立审核两次模型请求。
- 用户指定锚点不能被模型丢弃；所有已选卡片各进入一个工作包。
- 正常工作包只发送作者和独立审核两个请求；审核问题最多增加一次修复和一次复核。
- 每次请求的 `messages` 固定为本阶段输入，`tools=[]`，没有原生 replay state。
- 关系发现每轮最多六张卡；焦点从当前范围随机无放回抽取，端点从全部有效卡片检索。拓扑统计不得改变焦点或端点顺序。
- 相同任务在恢复时保持抽样顺序；新任务使用不同随机种子。没有检索端点时不调用模型，也不把无候选写成“必然独立”。
- 关系审核拒绝不会留下作者暂存草稿；第一组端点失败后排除已尝试端点再试一组，第二组仍失败则保留待办并继续主线。
- 局部响应格式恢复不携带知识材料且每阶段最多一次；恢复结果仍需通过原校验，不把格式修复当作语义批准。
- 全库自由建构与领域自动选卡无需提交 `card_ids`；指定卡片模式仍要求至少一个有效锚点。
- 关系单独更新不因旧卡无关字段缺失失败，并保持正文逐字不变。
- 未知 ID、版本冲突、越权操作、缺失来源证据、无效 JSON、停止意图和请求预算不足都不能产生新的正式写入。
- 历史 `direction-driven-v1` 和 `incremental-relation-weaving-v1` 任务继续按原状态读取或恢复，不在任务中途迁移。

程序验证使用临时合成知识库，不读取或改写真实知识实例。真实模型选卡质量、语义审核稳定性、费用和延迟必须在用户授权的隔离副本中另行评测。

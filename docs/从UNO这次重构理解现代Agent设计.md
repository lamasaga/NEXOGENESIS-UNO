# 从 UNO 这次重构理解现代 Agent 设计

日期：2026-09-13。本文根据两轮真实编译审计及随后完成的基础能力修改整理，解释问题、取舍与可迁移的设计原则。实现和测试记录见 [Agent 基础能力改进](UNO-Agent基础能力改进.md)。

**这次最重要的教训是：模型的表现，既取决于模型能力，也取决于我们给它怎样的工作环境。** 工具难用、证据缺失、状态含糊时，模型会花大量成本处理工程摩擦；工具可靠、证据适量、任务可恢复时，同一个模型才更容易把精力用于知识判断。

这不意味着“底层做好，质量自然解决”。知识是否忠实、案例是否重要、类比是否有启发，仍需要模型判断和真实样本检验。工程的作用，是减少可避免的错误，让剩下的质量问题能够被准确观察。

## 一、先看真实发生了什么

最近复查的一轮任务中，用户交付了 5 份材料，模型接收 2 份、排除 3 份，最终发布 3 张卡片、1 条关系。过程中发生了 43 次模型请求、86 次工具调用、12 次工具报错；已报告输入约 206 万 tokens，缓存命中率 14.35%。两个正式消化的文章又被分成了四个单元，其中两个只有元数据。

这些数字值得调查，但不能仅凭“2 篇文章用了 43 次请求”，就认定其中多少次一定多余。审核确实补充了有效内容，并区分了采购意向与实际成交、会前预告与会后结果。真正可以确定的浪费来自具体故障：

| 观察到的问题 | 背后的原因 | 本轮处理 |
|---|---|---|
| 状态或检查点工具频繁报错 | 工具返回值没有接上已有的 JSON 规范化入口 | 统一输出协议，失败附带恢复建议 |
| 修改少量内容却需要重新输出卡片 | 省略字段被当作空值，缺少可靠的局部更新语义 | 省略字段保留原值，增加精确补丁 |
| 模型提交过关系，但结果中没有 | 普通写卡分支没有处理关系字段，也没有报错 | 不支持的参数组合明确拒绝，关系使用明确操作 |
| 每次请求的系统提示都不同 | 阶段、剩余预算等动态信息不断改写系统提示 | 固定规则与动态状态分开组织 |
| 暂存问题恢复时又回到前面的步骤 | 恢复主要依赖流程位置，没有充分核对实际遗留对象 | 根据草稿、材料状态和收据恢复原批待办 |
| 审核把可用的跨卡比较删掉 | 把“原作者的论证”与“模型整理的阅读导航”混为一谈 | 保存关系依据，分别说明使用边界 |

这些问题主要发生在 UNO 自建的集成与业务层。已有 Agent Loop 并不缺少继续调用工具的能力，缺的是准确接入和适合当前任务的工具设计。详细原始证据见 [编译复查](2026-09-13-编译复查与开源组件选择.md)。

## 二、Agent 的基本能力：根据结果改变下一步

普通固定流程可以写成：读取文章 → 分类 → 摘要 → 制卡 → 审核。每一步是否有必要，由流程预先决定。

Agent 的关键区别，是模型看到当前结果之后，可以改变下一步：

```text
目标、规则、当前状态和必要证据
              ↓
模型判断：继续读取、搜索、修改、排除、暂存，还是结束？
              ↓
程序执行选定工具，返回结果或可处理的错误
              ↓
保存实际进展，提供新的观察结果
              └────────→ 下一次判断
```

这里的“判断”指选择动作及必要的简短理由，不需要保存模型隐藏的思维过程。

对于 UNO，一篇过期活动通知可能看清标题、日期和相关段落就足以排除；一篇包含关键产业事实的文章值得继续深入。用户选中材料，授权的是“判断这些材料如何处理”，并没有断言“每一篇都值得制卡”。

**自主权来自有意义的选择，以及这些选择能否真正生效。** 如果工具只提供“继续制卡”，或者“排除”也必须全文精读、反复审核，那么界面虽然叫 Agent，实际仍把模型绑在固定流水线上。

但自主也不意味着每一步都要问模型。模型已经决定读取三份材料时，程序可以一次执行三次读取；已经确定某段是广告时，程序可以按定位删除，不需要再问一次“是否开始删除”。

一个实用的判断方法是：**这个环节还有尚未解决的意义判断吗？** 有，就交给模型；没有，就让程序执行。业务流程可以有阶段，阶段内部仍然允许根据新证据调整行动。

## 三、工具是给模型使用的操作界面

我们容易重视人类看见的按钮，却忽略模型也有自己的“界面”：工具说明、参数、返回结果和错误信息。

### 1. 一次操作必须有清楚的含义

设想模型只想把标题“参与机制的相关问题”改成“参与和决策授权”。理想情况下，它只需要提交卡片身份、当前版本和新标题。

旧逻辑中，省略正文可能被解释成正文为空，导致后面补救、重新生成。这不是模型知识不足，而是接口把“我没改这个字段”与“我要清空这个字段”混淆了。

现在局部更新保留省略字段；明确提交空值仍需要接受质量检查。正文修改可以指定唯一匹配的原句和替换文本。如果原句出现多次，程序要求重新定位，而不猜模型想改哪一处。

这体现了 **局部修改（patch）** 的价值：让操作的范围与意图一致，减少重新搬运整张卡片，也降低误改其他内容的概率。

### 2. 成功必须意味着承诺的动作确实执行了

模型曾在普通卡片写入中附带关系参数。程序保存了正文，却忽略关系，然后返回成功。模型因此以为关系已经建立。

现在不支持的组合明确报错。模型可以改用关系操作，并从收据确认保存结果。

**静默忽略通常比明确失败更难修复。** 明确失败还能触发调整；虚假的成功会污染模型对当前世界的认识，影响后续所有决定。

### 3. 错误应该指出最小修复范围

“失败，请重新生成本批”会把一个对象的问题扩大成整批成本。

“文件版本已变化，请读回当前对象后局部修订”提供了可以执行的恢复路径：读取最新对象，理解变化，重做必要修改。

工具接口的完整契约包括：说明、参数约束、实际执行、返回结果、失败恢复。只写一份漂亮的说明，或者只证明内部函数能运行，都不够。

## 四、上下文组织：让模型知道足够的信息，同时不反复搬家

模型每次请求只能依据本次获得的上下文工作。资料保存在磁盘上，不等于模型当前能看到；有“读过”的记录，也不等于关键细节仍留在当前窗口。

UNO 应区分四类信息：

| 信息 | 典型内容 | 合适的组织方式 |
|---|---|---|
| 稳定指令 | 任务目标、类型说明、卡片示例、来源边界 | 固定部分保持稳定，不因一次工具调用而重写 |
| 当前状态 | 当前阶段、剩余预算、检查点、补充要求 | 用动态上下文提供；不能为缓存而隐瞒变化 |
| 当前证据 | 正在处理的原文、相关卡片、引用范围 | 按当前判断需要读取，保留出处和省略提示 |
| 持久资料 | 原文、历史版本、收据、遗留草稿 | 保存到文件和状态记录，需要时定位回查 |

本轮复用了原生宿主的动态上下文机制，没有另造一套请求改写器。类型、正文要求和示例仍然保留；节省来自减少无用重复和错误修复，不是削弱规范。

### 缓存是一个收益，不能成为唯一目标

旧实现不断把剩余预算等变化写进系统提示，破坏了稳定前缀。现在固定规则保持稳定，使重复前缀更有机会复用。实际命中还受供应商实现、路由、缓存时效、工具定义和历史压缩等因素影响。

需要同时观察：未命中输入、命中输入、输出、请求次数、等待时间，以及最终质量。**很长的上下文即使命中率很高，也可能比短而准确的上下文更贵、更难理解。** 不应该为了提高百分比，故意保留无用历史。

上下文压缩也有代价。恢复摘要适合记录“完成了什么、剩下什么、去哪里找证据”，不适合替代原文里的数字、限定条件和争议表述。涉及这些细节时，应回查原文。

## 五、程序处理确定性工作，模型处理意义判断

前一轮中，模型多次为清理内容计算字符位置，遇到 Unicode、重复句子或版本变化时容易出错。材料中的来源头部也被误当作独立文章单元，导致额外阅读、结算和审核。

这类工作适合程序承担：解析来源头部、提供段落 ID、计算位置、检查原句是否唯一、统计链接和重复段落。模型负责判断哪些内容应该删除、重复是否有意义、什么内容值得沉淀。

本轮增加了材料检查工具和带版本的段落定位，并允许把已经确定的多个操作合并执行。批量工具最多执行 8 项，逐项返回结果；一个操作失败，不撤销其他成功操作。涉及依赖判断时，仍应先看前一步结果，再决定后一步，不能盲目塞进一批。

工具返回量也需要控制。批量调用虽然减少往返，但如果一次返回大量无关正文，会把节省的成本重新变成上下文负担。

这里要守住一个区别：

- 程序发现相同段落，是重复候选，不代表它一定无价值。
- 程序识别图片或链接，是结构识别，不代表它知道图片是否解释了关键机制。
- 程序登记文本已返回，证明传递发生过，不证明模型已经理解。

UNO 目前提供固定 Python 预处理和可组合的数据操作，尚不是允许模型任意执行代码的沙箱。是否增加这种能力，应取决于真实任务是否反复需要临时算法，以及执行隔离、资源限制和恢复能力是否准备好。

## 六、可靠恢复依靠事实记录，而不是一句“上次做到这里”

长任务中最容易被低估的场景是：结果已经写入，但响应丢了；一批完成了大部分，仍有两个对象待修；用户暂停后又继续。

如果恢复只读模型总结，可能重新生成已经发布的卡片，也可能把尚未完成的部分当作完成。

本轮让恢复优先检查实际草稿、材料去向、审核记录和成功收据，再定位原批待办。已发布对象不重复制卡；缺少有效证据时，仍需补读，不能凭总结补造记录。

这里有三个常见工程概念值得认识：

**幂等（idempotency）**：同一个已成功操作因网络等原因重试，不重复产生效果。UNO 用操作 ID 和收据帮助确认；修改后的新意图需要新操作 ID，不能把不同请求都当成同一次重试。

**版本冲突检查（optimistic concurrency control）**：写入前确认对象仍是模型读取时的版本。如果别人已经修改，就先读回再调整，避免覆盖新内容。

**事务（transaction）**：需要共同成立的一组写入，要么完整提交，要么回滚，避免卡片写了一半、索引和收据各说各话。事务范围应围绕实际一致性要求，不能把全库绑成一个巨大事务。

发布依赖也有方向。假设新卡 B 引用新卡 A，B 有问题，不应因此阻止正常的 A 发布；但是发布 B 时，如果它引用的 A 尚不存在，就必须处理端点依赖。本轮按这种方向隔离发布，循环依赖仍共同处理。

这类设计支持 **持久化执行与恢复（durable execution）**。UNO 已补上相关机制，但不能据此宣称具备任意故障下的完整执行保证，还需要持续做中断和恢复验证。

任务状态同样需要区分：暂停是允许继续；结束是停止本次执行；部分交付说明已有成果；覆盖完成说明约定范围已经结算。一个状态不能代替另外三个。

## 七、Harness 和审核各自解决什么问题

你之前反复追问：应该第一次拦住不合格卡片，还是第二次检查？更有用的划分依据是“程序能否可靠判断，以及出错后的影响”。

| 问题 | 更合适的处理位置 |
|---|---|
| 越过授权范围、覆盖新版本、写入不存在的关系端点 | 写入前的机械保护，不能等事后再发现 |
| 缺少约定的必填信息、参数不合法 | 明确指出具体对象和缺项，允许局部修正 |
| 标题是否准确、内容是否忠实、案例是否独立有用 | 具备来源上下文的语义审核 |
| 类比是否启发思考、领域组织是否帮助回答 | 真实检索与回答样本评测 |

机械保护应足够明确，让模型知道怎样修复。语义审核应允许讨论和局部修改，不能把每个疑问升级为整批返工。

本轮保留全新审核会话，让审核者直接获得规范、候选与相关证据，减少沿用作者过程的倾向。但“新会话”不等于统计意义上的独立判断，也不保证审核更正确。

真实例子是：审核把“超过 2000 位行业从业者”和“线下超过 1600 人”直接判作矛盾。两个表述可能范围不同，而且两个下界本身不互斥。正确处理是核对时间、对象和统计口径，说明不确定性，而不是机械要求二选一。

**审稿人也需要证据、明确任务和质量评测。** 增加一个子代理或多审几轮，可能增加视角，也可能重复相同误解。应看它是否纠正真实错误、是否引入新错误，而不只看它提出多少意见。

## 八、检索系统的职责：把适合判断的证据送到面前

知识库里有一张相关卡片，与模型最终获得了正确证据，是两回事。

如果检索总截取卡片开头，重要限定可能藏在后半段。模型看起来“没有遵守边界”，实际可能根本没收到边界。

本轮思考检索在有限预算中保留摘要、边界，并从正文开头和字面命中的后段抽取片段，附带定位与省略信息。它没有增加模型请求，也没有实现稠密向量检索，因此跨词面召回仍有限。

关系还需要区分两种用途：

**来源关系**：材料本身表达了某个案例支持某个观点，或某位作者反对另一种解释。应忠实记录原有归属与论证。

**导航关系**：模型发现两张卡片值得比较，例如都涉及基础设施投入，但约束、规模或组织方式不同。应写清比较维度和适用边界，不能伪装成原作者的论证，更不能因此推导相同因果效果。

两者都可以有用，进入思考上下文时必须保留区别。关系数量和图谱连通率无法直接证明知识质量；更有意义的问题是：这些关系有没有帮助找到本来遗漏的反例、情境和类比？

同样，领域索引的价值应体现在提供整体背景和入口，而不是为了图上多一个节点。审计自身也应核对正确的数据位置：此前用旧的 Profile 路径判断领域不存在，就是检查方法出错，不能归咎于模型没有建立领域。

## 九、怎样知道优化真的有效

这次测试过程中出现了一个有教育意义的失败：内部功能看起来可用，但原生宿主联调发现新增工具缺少说明，导致实际请求头无法形成合法 JSON。补齐说明、加入回归后，隔离样本才完成全流程。

它说明“测试通过”必须回答：**测的是哪一层？**

| 验证层 | 能说明什么 | 不能说明什么 |
|---|---|---|
| 函数和行为回归 | 字段保留、版本拒绝、失败隔离等符合预期 | 模型真实可见的工具一定正确 |
| 原生宿主 + 模拟模型 | 请求、工具、会话切换、写入与恢复链路能接通 | 模型真正理解材料、实际省多少钱 |
| 真实模型 + 固定样本 | 在给定材料和模型下的质量、成本、错误情况 | 换模型、换材料后仍必然成立 |
| 正式运行确认 | 当前服务确实加载了相应代码 | 代码具备长期稳定性或语义质量保证 |

本轮记录了后端完整回归 317 项、前端 175 项通过，构建成功。隔离原生样本完成 17 次模拟模型请求，只有 1 个系统提示哈希，工具错误为 0。最后的局部修改另有针对性回归。

这些是协议与程序行为的证据。模拟模型不提供真实供应商缓存，不能把结果解释成实际命中率上升，也不能宣称卡片质量已提高。真实知识文件没有被本轮重新编译。

本轮结束时，正式服务仍是旧进程：自动审批拒绝了停止并重启操作，返回 `blocked by policy`，没有提供具体原因；没有绕过拒绝。因此“代码和构建准备好”与“正在使用新版”必须分开说明。这是本轮记录，不代替日后的运行核对。

### 成本记录应帮助定位原因

新增观察记录包括工具耗时、错误类别、输入输出字符量和固定提示哈希；不额外复制原文、完整提示或凭据。费用分析还要使用模型返回的 usage，字符数不能当 tokens，缺少 usage 也不能算零。

接下来真实对照应固定材料、用途、模型和预算，在相同知识库起点的隔离副本中比较：

- 工具错误、重复写入和恢复后重复阅读是否减少。
- 未命中输入、总输入、输出及完成时间如何变化。
- 关键知识有没有遗漏，数字、归属和边界有没有错。
- 排除理由是否合理，是否错误丢弃高价值材料。
- 关系能否帮助实际问题获得额外有效依据。

不能只比较卡片数量，也不能只挑一个输出漂亮的样本。最好覆盖普通文章、活动宣传、长报告、多立场材料和中断恢复，并保留失败案例。如果增加审核显著改善质量，即使略有成本，也可能值得；如果只产生格式争论，就应收缩它的职责。

## 十、如果重新开始，我会怎样设计

本次暴露的问题说明，我此前把不少注意力放在“流程看起来完整”，却没有足够早地验证模型实际操作是否顺手、成功回执是否真实、恢复是否重复劳动。程序自动切分和严格结算又被过早套到所有材料上，使用户交付的判断范围变成了必须逐一消化的清单。

重新开始时，我会先做一个完整的小样本：混合几篇有价值文章、一篇明确无价值材料、一篇存在歧义的材料，走完筛选、制卡、修改、审核、暂停与恢复。重点观察模型在哪里被工具迫使返工，而不是先把所有阶段和面板做齐。

具体顺序应是：

1. **先定义结果。** 什么算排除、暂存、正式消化、已交付和覆盖完成；这些结果都要能被诚实记录。
2. **再定义少量可靠操作。** 查找、读取、局部修改、建立关系、查收据和待办；工具描述与执行必须一致。
3. **让确定性工作尽早由程序完成。** 定位、版本、计数、文件组织不反复请模型处理。
4. **从第一版就考虑恢复和观察。** 请求丢失、局部失败、用户暂停都不是罕见例外。
5. **最后依据样本增加复杂度。** 新审核、新检索、新代理必须解决已观察到的问题，并有衡量方式和撤回路径。

开源项目最值得借鉴的，是已经处理好的机制与契约，例如明确的工具结果、局部修改和原生上下文。UNO 已有合适的运行底座时，优先把它正确接入；直接更换框架，并不会自动修复“关系字段被忽略”或“省略字段被清空”这类业务错误。

## 十一、以后讨论 Agent，可以反复问的六个问题

1. **模型能作哪些真正有用的决定？** 它能否排除、补读、改方向和正常停止？
2. **程序替模型承担了哪些可靠的劳动？** 是否还在让模型反复计数、定位、搬运相同文本？
3. **模型此刻拿到的证据够不够？** 不只问磁盘里有没有，也问上下文里有没有关键限定。
4. **失败之后能修多小的一块？** 是修一个字段，还是又重跑整批？成功过的操作能否确认？
5. **质量标准是否符合知识用途？** 导航关系不能冒充论证，也不必满足严格证明才允许存在。
6. **我们拿什么证明改进？** 区分程序测试、原生联调、真实模型质量、实际成本和正式运行。

一个适合 UNO 的 Agent，应当有足够自主权判断材料价值，有足够可靠的工具处理细节，有足够准确的上下文保持方向，也有明确的记录承认“完成了哪些、还有哪些没有完成”。复杂度只有在帮助这些目标时，才值得留下。

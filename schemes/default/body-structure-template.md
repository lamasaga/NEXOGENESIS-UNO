# 知识卡正文结构契约

本契约由新编译、建构、涌现、精修、质量审核和 HarnessGateway 共同使用。卡片分类只有单一 `type` 与多个 `domains`；完整定义和示例见 `docs/design/knowledge-guidance/card-types.md`。

## 1. 卡片字段

新建或完整重写的卡片使用：

- 必需：`id`、`title`、`type`、`domains`、`origin`、`sources`、`relations`、`body`；
- 运行时补充：`schema`、`maturity`、`lifecycle`、`created`、`updated`、版本与审核记录；
- 条件字段：实体卡的 `entity_kind`、稳定别名 `aliases`，退役卡的 `superseded_by`。

`type` 只能取 `conflict/entity/case/concept/method/mechanism/model/claim/phenomenon/undetermined` 中一个，并按此顺序严格判定。`domains` 只能引用既有领域，通常 1–2 个、最多 3 个；无合适领域时允许 `[]`。新卡不得写 `tags/topics`。

历史卡中的旧字段可以读取，但任何新写入都按本契约生成。

## 2. 九种实质类型与未定正文骨架

下列二级标题是硬性语义槽。标题可使用列出的同义形式；每个槽都必须有实质内容，不能用“原文未提及”“暂无”“待补充”凑格式。

| type | 必需二级标题 |
|---|---|
| `concept` | 定义 → 关键特征 → 边界与辨析 → 来源与证据边界 |
| `claim` | 核心主张（兼容：一句话主张） → 依据 → 已知限制 → 来源与证据边界 |
| `mechanism` | 起点与条件 → 传导链条 → 结果 → 失效边界 → 来源与证据边界 |
| `model` | 核心思想 → 关键组件 → 结构关系或因果链条 → 失效边界 → 来源与证据边界 |
| `method` | 输入 → 步骤 → 输出 → 适用边界 → 来源与证据边界 |
| `phenomenon` | 模式描述 → 典型实例 → 反例与失效条件 → 来源与证据边界 |
| `case` | 情境与对象 → 过程 → 结果与证据 → 可迁移启示 → 限制与边界 → 来源与证据边界 |
| `entity` | 定义 → 关键属性 → 边界与局限 → 来源 → 来源与证据边界 |
| `conflict` | 对立双方 → 核心分歧点 → 各自证据或代价 → 调和可能 → 来源与证据边界 |
| `undetermined` | 知识对象 → 核心内容 → 依据 → 限制与边界 → 来源与证据边界 |

正文骨架服务于可读性和判断，不要求每段同样长。必要条件应靠近对应结论，不能先写绝对结论，再在末尾用空泛免责声明补救。

## 3. 选择类型的原则

类型由卡片主要回答的问题决定。必须按 `conflict → entity → case → concept → method → mechanism → model → claim → phenomenon → undetermined` 顺序逐项检查。只有完整满足某类的最低成立条件才能命中，命中后停止；不得为适配骨架而补写来源没有的结构。详细门槛见 `docs/design/knowledge-guidance/card-types.md`。

`phenomenon` 只用于有观察对象和观察依据的状态、趋势、分布、差异或反复模式，不是无条件兜底。`undetermined` 用于其他九类均不成立，但仍完整、可独立阅读且可复用的知识单元；不得用它保存空洞、未读完或编译失败的内容。

正文含有多种材料不代表多类型。一张机制卡可以包含案例证据，仍只写 `type: mechanism`。若两个对象都能独立回答不同问题，再拆成两张卡。

## 4. 来源与证据边界

该段应说明：

- 哪些判断来自本次来源；
- 作者原意、跨来源综合与系统推断如何区分；
- 样本、时期、制度和方法限制；
- 当前材料不能推出什么。

它可以替代逐字引文，不得编造引文。来源路径与字符区间由宿主绑定；模型只引用本次提供的真实 `ref`。

## 5. 关系与领域

`domains` 只表达组织归属，不证明因果、支持、反驳或类比。领域成员以卡片自身字段为准。

关系必须读取两端内容并说明方向。主题相近、同属领域或关键词相同都不足以建边。没有可靠关系时允许空数组；不得为连边率制造关系。

## 6. 审核与局部修复

审核先检查知识对象、类型、正文槽、领域、来源和关系。问题必须指出卡片、具体位置、具体改法及当前材料中的理由。可选扩展和文风差异不阻止保存。

通过卡先保存。问题卡的修复请求只携带该卡与具体问题，不携带整章、其他候选或历史。修复保持 ID，不改无关段落，不新增问题未支持的事实或关系；复核只检查原问题是否解决和本卡是否自相矛盾。

## 7. 内部语义地址

少量会被反复精确读取的主张、机制、条件、证据、定义或边界可以使用 `<!-- unit: kind-local-id -->`。它不是类型、领域或图节点。卡内 ID 必须唯一，不给所有段落机械编号；通常 2–4 个，高于 8 个需复核是否过度切分。

## 8. 历史 Buffer

`05-Buffer/books/` 保存新编译的清洗拆分 Markdown 单元、目录和提取图片；原始文件保存在 `03-Archive/books/`。这些单元是卡片可追溯来源，按提取版本持续保留，不自动加入全量检索索引。Buffer 中既有材料和稳定索引保持兼容；旧 role、digest 骨架和提示词不能定义新卡的类型或领域。
